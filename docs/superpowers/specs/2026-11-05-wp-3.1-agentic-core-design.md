## Konflik kontrak (dilaporkan sebagai #72, tidak dipilih diam-diam)

Konflik yang mengubah apa yang dibangun di WP-3.1 dicatat di sini. Konflik yang hanya relevan untuk satu sub-WP diputuskan di spec sub-WP itu.

1. **Registry.** FR-041, ARCHITECTURE §6, `AGENT_REGISTRY_PATH` (`/app/agents/registry.yaml`, skema 1, 42 entri), dan AGENT_CATALOG §12.9 (loader v1; v2 di WP-9.0) merujuk file yang tidak ada. Repo hanya punya `agents/registry.v2.yaml` (skema 2, 53 entri, 20 aktif). Diputuskan di 3.1b: file v2 disalin ke `/app/agents/registry.yaml` di image dan loader membaca skema 2.
2. **Kontrak I/O agent** (`agents/contracts.py`): namanya disebut (`IntakeInput/Output`, `PlanInput/Output`, …), field-nya tidak didefinisikan di dokumen mana pun. Dipindah ke 3.1f (spec 3.1b, Non-goals): kontrak dibuat bersama runtime yang memakainya; sampai saat itu nama kontrak dijaga peta `RUNTIME_CONTRACTS`.
3. **Skenario scripted:** `generic`, `calc`, `calc-debug`, `calc-gap` hanya berupa nama di WBS dan tracker. Isinya dan cara memilihnya tidak didefinisikan, dan berbeda dari daftar TEST_STRATEGY §4. 3.1a menetapkan kerangka dan cara memilih; isinya di 3.1f.
4. **Allowlist vs tool yang ada:** agent aktif di registry mengizinkan tool yang tidak dibangun di WP-3.1 (`tests.run`, `review.*`, `acceptance.*`, `memory.*`, `security.scan_secrets`, `env.inspect_runtime`). Hal ini melanggar AGENT_CATALOG §4.4/§10 (tool dibangun sebelum di-allowlist). Diputuskan di 3.1b/3.1d.
5. **Layering:** ARCHITECTURE §3.2 melarang tools mengimpor llm, tetapi §4.2 membuat `tool_defs_for` mengembalikan `ToolDef` (tipe llm); IMPLEMENTATION_DESIGN_V2 §4.3 mengizinkan tools → llm(base). Keputusan Lead: `ToolDef` tinggal di `app/llm/base.py`, dan tools boleh mengimpor `app.llm.base` saja (kontrak import-linter di 3.1d).
6. **Path:** prompt `agents/prompts/` vs `app/agents/prompts/` (#16); tarif `config/pricing.yaml` (CONFIGURATION, default Settings) vs `backend/config/pricing.yaml` (RUNBOOK §5, ADR-004). Untuk tarif: 3.1a memakai `backend/config/pricing.yaml` di repo, yang di image menjadi `/app/config/pricing.yaml`. Itu sama dengan default `config/pricing.yaml` relatif terhadap `WORKDIR /app`, jadi kedua rujukan dipenuhi.
7. **Smoke test:** §9 menjawab `{job_id}`, §11 #8 sinkron. ADR-004 menaruh key di `api` untuk smoke test, sedangkan ARCHITECTURE §2 dan compose hanya di `worker` (#12/#40). Diputuskan di 3.1e.
8. **Approval:** kedaluwarsa API §11.1 (7 hari/24 jam) vs SECURITY_MODEL §5 (24 jam/1 jam) (#13); `waive_criterion` ada di CHECK tetapi "bukan approval"; jawaban `DELETE /projects` §3 vs §11 #14. Diputuskan di 3.1c.
9. **`usage:read`** dipakai `GET /usage` (§9) tetapi tidak ada di RBAC v1 (§2, `rbac.py`). Diputuskan di 3.1f.
10. **Bentuk data:** `agent_profiles` tidak punya purpose/trigger/kontrak (FR-042); `AgentRun` §11.2 punya `cost_status`/`agent_name` yang tidak ada di tabel; `ToolCall.output_artifact_id` vs `output_ref`. Diputuskan di sub-WP pemilik tabelnya.
11. **Tiga batas iterasi** yang tumpang-tindih: `budget_limit.max_tool_iterations` (task), `CLAUDE_MAX_TOOL_ITERATIONS` (per run), dan `limits.max_iterations` di registry. Biaya dengan `cost_status=unavailable` terhadap `max_cost_usd` juga tidak didefinisikan. Diputuskan di 3.1f.
12. **Batas konteks:** `repo.read_file` 64 KB (TOOL_CATALOG) vs 256 KB (ARCHITECTURE §7) vs 60 KB per request (ADR-011). Diputuskan di 3.1d.
13. **FR-158** (kill switch, P0) tidak ada di daftar FR WP-3.1 di WBS, `provider_calls_enabled` tidak ada di DATA_MODEL `projects.settings`, dan `SETTINGS_KEYS` menolak kunci asing. 3.1e menambahkannya.
14. **Uji adapter:** TEST_STRATEGY §3 menyebut transport tiruan dan `respx` (dev dependency). SDK resmi yang boleh dipakai (`anthropic` 1.13.0, rilis sebelum batas `exclude-newer`) memakai `httpx2`, bukan `httpx`, sehingga `respx` tidak bisa menangkap request-nya. 3.1a memakai `httpx2.MockTransport` lewat parameter `http_client` milik SDK.

## 3.1a — rancangan

### Intent

Backend dapat memanggil Claude lewat satu pintu (`LLMProvider`): adapter SDK resmi untuk produksi, atau `ScriptedProvider` yang deterministik untuk test dan demo. Error vendor dinormalisasi ke satu set jenis, retry dibatasi dan menghormati `retry-after`, setiap percobaan melaporkan token, durasi, dan request ID-nya, dan biaya diestimasi dari tabel tarif berversi. API key dan isi prompt tidak pernah muncul di log, pesan error, atau repr.

Belum ada loop agent, tabel, atau endpoint di 3.1a. Penulisan `usage_records` ada di 3.1f; 3.1a menyediakan data per percobaan yang akan ditulis di sana.

### Goals

1. **Port `app/llm/base.py`** (AG-00 pemilik kontrak), sesuai ARCHITECTURE §4.2:
   - Blok konten: `TextBlock(text)`, `ToolUseBlock(id, name, input: dict)`, `ToolResultBlock(tool_use_id, content: str, is_error: bool)`. `Message(role: "user" | "assistant", content: str | tuple[blok, ...])`.
   - `ToolDef(name, description, input_schema: dict)`. Nama kanonik bertitik: segmen huruf kecil dipisah `.`, tiap segmen `[a-z][a-z0-9]*` dengan `_` hanya di antara karakter (jadi tanpa `__`, dan tanpa `_` di awal/akhir segmen, karena `a_.b` di-encode `a___b` lalu di-decode `a._b`) (ADR-023); panjangnya ≤ 64 setelah di-encode.
   - `LLMRequest(model, system, messages, tools, max_tokens, metadata, cache_system=True, timeout_s)`. `metadata` (task_id, agent_id, agent_run_id, scenario) hanya untuk sisi KodeKantor dan **tidak dikirim** ke provider.
   - `Usage(input_tokens, output_tokens, cache_creation_tokens, cache_read_tokens)`; hitungan negatif ditolak.
   - `repr(LLMRequest)` tidak memuat `system` dan `messages`, supaya prompt tidak masuk log lewat repr (AG-13 I1).
   - `LLMResponse(content, stop_reason: "end_turn" | "tool_use" | "stop_sequence", usage: Usage | None, model, request_id, duration_ms)`.
   - `LLMError(kind, *, retry_after_s, request_id, usage, status_code)`. `kind` ∈ `rate_limited | overloaded | transient | timeout | refusal | bad_request | auth | malformed | cancelled | max_tokens`; `retryable` diturunkan dari `kind`: hanya `rate_limited`, `overloaded`, `transient`, `timeout` (ARCHITECTURE §6.1). Pesannya hanya memuat jenis, status HTTP, dan tipe error vendor, tidak pernah body request atau response.
   - `LLMProvider` (Protocol): `name`, `create_message(req, *, on_text_delta=None, cancel=None) -> LLMResponse`. **Satu panggilan = satu percobaan.**
   - `CancelToken` di `app/core/cancel.py`, karena tools (3.1d) juga memakainya: `cancel()`, `cancelled`, `wait()`.
2. **Retry `app/llm/retry.py`:** `create_with_retry(provider, req, *, policy, on_text_delta, on_restart, cancel, on_attempt, sleep, rng) -> LLMResponse`.
   - Hanya jenis yang `retryable` yang diulang: paling banyak 4 ulangan (5 percobaan). Backoff eksponensial dengan full jitter: dasar 1 dtk, faktor 2, plafon 30 dtk.
   - `retry-after` dihormati: jeda = max(backoff, retry_after). Bila `retry_after` > 60 dtk, tidak diulang dan error diteruskan, karena worker tidak boleh tidur selama itu di tengah lease.
   - `on_attempt(AttemptRecord)` dipanggil untuk **setiap** percobaan, berhasil atau gagal: provider, model, nomor percobaan, request_id, usage (parsial bila gagal setelah `message_start`), durasi, status `ok | error | cancelled`, dan jenis error. Dari sini 3.1f menulis satu `usage_records` per percobaan (FR-133: "setiap request").
   - Cancel saat menunggu jeda → `LLMError(cancelled)`, tanpa percobaan berikutnya. `sleep` yang gagal diteruskan, bukan dianggap jeda.
   - Task pemanggil di-cancel di tengah percobaan → percobaan itu tetap dicatat (`cancelled`, usage `None` = biaya tidak diketahui, bukan 0), lalu `CancelledError` diteruskan.
   - Teks yang sudah dikirim ke `on_text_delta` tidak bisa ditarik. Percobaan yang gagal setelah mengirim teks hanya diulang bila ada `on_restart(attempt)`, yang dipanggil sebelum percobaan baru supaya konsumen membuang teks parsial. Tanpa `on_restart`, error diteruskan (temuan review backend S3 / silent M1).
   - Kegagalan `on_attempt` sendiri diteruskan: kehilangan catatan ledger tidak boleh diam.
   - Retry SDK dimatikan (`max_retries=0`), sehingga hanya kebijakan ini yang berlaku.
3. **Adapter `app/llm/anthropic_provider.py`**, satu-satunya modul yang mengimpor `anthropic` (ADR-023, CLAUDE.md #6):
   - Memakai `AsyncAnthropic(api_key, base_url, max_retries=0)` dengan klien HTTP buatan adapter sendiri, `follow_redirects=False`: klien bawaan SDK mengikuti redirect dan, pada 307 ke origin lain, meneruskan `X-Api-Key` beserta prompt (AG-13 M1). Respons 3xx → `bad_request` dengan `vendor_type="redirect"`. Seam test adalah `transport` (httpx2), sehingga konfigurasi klien test dan produksi sama.
   - Request streaming (`messages.create(stream=True)`). Event mentah dirakit sendiri: delta teks diteruskan ke `on_text_delta`, dan input tool dikumpulkan dari `input_json_delta` lalu di-parse setelah stream selesai (sesudah `message_delta`); stream yang putus sebelum itu berakhir `transient`, bukan `malformed`. Usage diambil dari `message_start` lalu diganti nilai kumulatif `message_delta`, tidak dijumlahkan.
   - Nama tool di-encode `.`→`__` saat request dan di-decode saat response.
   - `cache_system=True` → `cache_control: {"type": "ephemeral"}` pada blok system dan definisi tool terakhir. Caching hanya optimasi (PRD §7.3.4).
   - Request ID dari header `request-id`, juga pada error. String dari vendor dibatasi: tipe error, `stop_reason`, dan tipe blok harus cocok `^[A-Za-z0-9_.:-]{1,64}$` (selain itu `unrecognised`); request ID `^[A-Za-z0-9_-]{1,128}$` (selain itu `None`) (AG-13 L4).
   - `timeout_s` = batas total satu percobaan (`asyncio.timeout`); SDK diberi timeout yang sama.
   - Cancel lewat token menutup stream dan menghasilkan `LLMError(cancelled)` dengan usage parsial. Cancel menang juga atas balasan yang selesai pada saat yang sama (sama dengan `ScriptedProvider`). Bila task pemanggil sendiri di-cancel, stream ditutup lalu `CancelledError` diteruskan; cancel pemanggil selama penutupan tidak tertelan.
   - Pemetaan error:

     | Sumber | `kind` |
     |---|---|
     | HTTP 429 | `rate_limited` |
     | HTTP 529, event error `overloaded_error` | `overloaded` |
     | event error di dalam stream 200 lainnya: `api_error` → `transient`, `rate_limit_error` → `rate_limited`, `timeout_error` → `timeout`, `invalid_request_error`/`not_found_error`/`request_too_large` → `bad_request`, `authentication_error`/`permission_error`/`billing_error` → `auth`; tipe yang tidak dikenal → `transient` (diulang dalam batas retry) | lihat kolom kiri |
     | HTTP 5xx lain, koneksi putus, stream putus | `transient` |
     | timeout, HTTP 408 | `timeout` |
     | HTTP 4xx lain (400, 404, 409, 413, 422) | `bad_request` |
     | HTTP 401, 403 | `auth` |
     | `stop_reason` `refusal` | `refusal` |
     | `stop_reason` `max_tokens` atau `model_context_window_exceeded` | `max_tokens` |
     | JSON input tool tidak valid, blok atau delta tak dikenal, `stop_reason` tak dikenal, bentuk event yang tidak sesuai dokumentasi, error SDK lain | `malformed` |

     Nama event SSE yang tidak dikenal sudah dibuang SDK; `retry-after` (detik) dibaca dari setiap respons error HTTP dan dipakai hanya untuk jenis yang diulang.
     | HTTP 3xx (redirect tidak diikuti) | `bad_request` |

   - Exception SDK tidak dirantai ke `LLMError` (`from None`), supaya traceback tidak membawa body request. Exception dari `on_text_delta` milik pemanggil diteruskan apa adanya.
4. **Log tanpa prompt.** SDK mencatat "Request options" (berisi prompt) di level DEBUG, sama seperti bug yang ditemukan di snapshot. Penanganannya:
   - `configure_logging` memasang filter `QuietVendorFilter` di handler root (record di bawah WARNING dari `anthropic`, `httpx2`, `httpcore2` dibuang) dan level minimal WARNING untuk ketiga logger itu, berapa pun `LOG_LEVEL`-nya. `httpx`/`httpcore` tidak dipakai SDK dan tidak diubah (log klien sandbox tetap);
   - adapter memasang level itu lagi setelah `import anthropic`, karena SDK menyetel level dari `ANTHROPIC_LOG` saat diimpor. Handler yang ditambahkan setelah `configure_logging` hanya dilindungi pin level (AG-13 L5).

   Test regresi: (a) `LOG_LEVEL=DEBUG` dengan logger SDK di DEBUG → penanda prompt dan key tidak ada di output log; (b) interpreter baru dengan `ANTHROPIC_LOG=debug` membuktikan SDK menurunkan levelnya saat diimpor, dan kedua urutan import (logging dulu / SDK dulu) berakhir di WARNING.
5. **`ScriptedProvider` `app/llm/scripted_provider.py` + `app/llm/scenarios/`** (ADR-015):
   - Skenario adalah modul Python: `Scenario(name, scripts: {agent_id: [Turn, ...]}, default: [Turn, ...])`. `Turn` berupa `Reply(content, stop_reason, usage)`, `Fail(kind, retry_after_s?)`, atau fungsi `LLMRequest -> Reply | Fail`.
   - **Tanpa state:** giliran ke-n = jumlah pesan `assistant` di `req.messages`. Run yang dilanjutkan setelah worker restart mendapat jawaban yang sama.
   - Skenario dipilih dari `req.metadata["scenario"]`, defaultnya `generic`. Nama yang tidak dikenal → `LLMError(bad_request)`. Cara task memilih skenario ditetapkan di 3.1f.
   - Teks dipecah menjadi beberapa delta, dan cancel diperiksa di antara delta.
   - Usage tetap per giliran, sehingga test biaya deterministik.
   - Request disimpan (`requests`) hanya dengan `record_requests=True`, untuk test kebocoran secret (SECURITY_MODEL T5, `test_secret_redaction.py` di 3.1f). Worker demo tidak menyimpan prompt (AG-13 L6).
   - Skenario 3.1a: `generic` (balasan teks, lalu `submit_result` palsu bila tool itu ada di request) dan `faults` (tiap jenis `LLMError`, 429 dengan `retry-after`, stream yang di-cancel). Skenario per agent (`calc`, …) dibuat di 3.1f, saat kontrak agent dan tools sudah ada.
   - Config produksi sudah menolak `scripted`. Badge "Scripted provider (demo)" ikut layar task (WP-3.2).
6. **Tarif `app/llm/pricing.py` + `backend/config/pricing.yaml`** (FR-134, ADR-004, ADR-025):
   - Format file: `version` (tanggal), `currency: USD`, `source` (URL halaman harga resmi), `verify_before_production: true`, dan `models: {<model id>: {input, output, cache_write, cache_read}}` dalam USD per juta token, berupa string desimal.
   - `load_pricing(path) -> PricingTable` memvalidasi isi (Pydantic, `Decimal` dari string atau integer, float ditolak, harga harus > 0 karena salah ketik "0" akan tampak seperti harga sungguhan, tidak ada kunci asing). Tingkat `long_prompt: {above_tokens, …}` dipakai untuk model yang tarifnya naik di atas panjang prompt tertentu (Haiku 5.5: > 100.000 token, termasuk token cache). File rusak atau hilang → `PricingError`, bukan biaya 0. Worker memuat tabel saat start sejak pemakai pertamanya ada (ledger usage, 3.1f), sehingga file rusak menolak start.
   - `PricingTable.estimate(model, usage, *, partial) -> CostEstimate(estimated_cost: Decimal | None, cost_status, pricing_version)`. `partial` wajib dinyatakan pemanggil. Angkanya eksak, tanpa pembulatan: panggilan sangat kecil yang dibulatkan ke 0.000000 akan tampak seperti harga nol (temuan silent M3). Presisi simpan di ledger diputuskan 3.1f:

     | Keadaan | `estimated_cost` | `cost_status` |
     |---|---|---|
     | model ada di tabel, usage lengkap | angka | `estimated` |
     | percobaan putus setelah `message_start` | angka dari usage parsial | `partial` |
     | model tidak dikenal, atau usage tidak ada | `null` | `unavailable` |

     Nilai `actual` dicadangkan (ADR-025). Usage percobaan parsial adalah batas bawah: provider mengirim hitungan output di akhir stream, sehingga percobaan yang terpotong bisa menunjukkan 1 token output untuk ribuan yang ditagih (AG-13 M2). BudgetGuard 3.1f wajib memperhitungkannya.
   - Isi awal: model Claude yang tercantum di halaman harga resmi pada tanggal `version`, diambil saat implementasi. `verify_before_production: true` tetap sampai operator memverifikasinya.
7. **Factory `app/llm/factory.py`:** `build_provider(settings, *, transport=None) -> LLMProvider`.
   - `anthropic` tanpa key → `ProviderNotConfigured`. Config tidak mewajibkan key per proses (ditunda ke ADR-053), jadi pemanggil yang memutuskan. `Settings` men-strip key (kosong = tidak ada), supaya literal redaksi sama dengan key yang dikirim (AG-13 L2). Produksi menolak `ANTHROPIC_BASE_URL` selain https dengan host (AG-13 L1). Base URL kosong berarti default SDK, bukan `""`, karena compose meneruskan `${ANTHROPIC_BASE_URL:-}` (AG-13 L8).
   - `scripted` → `ScriptedProvider`.
   - Model tidak dipilih di sini; pemanggil membaca `CLAUDE_MODEL_*` (FR-130).
8. **Dependensi dan layering:**
   - Dependensi `anthropic>=1.13` (terkunci 1.13.0, MIT; membawa `httpx2`/`httpcore2`, BSD-3). `pyyaml` pindah dari grup dev ke dependensi runtime.
   - Image backend menyalin `backend/config` ke `/app/config`; konteks build hanya membuka `backend/config/pricing.yaml` (AG-13 L7).
   - import-linter:
     - `app.llm` masuk lapisan yang sama dengan `app.workspace | app.gitops | app.sandbox` (llm → core saja);
     - `ignore_imports = ["app.llm.anthropic_provider -> anthropic", "app.llm.anthropic_provider -> httpx2"]`;
     - kontrak framework-free mencakup `app.llm`;
     - kontrak baru melarang `httpx2`/`httpcore2` di luar adapter.
   - Pyright standard untuk `app/llm` (ADR-017; sudah berlaku untuk seluruh `app`).

### Non-goals

- Loop agent, `submit_result`, prompt, BudgetGuard, tabel `usage_records`/`agent_runs`: 3.1b dan 3.1f.
- Fallback model (FR-131, P1).
- Smoke test dan readiness: 3.1e.
- Server tools, citations, `on_event`, sensitivity (IMPLEMENTATION_DESIGN_V2 §5.0.1, Proposed).
- Panggilan ke API nyata di CI.

### Anti-goals

- Key, header Authorization, atau isi prompt muncul di log, pesan error, repr, atau traceback.
- Biaya 0 atau angka karangan saat tarif atau usage tidak diketahui.
- Retry yang tidak terlihat: setiap percobaan menghasilkan `AttemptRecord`.
- Modul selain adapter mengimpor `anthropic` atau `httpx2`.

### Pendekatan

| | Isi | Untung | Rugi |
|---|---|---|---|
| **A. Satu percobaan per `create_message`, retry di pembungkus** (dipilih) | Provider mengerjakan satu percobaan; `create_with_retry` mengulang dan melaporkan tiap percobaan | Setiap request punya record sendiri (request_id, token, durasi); kebijakan retry diuji tanpa HTTP; scripted dan Anthropic memakai retry yang sama | Pemanggil harus memakai pembungkus, tidak memanggil provider langsung |
| B. Retry di dalam adapter | Adapter mengulang sendiri dan mengembalikan `retry_count` | Pemanggil sederhana | Token percobaan yang gagal hilang dari ledger (FR-133); scripted perlu retry sendiri |
| C. Retry bawaan SDK | `max_retries=4` | Tanpa kode | Percobaan tidak terlihat; `retry-after` dan jeda tidak bisa dibatasi atau di-cancel |

### Review Focus (dibuktikan test)

1. Prompt dan key tidak ada di log pada `LOG_LEVEL=DEBUG` + `ANTHROPIC_LOG=debug`, dan tidak ada di `str`/`repr` `LLMError` maupun provider.
2. Setiap jenis error dipetakan sesuai tabel, termasuk error di tengah stream setelah sebagian teks terkirim. Hanya jenis `retryable` yang diulang, dan `retry-after` dihormati.
3. Satu `AttemptRecord` per percobaan, dengan usage parsial untuk percobaan yang putus.
4. Cancel di tengah stream dan saat jeda retry menghentikan pekerjaan tanpa percobaan baru.
5. Tarif tidak dikenal → `null` + `unavailable`, tidak pernah 0; file tarif rusak menolak start.
