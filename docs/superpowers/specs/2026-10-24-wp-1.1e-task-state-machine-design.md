## Intent

CLAUDE.md #4 menyatakan status task hanya berubah lewat `workflow.states.transition`. WP ini membangun satu-satunya pintu itu, ditambah tabel yang ia butuhkan, sebelum orchestrator (WP-3.x) dan endpoint task (WP-2.x/3.x) ada. Dengan begitu, invarian ini dikunci sejak awal.

**Goals**
- Migrasi `0003_tasks` berisi `projects`, `conversations`, `tasks`, `task_dependencies`, dan `task_events`, persis sesuai DATA_MODEL. Enum memakai VARCHAR + CHECK `ck_<table>_<rule>`.
- `app/workflow/states.py` berisi:
  - `TaskStatus`;
  - `ALLOWED`, sama persis dengan diagram ARCHITECTURE §5.1 (termasuk ADR-006 dan ADR-021);
  - `transition(db, task, to, *, reason, actor)`.
- `app/core/events.py` berisi:
  - `EventBus` (Protocol) dan `RedisEventBus.publish`;
  - `emit_task_event` (seq monotonik per task dalam transaksi pemanggil);
  - `publish_pending(db, bus)` untuk publish setelah commit.
- Penjaga statis: test yang gagal bila ada modul lain di `app/` yang menulis `tasks.status`.

**Non-goals**
- Endpoint task dan project (WP-2.1, WP-3.x).
- SSE dan subscribe (WP-3.2).
- Orchestrator, lease, dan recovery sweep (WP-3.x).
- Tabel `messages`, `requirements`, `acceptance_criteria`, `repositories`, dan tabel lain di luar kelima tabel di atas (dibuat di WP pemiliknya, satu WP satu revisi).

**Anti-goals**
- Transisi di luar `ALLOWED` yang lolos.
- Dua writer bersamaan yang sama-sama "berhasil" mengubah status dari versi yang sama.
- Seq event yang bolong atau dobel dalam satu task.
- Event non-ephemeral yang dipublish sebelum transaksinya commit.

## Approaches

| | Pendekatan | Trade-off | Status |
|---|---|---|---|
| A | `transition` memakai `UPDATE … WHERE id AND version AND status RETURNING` (optimistic lock), lalu audit + event di transaksi pemanggil | Sesuai ARCHITECTURE §5.1. Pemanggil yang commit; publish dilakukan setelah commit lewat `publish_pending`. | **dipilih** |
| B | Trigger DB yang memvalidasi transisi | Logika ganda (Python + SQL). Pesan error tidak masuk envelope. Kontrak menunjuk `workflow/states.py`. | ditolak |
| C | `SELECT … FOR UPDATE` lalu update | Lock pesimis menahan baris selama langkah LLM. ARCHITECTURE memilih `version`. | ditolak |

Publish setelah commit:
- **Dipilih: outbox di `session.info`.** `emit_task_event` mencatat event tertunda di `db.info`. Pemanggil menjalankan `publish_pending(db, bus)` setelah `commit()`. Alternatif hook `after_commit` sinkron ditolak karena publish async dari hook sinkron berisiko task yatim yang gagal diam-diam.
- **Publish gagal:** cukup di-log `warning`, tidak menggagalkan apa pun. DB tetap sumber kebenaran, dan UI memulihkan lewat replay (ARCHITECTURE §9).

### `workflow/states.py`
- **`TaskStatus(StrEnum)`**: `draft`, `needs_clarification`, `planned`, `queued`, `running`, `validating`, `needs_changes`, `waiting_approval`, `interrupted`, `completed`, `failed`, `cancelled`, `rejected`.
- **`ALLOWED`**: disalin edge per edge dari diagram §5.1. `cancelled` dan `rejected` adalah terminal (himpunan kosong).
- **`Actor(type: "user"|"agent"|"system", id: str)`**.
- **`transition(db, task, to, *, reason: str | None, actor: Actor) -> None`** menjalankan:
  1. **Validasi.** `to` di luar `ALLOWED[task.status]` → `InvalidTransition` = `AppError("INVALID_TRANSITION", 409)`, dengan `details` berisi `{from, to}`.
  2. **Update dengan optimistic lock.** `UPDATE tasks SET status, status_reason=reason, version=version+1, updated_at=now(), … WHERE id=:id AND version=:v AND status=:from RETURNING …`.
     - 0 baris → `VersionConflict` = `AppError("VERSION_CONFLICT", 409)`.
     - Atribut objek `task` diperbarui dari `RETURNING`.
  3. **Efek samping kolom** [Kemungkinan Besar, dari DATA_MODEL "iteration naik pada remediation / reopen"]:
     - masuk `running` → `started_at` diisi bila masih NULL;
     - masuk `completed`/`failed`/`cancelled`/`rejected` → `completed_at = now()`;
     - `completed → queued` dan `needs_changes → queued` → `iteration + 1`, dan `completed_at = NULL`.
  4. **Audit** `task.status_changed`:
     - `actor_type`/`actor_id` dari `actor`;
     - `resource_type="task"`, `project_id` diisi;
     - `metadata={from, to, reason}`.
  5. **Event** `emit_task_event(db, None, task.id, "task.status_changed", {from, to, reason})`.
- Pemanggil yang commit. Tidak ada commit di dalam `transition`.

### `core/events.py`
- **`EventBus`**: Protocol dengan `publish(channel, message)` dan `subscribe(channel)` (subscribe diimplementasikan di WP-3.2).
- **`RedisEventBus(redis)`**: `publish` berupa `PUBLISH kk:task:{id} <json>`.
- **`emit_task_event(db, bus, task_id, type, payload, *, ephemeral=False) -> int | None`**:
  - `type` maksimal 60 karakter, dan payload diredaksi lebih dulu (SECURITY_MODEL §6.2).
  - **Ephemeral**: `bus` wajib ada, langsung publish tanpa seq, mengembalikan `None`.
  - **Non-ephemeral**:
    - `UPDATE tasks SET event_seq = event_seq + 1 WHERE id RETURNING event_seq`;
    - INSERT `task_events`;
    - pesan `{task_id, seq, type, ts, payload}` ditambahkan ke `db.info["kk.pending_events"]`;
    - mengembalikan `seq`.
- **`publish_pending(db, bus)`**: dipanggil setelah commit. Mem-publish lalu mengosongkan antrean. Publish yang gagal di-log `warning` dengan `task_id` dan `seq`, tanpa payload.
- **`discard_pending(db)`**: dipanggil setelah rollback, agar event yang tidak pernah commit tidak dipublish.
