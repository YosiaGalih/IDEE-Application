# WP-3.1d — ToolGateway, `tool_calls`, approval `tool_r3`, builtin R0/R1

Status: rancangan Lead (PO: "jalankan P2, P3 dan P4"; jalan tanpa menunggu, keputusan dicatat sebagai keputusan Lead, konflik dilaporkan ke #72). Sumber: spec induk `2026-11-05-wp-3.1-agentic-core-design.md` (baris 3.1d, Keputusan Lead 5, konflik 4, 5, 12), ARCHITECTURE §3.2/§4.2/§6.1/§7/§9/§10, SECURITY_MODEL §2 (T1, T5, T7, T10)/§3/§5/§9/§10, TOOL_CATALOG (MVP), DATA_MODEL `tool_calls`/`approvals`, API_CONTRACTS §2 (event `tool.call_*`)/§11 #6/§11.1, ADR-013/021/022/023/024/034, TEST_STRATEGY §2/§3 (AC-06, AC-13), tracker WP-1.2, WP-2.1c, WP-2.1d, WP-3.1a–3.1c2.

## Intent

Semua aksi runtime agent lewat satu pintu (CLAUDE.md #2). Pintu itu menegakkan izin di server, bukan di prompt: tool di luar allowlist agent, di luar yang ditawarkan ke model, atau di luar izin profilnya ditolak dan tercatat; aksi R3 menunggu manusia; setiap panggilan meninggalkan baris `tool_calls` yang jujur (bukti, bukan klaim). Model tidak dapat memperoleh hak lebih dengan menulis nama tool, input, atau teks apa pun.

## Goals 3.1d1

1. **Kontrak `app/tools/base.py`** (AG-00):
   - `RiskLevel(IntEnum)` R0–R4.
   - `AgentGrant(agent_id, tools: frozenset[str], permissions, tool_quota)`: apa yang registry tervalidasi izinkan untuk satu agent. Dibangun oleh `app/agents/grants.py::grant_for(registry, agent_id)` dari `AgentRegistry` di memori, **tidak pernah** dari baris `agent_profiles` (syarat 3.1b C3). `permissions` bertipe Protocol baca-saja (`PermissionView`), sehingga tools tidak mengimpor `app.agents`.
   - `ToolSpec(name, description, input_model, risk, handler, timeout_s=60, side_effect=False, write_paths=None)`. `input_model` wajib `extra="forbid"`. `write_paths(validated) -> Iterable[str]` menyebut path yang akan ditulis (dipakai aturan `test_only`/`docs_only`).
   - `ToolContext(task_id, project_id, agent_run_id, grant, offered, correlation_id, cancel, workspace=None, ports=None)`: dibangun runtime, baca-saja bagi handler. `offered` = nama tool yang ditawarkan ke model di request ini.
   - `ToolOutput(content: str | dict, evidence_refs=())`, `ToolResult(tool_call_id, status, content, is_error)`, `ToolError(code, message)` (galat yang aman ditampilkan ke model).
   - `ToolPorts(approvals: R3Approvals)` (ADR-022). `R3Approvals.authorize(session, ...) -> R3Ticket(approval_id, consumed)`; implementasinya di `app/services/tool_approvals.py`.
2. **Policy `app/tools/policy.py`:**
   - Prasyarat izin dari `TOOL_CATALOG` (`fs_read`, `fs_write`, `fs_scoped_write`, `git_read`, `git_branch_commit`, …) + `sandbox: allow` untuk R2, sama dengan aturan loader registry (satu sumber: fungsi yang sama dipakai loader dan gateway).
   - Aturan path tulis: `test_only` → hanya pola test TOOL_CATALOG; `docs_only` → `**/*.md`, `docs/**`; `scoped_write` → semua (denylist tulis tetap di `Workspace` AGENT_WRITE, 3.1d2).
   - Nama R4 (shell/terminal/host/docker/audit/policy/approval/…, SECURITY_MODEL §3, T19) tidak pernah dapat didaftarkan.
3. **`ToolGateway` `app/tools/gateway.py`:**
   - `register(spec)`: nama kanonik, ada di katalog dengan risk yang sama, berstatus `mvp`, bukan `submit_result`, bukan R4, belum terdaftar, `extra="forbid"`. Katalog bisa diganti di test (alat R3 uji).
   - `tool_defs_for(grant) -> list[ToolDef]`: allowlist ∩ terdaftar ∩ prasyarat terpenuhi, urut nama (stabil untuk cache prompt). `submit_result` milik runtime (3.1f).
   - `execute(ctx, tool_name, raw_input, *, tool_use_id=None) -> ToolResult`, urutan:
     1. **Nama dan allowlist:** nama kanonik, ada di `ctx.offered` **dan** `ctx.grant.tools`, terdaftar, bukan `submit_result` (syarat 3.1a I2/T1: `decode_tool_name` men-decode apa saja; gateway yang mencocokkan). Nama tidak sah dicatat sebagai `<invalid>`, tidak pernah digemakan.
     2. **Izin profil:** prasyarat katalog + R2 `sandbox: allow`.
     3. **Skema input:** Pydantic `extra="forbid"`. Gagal → status `error`, `error_code=invalid_input`, pesan berisi lokasi field saja.
     4. **Scope dan path:** task milik `ctx.project_id`, task belum selesai (`FINISHED`), project `active`; path tulis lolos aturan `filesystem`.
     5. **Kuota:** `grant.tool_quota[tool]` dihitung dari `tool_calls` run itu (yang sampai ke handler).
     6. **Risk dan approval:** R3 → `ToolPorts.approvals.authorize`: approval `tool_r3` yang sudah disetujui untuk hash aksi persis ini dikonsumsi (lanjut), selain itu approval `pending` dibuat atau dipakai ulang → status `approval_required`.
     7. **Klaim idempotensi** (hanya tool `side_effect`): `idempotency_key = sha256(agent_run_id|tool_use_id)` (tanpa run: `task:<task_id>|tool_use_id`); baris `running` di-commit sebelum handler. Kunci sudah ada → handler **tidak** dijalankan lagi: hasil tersimpan dikembalikan sebagai replay, atau `error` `outcome_unknown` bila baris lama masih `running` (proses mati di tengah handler). Tool side effect tanpa `tool_use_id` ditolak.
     8. **Handler** dengan `asyncio.timeout(spec.timeout_s)` dan `ctx.cancel`. Timeout → `timeout`; cancel token → `cancelled`; task pemanggil di-cancel → baris dicatat `cancelled` lalu `CancelledError` diteruskan. Untuk tool side effect, timeout/cancel berarti hasil tidak diketahui dan dikatakan begitu (thread `to_thread` tidak berhenti; tracker WP-1.2). `ToolError`/`AppError` → `error` dengan kode dan pesannya; exception lain → `error` `internal` tanpa pesan exception (bisa membawa path atau isi), dilog dengan `exc_info`.
     9. **Redaksi lalu pemotongan:** isi ke model diredaksi (`Redactor` dengan literal secret) lalu dipotong ke 64 KB UTF-8 dengan penanda; `output_summary` ≤ 2 KB. Redaksi sebelum potong, supaya potongan tidak membuat pola secret lolos.
     10. **Catat:** baris `tool_calls` diperbarui; audit `tool.denied` (setiap penolakan) dan `tool.executed` (setiap R1+ yang sampai ke handler); event task `tool.call_started` (klaim) dan `tool.call_finished` (API §2).
   - Gateway memakai `async_sessionmaker` sendiri, bukan sesi runtime: baris klaim harus ter-commit sebelum handler berjalan. Transaksi kebijakan mengunci baris task (`FOR NO KEY UPDATE`) lebih dulu, lalu approval, sama dengan urutan handler `tool_r3`.
   - Kegagalan DB saat mencatat diteruskan (tidak pernah "ok" tanpa baris).
4. **Tabel `tool_calls` (migrasi 0008_tool_calls):** `id`, `task_id` FK CASCADE, `agent_run_id` FK CASCADE null, `agent_id` varchar(40), `tool_name` varchar(80), `tool_use_id` varchar(128) null, `risk_level` smallint (CHECK 0–4), `idempotency_key` char(64) unique null, `input_hash` char(64), `sanitized_input` jsonb (diredaksi, string panjang dipotong), `status` (CHECK `running|ok|error|denied|timeout|approval_required|cancelled`), `error_code` varchar(40) null, `output_summary` text null (CHECK ≤ 2048 karakter), `output_ref` uuid null (tanpa FK sampai tabel `artifacts` ada), `approval_id` FK approvals SET NULL null, `duration_ms` null, `created_at`, `updated_at`. Index `(task_id, created_at)`, `(agent_run_id, tool_name)`.
5. **Approval `tool_r3`:**
   - Payload §11 #6 `{task_id, agent_run_id, tool, input}`, `input` = input tervalidasi (`model_dump(mode="json")`); target `{project_id, task_id}`; `risk_level` 3; kedaluwarsa 24 jam (§11.1); `requested_by = system:tool_gateway`, agent di metadata audit.
   - Paling banyak satu `tool_r3` terbuka per task (index unik parsial). Hash sama → dipakai ulang (pending) atau dikonsumsi (approved). Hash lain → approval lama `superseded`, approval baru `pending`. Approved yang lewat waktu saat dikonsumsi → `superseded` dan diminta lagi.
   - Handler (ADR-024): **disetujui** → task `waiting_approval` dilanjutkan ke status asal parkirnya (`draft` bila diparkir dari `draft`, ADR-021; selain itu `queued`); **ditolak/kedaluwarsa** → `waiting_approval → failed`. Task yang sudah selesai → tidak ada yang dikerjakan. Task yang belum diparkir (masih `running`, dsb.) → handler gagal terlihat dan sweep mengulang (balapan keputusan cepat vs engine yang memarkir). Approval **dikonsumsi oleh gateway** saat tool dijalankan ulang, bukan oleh handler.
   - Keputusan: `approval:decide` (§11.1), self-approval boleh.
6. **Syarat warisan approval (3.1c1 C3, LOW-A, LOW-E):**
   - `approval_store.decide` menjadi `UPDATE` bersyarat (`status='pending'`, hash sama, belum kedaluwarsa) dan mengembalikan apakah ia menulis.
   - Penulis status approval dibatasi di database: trigger `approvals_status_guard` (pola `tasks_status_guard`) menolak insert selain `pending`, perubahan status tanpa penanda transaksi `kk.approval_status_writer = 'approval_store'`, dan transisi di luar siklus. Penjaga AST: hanya `services/approvals.py` memanggil `approval_store.decide`; hanya `approval_store` memakai penanda itu.
   - Handler membaca jam **sesudah** lock: `dispatch` meneruskan `now` pemanggil apa adanya (`None` di produksi); handler memanggil jamnya sendiri sesudah mengunci.
   - `REQUESTABLE` sama persis dengan kunci `default_handlers` (test), jadi jenis tanpa handler tidak bisa diminta.
7. **`CancelToken` thread-safe (3.1a L3):** `cancel()` dari thread lain membangunkan penunggu lewat `loop.call_soon_threadsafe`; dari thread loop tetap langsung.
8. **Layering (konflik 5 spec induk):** `app.tools` hanya boleh mengimpor `app.llm.base`; `app.tools` dan `app.agents` tidak mengimpor `app.models.agents` (izin dibaca dari registry tervalidasi).
9. **Komposisi (ADR-022):** `app/services/tool_gateway.py::build_tool_gateway(...)` merakit gateway + `ToolPorts`. 3.1d1 belum mendaftarkan builtin.

## Non-goals 3.1d1

- Builtin apa pun (3.1d2), pembungkus `<untrusted_content>` (3.1d2), AgentRuntime, `submit_result`, nudge, BudgetGuard (3.1f), engine yang memarkir task di `waiting_approval` (3.2), endpoint `GET /tasks/{id}/tool-calls`, server tools v2 (`executor=provider`, WP-9.0), `ApprovalGrant` v2.
- `test_prompt_injection.py` ujung-ke-ujung: butuh runtime dan builtin (3.1f). 3.1d1 menguji lapisan gateway-nya.

## Anti-goals

- Izin dibaca dari baris DB yang bisa di-UPDATE role runtime.
- Tool side effect dijalankan dua kali untuk satu `tool_use_id`, atau "ok" tanpa baris `tool_calls`.
- Input, path, atau isi exception yang tidak diredaksi masuk audit, log, event, atau pesan ke model.
- Approval yang bisa diputuskan, dibuat dari teks model, atau dikonsumsi untuk aksi lain.

## Keputusan Lead 3.1d1

1. **Pecah 3.1d1/3.1d2** seperti tabel di atas.
2. **Sesi gateway sendiri.** `ToolContext` tidak membawa `db` (beda dari ARCHITECTURE §4.2): klaim harus ter-commit sebelum handler, dan commit sesi runtime akan ikut meng-commit pekerjaan runtime yang belum selesai. Handler yang butuh DB (3.1d2+) memakai `ctx.ports`.
3. **`AgentGrant`** menggantikan `agent_id + permissions` di `ToolContext`; isinya dari registry tervalidasi.
4. **Status tambahan `running` dan `cancelled`** (di luar DATA_MODEL): klaim sebelum handler butuh status non-final; cancel bukan timeout dan bukan error model.
5. **Idempotensi hanya untuk tool `side_effect`.** Tool R0 boleh diulang dan replay-nya memberi isi lengkap; hasil tersimpan hanya ringkasan 2 KB. Penolakan dan `approval_required` tidak membawa kunci, sehingga pemanggilan ulang sesudah keputusan dievaluasi ulang.
6. **Batas konteks (konflik 12):** tiga angka itu ukuran berbeda, bukan kontradiksi: 64 KB = batas satu `tool_result` (TOOL_CATALOG, SECURITY_MODEL §3); 256 KB = file di atas ini tidak dikirim ke model sama sekali (ARCHITECTURE §7, builtin 3.1d2); 60 KB = paket konteks A04 per request (ADR-011, runtime 3.1f).
7. **Audit:** `tool.denied` untuk setiap penolakan, `tool.executed` untuk R1+ yang sampai ke handler (SECURITY_MODEL §10); R0 yang berhasil cukup di `tool_calls`. Input tidak valid bukan penolakan kebijakan: `error` tanpa audit.
8. **Kuota sebelum approval** (urutan SECURITY_MODEL §3 menaruh kuota sesudah approval): panggilan yang akan ditolak kuota tidak boleh meminta keputusan manusia atau mengonsumsi approval.
9. **Project tidak `active` atau task selesai → `denied`** (`project_not_active`, `task_finished`): menutup syarat WP-2.1a "kebijakan status project archived/deleting" untuk jalur agent.
10. **`tool_r3` satu terbuka per task;** konsumsi oleh gateway; handler hanya memindahkan task. Kedaluwarsa (tidak diatur §11.1) diperlakukan seperti tolak.
11. **Penjaga status approval di database** (bukan AST saja): mengikuti `tasks_status_guard`; AST tetap untuk pemanggil `decide`.
12. **Event `tool.call_*` disimpan** (bukan ephemeral): penolakan harus tampil di timeline task (SECURITY_MODEL §9).

## Pendekatan

| | Isi | Untung | Rugi |
|---|---|---|---|
| **A. Gateway dengan sesi sendiri, klaim lalu handler** (dipilih) | Tx kebijakan + klaim di-commit; handler tanpa transaksi; Tx hasil | Bukti tidak hilang saat crash; replay aman; sesi runtime tidak ikut ter-commit | Dua transaksi per panggilan |
| B. Satu transaksi di sesi runtime | Baris ditulis bersama hasil | Sederhana | Crash di tengah handler = side effect tanpa baris, lalu diulang; commit bocor ke pekerjaan runtime |
| C. Kebijakan di runtime, gateway hanya eksekutor | Runtime menyaring | Gateway tipis | Dua pintu kebijakan; tool-mode agent (A04, E27) melewati kebijakan |

## Review Focus 3.1d1 (dibuktikan test)

1. Setiap langkah urutan menolak dengan alasan dan audit yang benar; nama di luar `offered` atau allowlist ditolak walau terdaftar (AC-06, T1).
2. Tool side effect tidak pernah dijalankan dua kali untuk satu `tool_use_id`, termasuk sesudah "crash" dengan baris `running`.
3. Secret di input/output/exception tidak muncul di `tool_calls`, audit, event, atau `content` ke model; output dipotong sesudah redaksi.
4. `tool_r3`: approval dibuat server, terikat hash input tervalidasi, dikonsumsi sekali oleh gateway, supersede saat input berubah; handler memindahkan task sesuai keputusan; agent tidak punya jalan memutuskan.
5. Status approval tidak bisa diubah selain lewat `approval_store` (trigger), dan `decide` menolak sendiri prasyarat yang tidak terpenuhi.
6. `CancelToken.cancel()` dari thread lain membangunkan penunggu.

## Konflik (dilaporkan ke #72)

- `tool_calls` di luar DATA_MODEL: status `running`/`cancelled`; kolom `agent_id`, `tool_use_id`, `error_code`, `updated_at`; `output_ref` tanpa FK (tabel `artifacts` belum ada); `agent_run_id` CASCADE.
- `ToolContext` beda dari ARCHITECTURE §4.2: tanpa `db`, `agent_id`/`permissions` diganti `grant`, tambah `offered`; `ToolResult.status` tambah `cancelled`.
- Urutan SECURITY_MODEL §3: kuota dipindah sebelum risk/approval (Keputusan 8).
- §11.1 tidak mengatur `tool_r3` yang kedaluwarsa: diperlakukan seperti tolak (`failed`). Resume ke `draft` bila diparkir dari `draft` (ADR-021) tidak tertulis di §11.1 ("resume → queued").
- SECURITY_MODEL §5 "(turunan)" `tool_r3` 1 jam vs §11.1 24 jam (#13): §11.1.
- `approvals`: trigger penjaga status dan index unik parsial `tool_r3` per task (tambahan).
- Batas konteks 64/256/60 KB (konflik 12): diselesaikan sebagai tiga ukuran berbeda (Keputusan 6).
- Allowlist agent aktif memuat tool yang tidak dibangun di WP-3.1 (konflik 4): tetap; `implemented=False` di katalog membuat agent itu `not_ready` (3.1b), dan gateway tidak menawarkan tool yang tidak terdaftar.
- MVP tidak punya tool R3 yang hidup (`git.push`, `deploy.staging` P2 `disabled`; registry melarang R3 untuk agent llm/profile). Jalur `tool_r3` dibangun dan diuji dengan tool R3 uji lewat katalog yang disuntikkan.
