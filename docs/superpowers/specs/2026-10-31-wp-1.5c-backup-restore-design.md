## Intent

RUNBOOK §7 sudah menulis prosedur backup, restore, dan drill, tetapi belum ada skrip, target Makefile, maupun bukti bahwa restore berhasil. DoD WP-1.5 meminta "drill restore lulus". WP ini:
- mengubah RUNBOOK §7 menjadi `scripts/backup.sh` dan `scripts/restore.sh` yang teruji;
- menutup celah prosedur terhadap stack WP-1.5a/1.5b, terutama role DB runtime;
- menjalankan drill restore otomatis di CI pada setiap PR dan nightly.

**Goals**
1. `make backup` → `$BACKUP_DIR/kodekantor-<UTC>/` berisi `postgres.dump`, `workspaces.tar.gz`, `workspaces.manifest`, `manifest.json`, dan `SHA256SUMS` (RUNBOOK §7.1). Folder 0700, file 0600, retensi `BACKUP_RETENTION_DAYS`.
2. `make restore BACKUP=<dir>` / `scripts/restore.sh [--yes] [--db-only|--workspace-only] <dir>` mengikuti RUNBOOK §7.2, ditambah langkah yang hilang (lihat keputusan).
3. Drill otomatis `infra/tests/restore_drill.sh` di CI `clean-install`: seed → backup → rusak → restore → data dan workspace sama persis dengan saat backup, stack healthy.

**Non-goals.** PITR, enkripsi di dalam skrip, salinan off-site (tanggung jawab operator, RUNBOOK §7.1), Redis (dapat dibuang), sertifikat Caddy (diterbitkan ulang), dan path v2.

**Anti-goals**
- Backup yang memuat `.env` atau secret apa pun.
- Backup "berhasil" yang tidak bisa di-restore.
- Restore yang menulis di luar folder workspace.
- Restore yang diam-diam menimpa tanpa salinan `pre-restore`.
- Backup setengah jadi yang tampak lengkap.

## Desain

### `scripts/backup.sh [--quiesce]` (env file `KK_ENV_FILE`, default `.env`)

1. **Validasi dan kunci.** `BACKUP_DIR` (default `/var/backups/kodekantor`) dan `WORKSPACE_HOST_PATH` divalidasi seperti `prepare-workspace.sh`: path absolut polos, tanpa `.`/`..`. `flock` pada `$BACKUP_DIR/.lock` mencegah dua backup atau restore berjalan bersamaan.
2. **Folder kerja.** Ditulis ke `kodekantor-<UTC>.partial/` (umask 077), lalu di-`rename` ke nama final hanya setelah semua langkah dan checksum lulus. Backup gagal tidak pernah tampak lengkap.
3. **`postgres.dump`.** `pg_dump --format=custom` dijalankan di container postgres sebagai owner. Password dibaca dari env container itu sendiri, tidak lewat argv host. Lalu `pg_restore --list` harus memuat `TABLE DATA public alembic_version`.
4. **`workspaces.tar.gz`.** `tar --numeric-owner` atas `WORKSPACE_HOST_PATH`.
   - Dikecualikan: `node_modules`, `.venv`, `__pycache__` di mana pun, serta `./*/uploads` dan `./*/.kk-runs`. Keduanya hanya di level project, supaya folder pengguna bernama `uploads` di dalam repo tetap ikut.
5. **`workspaces.manifest`.** Isinya `tar --numeric-owner -tvzf` atas arsip itu sendiri: mode, uid/gid, ukuran, mtime, dan path. Manifest dengan begitu selalu sama dengan isi arsip.
6. **`manifest.json`.** Memuat:
   - `created_at`, `git_commit`, `image_tag`, `alembic_revision`;
   - `postgres_version`, ukuran per file;
   - `counts` (`users`, `projects`, `tasks`, `audit_events`), dipakai drill (konflik #51);
   - `quiesced`, dan `retention_days`.
7. **`SHA256SUMS`.** Mencakup keempat file di atas.
8. **Retensi.** Hanya folder yang namanya persis `kodekantor-YYYYMMDDTHHMMSSZ` dan lebih tua dari `BACKUP_RETENTION_DAYS` yang dihapus. Folder `.partial` ikut dihapus setelah lebih dari 1 hari. Folder lain di `BACKUP_DIR` tidak pernah disentuh.
9. **`--quiesce`.** Menghentikan `api worker scheduler` selama dump dan tar, lalu menyalakannya lagi lewat `trap`, termasuk saat gagal.
   - Default-nya live, cocok untuk cron 02:30 sesuai RUNBOOK. Dump DB selalu konsisten sendiri, tetapi tar workspace bisa menangkap repo yang sedang ditulis.
   - Untuk upgrade atau migrasi pakai `--quiesce`.

### `scripts/restore.sh [--yes] [--db-only|--workspace-only] <dir>`

1. **Validasi isi backup.** Backup tidak tepercaya sampai dicek:
   - `SHA256SUMS` harus mencakup tepat file yang dibutuhkan mode yang dipilih, dan `sha256sum --check --strict` harus lulus;
   - `manifest.json` harus ada.
   Gagal → exit 1 sebelum ada service yang disentuh.
2. **Konfirmasi.** Operator harus mengetik `RESTORE`, kecuali dengan `--yes`. Kunci yang sama dengan backup ikut berlaku.
3. **Hentikan penulis.** `caddy web api worker scheduler sandbox-manager egress-proxy` dihentikan, dan container task sandbox (label `kk.managed=1`) dihapus. Container task mem-bind subpath workspace.
4. **DB.**
   - Role `kodekantor_app` harus sudah ada. Bila belum, postgres belum pernah diinisialisasi; jalankan `make up` sekali lebih dulu.
   - Lalu `DROP DATABASE … WITH (FORCE)` → `CREATE DATABASE … OWNER kodekantor` → ACL database dipasang ulang: `REVOKE ALL … FROM PUBLIC`, `GRANT CONNECT … TO kodekantor_app`. ACL ini hilang bersama `DROP` dan dulu hanya dibuat skrip init (konflik #50).
   - Kemudian `pg_restore --exit-on-error` dari stream.
   - Terakhir event audit `ops.restore` (system, `restore.sh`) dicatat di DB yang baru di-restore, berisi nama backup dan waktunya. Celah audit antara waktu backup dan restore jadi tercatat (konflik #52).
5. **Workspace.**
   - Folder lama di-`rename` ke `<path>.pre-restore-<UTC>` tanpa dihapus. Folder baru dibuat 10001:10001 0750.
   - Arsip diekstrak **sebagai uid/gid 10001** (`setpriv`). Arsip yang dimanipulasi dengan begitu tidak bisa menulis di luar wilayah yang boleh ditulis uid 10001, dan semua file menjadi milik 10001 sesuai invarian workspace.
   - Pemilik lain yang tercatat di manifest dilaporkan sebagai peringatan.
   - Jumlah entri hasil ekstraksi dicocokkan dengan manifest.
6. **Nyalakan lagi.** `docker compose up -d --wait`: migrate memasang `grant-runtime-role` lalu `healthcheck.sh --wait 180`.
7. **Ringkasan.** Menampilkan umur backup (RPO) dan durasi restore (RTO), serta path `pre-restore` yang dihapus operator setelah verifikasi.

### Drill (`infra/tests/restore_drill.sh`, stack `ci.env`)

1. **Seed:** satu baris audit penanda dan workspace contoh (repo git milik 10001, file dengan mode khusus, `node_modules` dan `uploads` yang harus dikecualikan, nama file dengan spasi). Lalu snapshot sha256 dan metadata pohon.
2. **Backup:** `make backup` ke `BACKUP_DIR` sementara. Cek berkas, mode, `SHA256SUMS`, counts di `manifest.json`, dan pengecualian.
3. **Rusak:** baris audit ditambah, file di-edit dan dihapus, file baru ditambah.
4. **Restore:** `scripts/restore.sh --yes <dir>`. Lalu dicek:
   - counts DB sama dengan `manifest.json`;
   - penanda ada, sisa pengrusakan hilang, dan event `ops.restore` tercatat;
   - snapshot workspace sama byte demi byte, pemilik 10001;
   - `git fsck` bersih;
   - `pre-restore` berisi keadaan rusak;
   - healthcheck lulus.
5. **Restore palsu:** satu byte arsip diubah → restore menolak sebelum menghentikan apa pun.

### Test cepat (`infra/tests/test_backup_restore.py`, stub `docker`)

Mencakup:
- isi dan mode berkas;
- `.partial` yang tidak tersisa saat dump gagal;
- retensi yang hanya menghapus folder bernama tepat;
- penolakan restore saat checksum salah, file kurang, konfirmasi salah, atau mode saling bertentangan;
- jaminan bahwa tidak ada perintah `docker` sebelum validasi lulus.

## Keputusan saya (cek)

1. **Restore memasang ulang ACL database** dan memastikan role runtime ada sebelum `pg_restore`. Prosedur RUNBOOK §7.2 ditulis sebelum pemisahan role (konflik #50).
2. **`manifest.json` memuat counts.** RUNBOOK §7.3 membandingkan jumlah project/task "dengan `manifest.json`", tetapi §7.1 tidak mencantumkannya (konflik #51).
3. **Restore mencatat `ops.restore` di `audit_events`.** Restore memutar balik jejak audit, dan sekarang putaran balik itu sendiri tercatat. Nama aksi perlu masuk katalog oleh AG-00 (konflik #52).
4. **"Drill restore lulus" di Fase 1 = drill otomatis di CI** (setiap PR dan nightly). Drill operasional bulanan di VM staging dari salinan off-site tetap RUNBOOK §7.3 / WP-7.1, diputuskan Operator + PO di G7 (konflik #53).
5. **Tanpa enkripsi di dalam skrip.** WP-14.4 menaruhnya di tier L. Salinan lokal 0700/0600 milik root; off-site wajib terenkripsi oleh operator (restic/rclone crypt, RUNBOOK §7.1). SECURITY_MODEL V14 meminta "backup terenkripsi di host" (konflik #54).
6. **Workspace di-backup penuh**, bukan hanya metadata (RUNBOOK/DEPLOYMENT/ADR-005 lebih spesifik daripada PRD §7.5 "metadata workspace", konflik #54).
7. **Sertifikat Caddy dan Redis tidak di-backup** (DEPLOYMENT §4). Restore di VM baru menerbitkan ulang sertifikat, jadi perhatikan rate limit Let's Encrypt (RUNBOOK §11).

## Setelah review AG-13 (31 Okt)

Perubahan desain restore:
1. **Validasi sebelum service berhenti** mencakup:
   - kunci;
   - folder backup milik root tanpa tulis g/o, berisi file biasa;
   - `pg_restore --list`;
   - folder workspace asli milik 10001, dan ruang untuk salinan kedua.
2. **DB lama di-rename** menjadi `kodekantor_pre_restore_<utc>`, bukan di-DROP. Bila gagal, service tetap mati dan skrip mencetak langkah kembali.
3. **Cek role setelah `pg_restore`:** tidak boleh ada role baru atau superuser lain (M1). `SHA256SUMS` dinyatakan sebagai integritas, bukan keaslian.
4. **Workspace:**
   - root kembali ke 0750 dan bit setuid/setgid dibuang;
   - hitungan entri tahan nama ber-newline;
   - workspace yang berupa mount point disimpan di `<path>/.pre-restore-<UTC>`.
5. **Backup live** menerima status 1 tar dengan `workspace_consistent: false`, dan `--quiesce` ikut menghentikan sandbox-manager.
