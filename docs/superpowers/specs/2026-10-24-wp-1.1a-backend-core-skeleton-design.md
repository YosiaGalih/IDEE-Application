## Maksud

Fondasi paling kecil yang bisa diuji, sebagai pijakan semua WP backend berikutnya:

- aplikasi FastAPI yang menolak start bila konfigurasinya salah;
- satu bentuk respons dan error untuk semua endpoint;
- log yang tidak pernah membocorkan secret;
- endpoint health yang jujur tentang dependensinya;
- CI yang menjalankan semuanya.

## Yang dibangun

1. **Proyek `backend/`.** Python 3.12, uv dengan `uv.lock`; `exclude-newer` menegakkan aturan "rilis ≥ 2 minggu".
   - Toolchain: Ruff (lint + format), Pyright, import-linter, pytest + pytest-asyncio + respx.
2. **`app/core/config.py`.** `Settings` memuat semua variabel tabel pertama `docs/CONFIGURATION.md` (variabel aplikasi v1) dengan default dari dokumen.
   - Nilai wajib (★) yang hilang/invalid → `ConfigError` dengan **nama variabel dan aturan saja, tanpa nilai**.
   - Aturan production: `SECRET_KEY` ≥ 32 dan bukan contoh; `LLM_PROVIDER=scripted` ditolak (ADR-015); `SANDBOX_DRIVER=fake` ditolak; `COOKIE_SECURE=true`; `LLM_REQUIRE_READINESS=true`; `CELERY_TASK_ALWAYS_EAGER=false`.
   - Tambahan: `SANDBOX_MANAGER_TOKEN` ≥ 32.
3. **`app/core/redaction.py`.** Pola dari SECURITY_MODEL §6.2, ADR-030, appendix T12, dan M.2:
   - prefiks kunci: `sk-ant-admin` sebelum `sk-ant-`, `ghp_/ghs_/ghu_/github_pat_`, AKIA, `xox*`;
   - PEM private key, URL berkredensial, `ticket=`;
   - header `Authorization` / `Cookie` / `Set-Cookie` / `X-Api-Key`;
   - `key=value` / `key: value` untuk nama sensitif;
   - nilai literal secret dari settings.

   Wajib ada test negatif (`token_count = 3` tidak disensor).
4. **`app/core/logging.py`.** structlog JSON dengan processor redaksi dan `request_id` dari contextvar.
5. **`app/core/errors.py`.**
   - `AppError` dengan kode dan HTTP status dari API_CONTRACTS §1.
   - Handler untuk `AppError`, 404, 405, 422 (`VALIDATION_ERROR` + `details[{loc,msg}]`), dan 500 (`INTERNAL_ERROR` tanpa stack trace/path).
   - Envelope: `{request_id, status, data, error, meta}`.
6. **Middleware request id.** `X-Request-ID` klien dipakai bila cocok `^[A-Za-z0-9_-]{8,64}$`; selain itu dibuat `req_<hex>`. Header ini selalu ada di respons.
7. **Health.**
   - `GET /api/v1/health/live` → 200, `data.status=ok`.
   - `GET /api/v1/health/ready` memeriksa `db` (`SELECT 1`), `redis` (`PING`), `sandbox_manager` (`GET {SANDBOX_MANAGER_URL}/healthz`, timeout 2 dtk), dan `migrations` (revisi DB = head Alembic).
   - Semua ok → 200 `status=completed`, `data={status:"ok", checks}`.
   - Selain itu → 503 `status=failed`, `data={status:"degraded", checks}`, `error.code=DEPENDENCY_UNAVAILABLE`.
   - Check yang gagal ditulis `"unavailable"`, tanpa pesan exception (bisa memuat DSN).
8. **Alembic.** Scaffold async tanpa revisi. Tabel `0001_initial` masuk WP-1.1b.
9. **CI** `.github/workflows/backend.yml`:
   - `backend-lint`: ruff check, format check, lint-imports, validasi registry;
   - `backend-types`: pyright;
   - `backend-test`: pytest dengan service `postgres:16.15-alpine` + `redis:7.4.11-alpine`.

## Keputusan saya (cek)

- **Bentuk respons `/health/ready` saat degraded memakai envelope gagal.** API_CONTRACTS §9 hanya menyebut `{status, checks}`, sedangkan §1 mewajibkan envelope di semua respons.
- **Test "setiap variabel terdokumentasi ada di Settings" dibatasi ke tabel variabel aplikasi v1.** Variabel infra (POSTGRES_PASSWORD, dll.) dan v2+ ditambahkan bersama WP-nya. Ini menghindari kegagalan yang sama dengan snapshot lama (TRACKER §1).
- **`sandbox_manager` di readiness akan `unavailable` sampai WP-1.3 ada.** Itu memang keadaan sebenarnya, dan ditampilkan apa adanya.

## Di luar scope

Tabel dan migrasi `0001_initial`, auth/sesi/CSRF/RBAC, audit, events, state machine, Celery, Docker image, compose. Semuanya menyusul di WP-1.1b dan seterusnya.
