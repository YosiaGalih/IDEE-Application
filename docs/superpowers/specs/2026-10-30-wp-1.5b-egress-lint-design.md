## Intent

**Masalahnya.**
- ADR-007 menjanjikan instalasi dependency lewat allowlist, tetapi network `kk-egress` dan proxy-nya belum ada. sandbox-manager sudah bisa memasang container ke `kk-egress`, tetapi network itu tidak pernah dibuat, jadi `SANDBOX_EGRESS=allowlist` sekarang gagal.
- DoD WP-1.5 meminta hadolint, shellcheck, dan actionlint di CI.
- Review AG-13 WP-1.5a (L1): `--forwarded-allow-ips "*"` membuat container lain di `edge`/`app` bisa memalsukan IP klien. Akibatnya rate limit login per IP bisa dilewati dan `audit_events.ip` bisa dipalsukan.

**Goals**
1. Service `egress-proxy` (profil `egress`) dan network `kk-egress`/`egress-out` sesuai DEPLOYMENT.
   - Proxy hanya meneruskan CONNECT ke tiga host di port 443. Selain itu ditolak dan dicatat.
2. Probe live yang membuktikan:
   - tiga host tembus;
   - host lain, port lain, IP mentah, HTTP polos, dan koneksi langsung gagal.
3. hadolint, shellcheck, dan actionlint di job `infra-config`. Image dipin digest, berkas diambil dari `git ls-files`.
4. api hanya mempercayai header proxy dari IP Caddy di `edge`. Subnet dan IP-nya tetap, tetapi bisa diubah operator.

**Non-goals.**
- Profil install dan tool `deps.install` (WP-6.5).
- Proxy per ekosistem (ADR-064).
- Mengubah env sandbox.
- Backup/restore.

**Anti-goals.**
- Proxy yang membuka TLS (interception) atau menyuntik CA ke sandbox.
- Proxy yang jalan walau egress mati.
- Allowlist berbasis substring yang bisa ditembus `pypi.org.evil.com`.

## Desain

### egress-proxy

```text
sandbox task (network_mode=kk-egress, internal) ──CONNECT host:443──► egress-proxy :3128 ──egress-out (bridge)──► pypi.org / files.pythonhosted.org / registry.npmjs.org
```

- `infra/egress-proxy/Dockerfile`:
  - `alpine:3.24` dipin digest;
  - `apk add tinyproxy=1.11.3-r0` (versi alpine 3.24, terbaca dari run CI pertama karena repo apk diblokir proxy cloud);
  - `USER 100:101`;
  - CA build opsional `build_ca` hanya selama `apk add`, lalu bundle asli dikembalikan dalam RUN yang sama.
- `tinyproxy.conf`:
  - `FilterURLs On` + `FilterType ere` + `FilterDefaultDeny Yes` + `ConnectPort 443`.
  - Target CONNECT berbentuk `host:443`, sedangkan HTTP polos berbentuk `http://host/...`. Allowlist hanya cocok dengan `^host:443$`, sehingga HTTP polos, port lain, subdomain mirip, dan IP mentah ditolak.
  - `DisableViaHeader`, `XTinyproxy No`, `LogLevel Connect` ke stderr: setiap target yang diminta tercatat di `docker logs`, diizinkan maupun ditolak, dan penolakan allowlist menambah baris NOTICE. Baris request dicatat apa adanya, termasuk userinfo, jadi log proxy tidak boleh diteruskan ke event atau artefak tanpa `core/redaction`.
- Compose:
  - `profiles: [egress]`, `networks: [kk-egress, egress-out]`, tanpa `ports`, read-only, tmpfs `/tmp`, limit 0.25/128M/128;
  - healthcheck `nc -z 127.0.0.1 3128`;
  - network `kk-egress` memakai `name: kk-egress` (sandbox-manager memasang container dengan nama literal), `internal: true`, `enable_ipv6: false`, dan `com.docker.network.bridge.inhibit_ipv4: "true"` agar host tidak punya alamat di bridge itu. Tanpa opsi itu, kode task bisa menghubungi layanan host yang listen di 0.0.0.0 lewat alamat gateway (review AG-13, M1); `egress-out` bridge.
  - `scripts/healthcheck.sh` memeriksa `kk-egress` setiap kali proxy jalan: internal, dibuat project compose ini, tanpa alamat host. Compose mengadopsi network bernama sama yang sudah ada dengan hanya peringatan. Pemeriksaan juga memperingatkan bila proxy jalan saat `SANDBOX_EGRESS=off`; `make egress-off` menghentikannya.
- Menyalakan: `.env` berisi `COMPOSE_PROFILES=egress` dan `SANDBOX_EGRESS=allowlist`, keduanya setelah gate keamanan (RUNBOOK §11).
  - `scripts/healthcheck.sh` gagal bila `SANDBOX_EGRESS=allowlist` tetapi `egress-proxy` tidak ada atau tidak healthy.
  - Tanpa profil, compose tidak membuat proxy maupun `kk-egress`. Permintaan egress gagal tertutup: sandbox-manager menolak `network=egress` saat `SANDBOX_EGRESS=off`, dan saat `allowlist` tanpa network, container create gagal.

### IP klien tepercaya (L1)

- Network `edge` mendapat subnet tetap `${KK_EDGE_SUBNET:-10.231.231.0/28}` dengan `ip_range` dinamis `${KK_EDGE_IP_RANGE:-10.231.231.8/29}`, dan caddy mendapat `ipv4_address: ${KK_EDGE_CADDY_IP:-10.231.231.2}` di luar range itu. Tanpa `ip_range`, container yang start lebih dulu bisa mengambil alamat caddy ("Address already in use", ditemukan saat menjalankan stack).
- api menerima `FORWARDED_ALLOW_IPS: ${KK_EDGE_CADDY_IP:-10.231.231.2}`. uvicorn membacanya dari env; defaultnya `127.0.0.1`, jadi tanpa env tidak ada proxy yang dipercaya.
- `backend/Dockerfile` tidak lagi memuat `--forwarded-allow-ips "*"`.
- Subnet 10.x berada di luar pool default Docker (172.17–31, 192.168), dan karena `edge` internal, rute keluar host tidak terpengaruh. Operator mengubah kedua variabel bersama bila bentrok.
- Probe live:
  - dari container `web` (juga di `edge`), `X-Forwarded-For: 198.51.100.9` ke `api:8000/api/v1/auth/login` harus dicatat sebagai IP `web`, bukan 198.51.100.9;
  - lewat Caddy, kunci rate limit memakai IP klien yang dilihat Caddy, bukan IP Caddy.

## Keputusan saya (cek)

1. **tinyproxy (DEPLOYMENT), bukan Squid (IMPLEMENTATION_DESIGN_V2 §15).** ADR-007 membolehkan keduanya; DEPLOYMENT lebih spesifik (image, uid, healthcheck). Dicatat sebagai konflik #45.
   - Risiko: tinyproxy pernah punya bug memori yang bisa dieksploitasi dari klien (CVE-2023-49606, diperbaiki 1.11.2) [Kemungkinan Besar], dan kliennya di sini adalah kode sandbox yang tidak tepercaya.
   - Mitigasi: versi alpine terbaru dipin; proxy hanya jalan bila egress dinyalakan; rootfs read-only, non-root, tanpa capability; Trivy wajib sebelum G1.
2. **CONNECT-only, tanpa interception.** Integritas paket bergantung pada TLS registry dan hash lockfile, bukan pada proxy.
3. **Alamat proxy untuk sandbox tidak disuntik lewat env.** SECURITY_MODEL §4 mengunci env sandbox ke empat variabel. Profil install (WP-6.5) harus memberi `--proxy http://egress-proxy:3128` di argv. Lihat konflik #47.
4. **Profil `egress` mengikuti DEPLOYMENT.** Proxy dan network tidak ada sama sekali saat egress mati.
5. **Linter sebagai image Docker yang dipin digest**, sama seperti `caddy validate`. Paket PyPI pembungkusnya ditolak: `actionlint-py` hanya sdist yang mengunduh biner saat build.
6. **Subnet `edge` tetap tetapi bisa diubah** (`KK_EDGE_SUBNET`, `KK_EDGE_IP_RANGE`, `KK_EDGE_CADDY_IP`, diubah bersama). Belum ada di CONFIGURATION (konflik #48).

## Risiko sisa (review AG-13 WP-1.5b, M2) — syarat sebelum profil `egress-allowed` pertama / G4

Allowlist CONNECT memilih tujuan TCP, bukan isi tunnel:
- `pypi.org` dan `files.pythonhosted.org` berada di Fastly, `registry.npmjs.org` di Cloudflare. Keduanya IP anycast multi-tenant, sehingga SNI/Host di dalam TLS bisa menuju tenant lain [Kemungkinan Besar].
- `registry.npmjs.org` bisa ditulis (publish/dist-tag dengan token milik penyerang).

Kode paket yang berjalan saat install (sdist `setup.py`, skrip npm) dengan begitu bisa mengirim keluar isi worktree. WP-1.5b tidak bisa menutupnya. Sebelum egress pertama dinyalakan, pilih salah satu:
- dep-proxy ADR-064 berupa mirror pull-through read-only (GET artefak saja);
- minimal SNI peek-and-splice, ditambah `pip --only-binary=:all:` dan `npm ci --ignore-scripts`. Opsi ini tidak menutup penulisan ke npm.

Selain itu, container install hanya me-mount manifest dan lockfile, bukan seluruh worktree. Keputusan produk proxy ada di konflik #45; rekomendasi review: Smokescreen, Squid peek/splice, atau langsung ADR-064.
