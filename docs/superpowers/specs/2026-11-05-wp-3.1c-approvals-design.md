# WP-3.1c — Approval, hapus project, layar `/approvals`

Status: rancangan Lead (PO: "jalankan P2, P3 dan P4"; keputusan dicatat sebagai keputusan Lead, konflik dilaporkan ke #72). Sumber: digest discovery (scratchpad sesi), spec induk `2026-11-05-wp-3.1-agentic-core-design.md` (baris 3.1c, konflik 8), API_CONTRACTS §3/§8/§11/§11.1, DATA_MODEL `approvals` + ADR-024 kolom handler, SECURITY_MODEL §3/§5/§8/§10, ADR-002/005/021/024/034, FR-018/063/067/147, AC-13/AC-19, TEST_STRATEGY §2/§3.

## Intent

Aksi berisiko (R3) hanya terjadi bila manusia yang berwenang menyetujui **persis** aksi itu, sekali, sebelum kedaluwarsa. Persetujuan terikat hash payload: bila payload berubah, persetujuan lama tidak berlaku. Agent, tool, atau teks apa pun tidak dapat menyetujui (CLAUDE.md #5). Hapus project adalah aksi R3 pertama yang memakai jalur ini dari ujung ke ujung; 3.1d menyambungkan `tool_r3` ke jalur yang sama.

## Goals 3.1c1

1. **Tabel (migrasi 0007_approvals):**
   - `approvals` sesuai DATA_MODEL: `id`, `project_id` FK CASCADE, `task_id` FK CASCADE null, `action_type` (CHECK 8 nilai v1), `risk_level` smallint (CHECK 0–4), `summary`, `payload` jsonb, `payload_hash` char(64) (CHECK hex huruf kecil), `requested_by` varchar(80) (CHECK `user:<uuid>` atau `system:<nama>`), `status` (CHECK `pending|approved|rejected|expired|consumed|superseded`, default `pending`), `handler_status` (CHECK `pending|succeeded|failed|not_required`), `handler_attempts`, `handler_error`, `decided_by` FK users RESTRICT null, `decided_at`, `decision_note` (≤ 2000), `expires_at`, `consumed_at`, `created_at`, `updated_at`.
   - Index `(project_id, status)`; index parsial handler (ADR-024, diperluas ke `expired`); **index unik parsial**: paling banyak satu `project_delete` terbuka (`pending|approved`) per project, sehingga dua DELETE bersamaan tidak membuat dua approval.
   - `projects.deleted_at timestamptz null`, CHECK `(status = 'deleted') = (deleted_at IS NOT NULL)`: jam purge 7 hari.
2. **Hash kanonik** (`app/services/approvals.py::payload_hash`): `sha256(canonical_json({"action_type", "target": {"project_id", "task_id"}, "payload"}))`, hex huruf kecil. `canonical_json`: kunci terurut, pemisah `,`/`:`, UTF-8 tanpa escape ASCII, hanya `dict` berkunci string, `list`, `str`, `int`, `bool`, `null`; `float`, NaN, dan tipe lain ditolak (tidak deterministik lintas bahasa). UUID disimpan sebagai string huruf kecil di payload.
3. **Siklus approval** (satu-satunya penulis status adalah service ini):
   - `pending → approved | rejected | expired | superseded`; `approved → consumed | superseded | expired` (konsumsi gagal karena lewat waktu); sisanya terminal.
   - **Buat:** hanya untuk `action_type` yang punya handler terdaftar; `waive_criterion` tidak pernah dibuat (ADR-034: "bukan approval"). `expires_at = created_at + EXPIRY[action_type]` dari tabel §11.1.
   - **Putuskan** (`decide`): baris dikunci; status harus `pending` dan belum lewat `expires_at`; `payload_hash` kiriman harus sama (409 `APPROVAL_PAYLOAD_MISMATCH`); pemutus harus punya `approval:decide` **dan** izin per jenis (`project:delete` untuk hapus project) pada project-nya; keputusan di-commit lebih dulu, lalu handler dijalankan dengan transaksi sendiri (ADR-024).
   - **Konsumsi atomik:** `UPDATE … SET status='consumed', consumed_at=now() WHERE id AND status='approved' AND payload_hash=:h AND expires_at > now()`; 0 baris → aksi ditolak.
   - **Supersede:** payload baru untuk aksi yang sama → approval terbuka lama `superseded`, approval baru `pending`.
   - **Kedaluwarsa:** sweep menandai `pending` yang lewat `expires_at` menjadi `expired`; keputusan atas approval yang lewat waktu juga menandainya (dan menjawab 409).
4. **Handler (ADR-024):** registry `action_type → handler` dengan tiga jalur: disetujui, ditolak, kedaluwarsa. Handler idempotent dan commit sendiri. Gagal → `handler_status=failed`, `handler_attempts+1`, `handler_error` (ringkas, diredaksi), audit `approval.handler_failed`; keputusan tidak dibatalkan. Sweep mengulang `handler_status ∈ {pending, failed}` (status `approved|rejected|expired`) maksimal 5 percobaan dengan jeda 30 dtk, 2 mnt, 10 mnt, 1 jam dihitung dari `updated_at`; sesudah 5 kali tetap `failed` dan diaudit sekali `approval.handler_gave_up` (RUNBOOK: tindakan operator).
5. **`project_delete`:**
   - **Permintaan** (`DELETE /projects/{id}`, izin `project:delete`): project `active` atau `archived` → `deleting_pending_approval`; approval `pending` dengan payload `{project_id, name, previous_status}` (§11 #6), `risk_level` 3, kedaluwarsa 7 hari; audit `project.delete_requested` + `approval.requested`. Jawaban 202 `{approval, project}` (§11 #14).
   - DELETE ulang saat sudah `deleting_pending_approval` → 202 dengan approval terbuka yang sama (idempotent). Project `deleted` → 404.
   - **Rename saat menunggu:** nama ada di payload, jadi rename membuat approval lama `superseded` dan approval baru `pending` dengan nama baru (AC-13; tracker WP-2.1a). Ubahan lain (deskripsi, settings) tidak menyentuh payload.
   - **Disetujui:** handler mengunci project, mengonsumsi approval, membatalkan task terbuka (`transition(..., CANCELLED)` untuk setiap status yang mengizinkannya; WP-INT-04), lalu project `deleted` + `deleted_at`; audit `approval.consumed` + `project.deleted`. Project hilang dari semua daftar dan akses (sudah: `visible_projects_filter`, `permissions_for`).
   - **Ditolak atau kedaluwarsa:** project kembali ke `previous_status` (§11.1); audit `project.delete_rejected` / `project.delete_expired`.
   - **Purge:** job worker per jam: project `deleted` dengan `deleted_at` ≥ 7 hari lalu → folder workspace dihapus (path dari `repo_path`/`WORKSPACE_ROOT`, tidak pernah mengikuti symlink keluar), grant `project:<id>` dihapus, lalu baris project dihapus (cascade: repository, indeks, task, run, approval). Audit `project.purged` (tabel audit tidak ber-FK ke project, jadi jejak tetap ada; ADR-005).
6. **API:**
   - `GET /approvals?status=&project_id=&page=&page_size=`: `status` = `pending` (default) | `approved` | `rejected` | `expired` | `consumed` | `superseded` | `all`. Hanya approval di project yang terlihat (`visible_projects_filter`); untuk `pending` hanya yang dapat diputuskan pemanggil (§8). `meta.total`. Urutan: `pending` menurut `expires_at` naik; lainnya `created_at` turun.
   - `GET /approvals/{id}`: project tidak terlihat → 404.
   - `POST /approvals/{id}/decision` `{decision: approve|reject, payload_hash, note?}` → `Approval`. Izin route `approval:decide`; izin per jenis di service. Status tidak `pending` → 409 `INVALID_TRANSITION` dengan `details.reason` (`expired|approved|rejected|consumed|superseded`).
   - `Approval` = bentuk §6 + `consumed_at`, `handler_status`, `can_decide`.
7. **Audit (FR-147, AC-19):** `approval.requested|decided|consumed|superseded|expired|handler_failed|handler_gave_up`, `project.delete_requested|deleted|delete_rejected|delete_expired|purged`, semuanya lewat `AuditWriter` (redaksi).
8. **Test (TEST_STRATEGY):** `tests/security/test_approvals.py::test_payload_hash_mismatch_409`, `::test_replay_consumed_rejected`, `::test_expired_rejected`, `::test_superseded_on_payload_change`, `::test_agent_cannot_decide`; kasus baru di `test_cross_project.py`; unit hash/konsumsi/kedaluwarsa/supersede dengan jam yang disuntikkan (parameter `now`), tanpa dependensi baru.

## Goals 3.1c2 (ringkas; dirinci saat 3.1c2 direncanakan)

- `/approvals` mengikuti mockup screen-11: judul "Persetujuan", kalimat "Agent tidak pernah dapat menyetujui sendiri", bagian "Tertunda (n)" per project dan "Riwayat"; kartu menampilkan jenis aksi, ringkasan, payload apa adanya (JSON terformat sebagai teks), hash (dipendekkan, lengkap di dialog), peminta, kedaluwarsa, badge risiko.
- Setujui/Tolak membuka dialog yang menampilkan payload dan hash persis yang dikirim (`payload_hash` diambil dari approval yang ditampilkan, bukan dihitung ulang di klien); catatan opsional.
- Badge jumlah tertunda di navigasi dari `GET /approvals?status=pending` (`meta.total`, refetch berkala).
- Aksi "Hapus project" di layar project untuk pemanggil dengan `project:delete` (dari `permissions` respons project), dengan konfirmasi; status "menunggu persetujuan hapus" menautkan ke `/approvals`.

## Non-goals

- Handler untuk `apply_changes`, `budget_increase`, `tool_r3`, `git_push`, `deploy_*`: dibuat oleh WP pemiliknya (3.1d, 3.2, P4). Service menolak membuat approval tanpa handler.
- `four_eyes` (ADR-034: P1) dan tabel `policy_settings`: belum ada; owner tunggal boleh memutus permintaannya sendiri (§11.1).
- Undelete dalam 7 hari: tidak ada endpoint di kontrak.
- Kolom v2 (`owner_id`, `scope_type`, `project_id` nullable; ADR-056, Proposed sesudah G3).
- Event SSE `approval.*`: event task; approval tanpa task tidak punya stream (§13.5 v2.1). 3.1c2 memakai polling.
- Dashboard `has_pending_approval`/`waiting_approval` tetap dari status task sampai approval terikat task ada (3.1d).

## Anti-goals

- Approval yang bisa dipakai dua kali, dipakai sesudah payload berubah, atau sesudah kedaluwarsa.
- Jalur apa pun (tool, header, service token, teks model) yang membuat keputusan tanpa user terautentikasi dan berwenang lewat HTTP.
- Project yang hilang dari daftar tetapi tetap bisa diakses, atau dihapus fisik sebelum 7 hari.
- Keputusan yang dibatalkan diam-diam karena handler gagal; handler gagal yang tidak terlihat.

## Pendekatan

| | Isi | Untung | Rugi |
|---|---|---|---|
| **A. Service approval generik + registry handler; handler dipanggil inline sesudah commit keputusan, sweep worker mengulang** (dipilih) | ADR-024 apa adanya | Hasil cepat terlihat; retry tahan crash | Request keputusan menunggu handler (hapus project cepat; handler lambat di WP lain bisa memakai job) |
| B. Keputusan hanya mengantre job; handler selalu di worker | Request ringan | Status "disetujui tapi belum terjadi" selalu muncul; tes lebih rumit |

## Keputusan Lead

1. **Kedaluwarsa (#13):** tabel §11.1 (ADR-034 mengikat): `apply_changes` 7 hari, `budget_increase`/`tool_r3`/`git_push`/`deploy_staging` 24 jam, `deploy_production` 4 jam, `project_delete` 7 hari. Konstanta di kode; SECURITY_MODEL §5 "(turunan)" 24 jam/1 jam dilaporkan.
2. **`waive_criterion`:** tetap di CHECK (DATA_MODEL), tidak pernah dibuat (API §11.1, ADR-034). USER_PROXY_ACCEPTANCE:34 dan SECURITY_MODEL §3 dilaporkan.
3. **Jawaban DELETE:** 202 `{approval, project}` (§11 #14 menang atas §3).
4. **`target`** dalam hash = `{project_id, task_id}` approval itu; `canonical_json` seperti Goal 2.
5. **Asal hapus:** `active` atau `archived` (payload membawa `previous_status`, dan "reject → status sebelumnya" hanya bermakna bila asalnya lebih dari satu). FR-018 ("active → archived → deleting…") dilaporkan.
6. **Supersede:** dipicu perubahan field yang ada di payload (`name` untuk hapus project); status yang dapat di-supersede: `pending`, `approved` (belum dikonsumsi).
7. **Kedaluwarsa dan tolak** mengembalikan project ke `previous_status`; supersede tidak (permintaan hapus tetap ada dengan approval baru).
8. **Purge** di 3.1c1: berkas workspace, grant project, lalu baris project; kolom `projects.deleted_at` baru (DATA_MODEL tidak punya; dilaporkan).
9. **Task aktif** dibatalkan oleh handler saat disetujui (WP-INT-04), bukan alasan menolak DELETE.
10. **Payload** persis §11 #6; ukuran dan retensi (SECURITY_MODEL §5) masuk `summary`, bukan payload.
11. **Daftar:** `pending` = yang dapat diputuskan; status lain = semua di project yang terlihat (riwayat mockup). Filter `superseded` ditambahkan.
12. **Izin keputusan:** `approval:decide` di route dan service, ditambah izin per jenis di service. `requested_by` = `user:<uuid>` / `system:<nama>`. Aturan SECURITY_MODEL §5 "requester … role lebih rendah" tidak jelas dan tidak ada di §11.1: dilaporkan, tidak diterapkan.
13. **Kode error:** tanpa kode baru; 409 `INVALID_TRANSITION` + `details.reason`; project dalam status yang tidak dapat dihapus → 409 `INVALID_TRANSITION`.
14. **Dispatch:** inline sesudah commit keputusan (API) dan dari sweep (worker); registry dibangun di kedua proses (WP-INT-03 "bootstrap handler di API & worker"). Jeda retry dari `updated_at` (kolom tambahan, dilaporkan). `not_required` untuk jenis tanpa jalur tolak (belum ada di 3.1c1).
15. **Kolom v2:** tidak sekarang.
16. **Respons:** + `consumed_at`, `handler_status`, `can_decide`; `decided_by` uuid (kontrak); catatan ≤ 2000 karakter.

## Review Focus (dibuktikan test)

1. Hash berbeda → 409, tidak ada perubahan status; approval yang sudah `consumed` tidak bisa dipakai lagi; lewat waktu → ditolak dan project kembali.
2. Rename saat menunggu hapus → approval lama `superseded`, yang baru menunjukkan nama baru; keputusan atas yang lama → 409.
3. Dua DELETE bersamaan → satu approval; dua keputusan bersamaan → satu yang berhasil.
4. Pemutus tanpa `project:delete` (developer/reviewer dengan `approval:decide`) tidak dapat menyetujui hapus project; user project lain mendapat 404.
5. Handler gagal → keputusan tetap; sweep mengulang; sesudah 5 kali tercatat dan terlihat.
6. Purge tidak menyentuh project sebelum 7 hari, dan tidak menghapus apa pun di luar folder workspace project itu.

## Konflik (ditambahkan ke #72)

- Kedaluwarsa §11.1 vs SECURITY_MODEL §5 (#13): §11.1 dipakai.
- `waive_criterion`: CHECK DATA_MODEL vs §11.1/ADR-034 ("bukan approval") vs USER_PROXY_ACCEPTANCE:34 (baris approval langsung dikonsumsi) vs SECURITY_MODEL §3 (R3).
- Jawaban DELETE §3 `{approval}` vs §11 #14 `{approval, project}`.
- `target` dan `canonical_json` tidak didefinisikan; payload hapus §11 #6 vs SECURITY_MODEL §5 (ukuran, retensi).
- FR-018 urutan `active → archived → deleting_pending_approval` vs `previous_status` di payload.
- Kolom tambahan: `approvals.updated_at`, `projects.deleted_at`, CHECK `requested_by`/`payload_hash`/`decision_note`, index unik parsial `project_delete` terbuka; index handler ADR-024 diperluas ke `expired`.
- Filter `superseded` di `GET /approvals` (§11 #… hanya `pending|approved|rejected|expired|consumed|all`).
- Izin keputusan: route `approval:decide` (§8) vs "izin sesuai `action_type`" (§11.1, ARCHITECTURE): keduanya diterapkan.
- AC-13 di DoD fase 5 (TEST_STRATEGY) vs WBS WP-3.1.
