| Kontrak | API_CONTRACTS §3 (`POST /projects/{id}/imports`, multipart ≤ 200 MB, 202), §11 #14 (respons `{repository, job_id, upload}`); DATA_MODEL `repositories.provider = upload`; ARCHITECTURE §7 (`<project>/uploads/`, batas arsip), §4 (operasi panjang → 202, worker); ADR-005 (≤ 200 MB, ekstraksi ≤ 1 GB, ≤ 50.000 file); IMPLEMENTATION_DESIGN_V2 §2 (`platform_jobs` di worker-ide) |

## Intent

User membuat project dari arsip kode (zip, tar, tar.gz) yang ia punya. Isinya menjadi repository git project itu (satu commit awal), stack-nya terdeteksi, dan project siap dibuka seperti project blank/template. Arsip berbahaya ditolak seluruhnya tanpa meninggalkan apa pun, dan user tahu alasannya. Selama unggah dan ekstraksi, user melihat kemajuan.

## Goals

1. **Project dari arsip** (`POST /projects`, sumber baru `{type: "upload"}`):
   - Baris `projects` + `repositories` dibuat dengan `provider = upload`, `sync_state = importing`, tanpa folder workspace.
   - Respons 201 `Project` seperti sumber lain. Rate limit, `CreateGate`, slug, dan audit `project.create` (`source: upload`) sama dengan 2.1a.
2. **Unggah** `POST /projects/{id}/imports` (`project:write`, pintu `require_project_permission`), multipart dengan satu field `file`:
   - Hanya untuk project `active` dengan `provider = upload`, `sync_state ∈ {importing, error}`, dan tidak ada import yang sedang berjalan. Selain itu 409 `CONFLICT` dengan `details.reason` ∈ `repository_not_empty`, `not_an_upload_project`, `import_running`, `project_archived`, `import_expired` (lock hilang selama unggah), `cleanup_failed` (sisa tidak bisa disapu). Pemeriksaan ini dilakukan **sebelum** body dibaca, sehingga unggahan 200 MB yang pasti ditolak tidak dibaca dulu. Urutannya: status → rate limit (penolakan karena status tidak memakai jatah) → lock → status sekali lagi **di bawah row lock project**.
   - **Row lock** (delta AG-13): job memegang row lock project dari pemeriksaan lock terakhirnya, lewat rename ke `repo/`, sampai commit `ready`. Pemeriksaan ulang di `begin_import` mengambil row lock yang sama, jadi job yang sedang mempublikasikan sudah selesai (`ready` → 409 `repository_not_empty`) atau akan mendapati lock-nya hilang, walau key Redis lenyap tanpa kedaluwarsa.
   - **Penanda publikasi** `.import-<job_id>.published`: ditulis job tepat sebelum rename ke `repo/`, dihapus begitu hasil commit diketahui. Penanda hanya berlaku untuk job yang **tidak** punya audit `project.import result=success` (event itu ditulis dalam transaksi `ready` yang sama dan append-only): `repo/` dengan penanda seperti itu adalah publikasi yang commit-nya tidak pernah masuk. Penanda basi milik job yang sudah commit tidak membuktikan apa pun. `repo/` lainnya tidak pernah dihapus: 409 `repository_not_empty` (perlindungan untuk WP-2.1c, yang akan menyimpan `sync_state = error` pada repo nyata).
   - **Sapu sisa** (review AG-13, MEDIUM T9): masih di bawah row lock, `repo/` berpenanda disingkirkan ke `.import-sweep-*`. Setelah itu semua yang ditinggalkan import yang terputus dihapus: isi `uploads/` (`.part` unggahan mati, arsip job mati), folder kerja, staging, penanda, dan `repo/` yang disingkirkan. Symlink hanya di-unlink, tidak pernah diikuti. Setiap job mati yang ditemukan (arsip atau folder kerja) dan belum punya event `project.import` mendapat audit `result=error reason=import_incomplete` yang tidak sempat ditulisnya. Gagal menyapu → 409 `cleanup_failed`.
   - `Content-Type` dengan `boundary` > 70 karakter (RFC 2046) → 422 sebelum lock diambil.
   - Body di-stream langsung ke `WORKSPACE_ROOT/<id>/uploads/<job_id>.part` (parser streaming `python-multipart`, batas header 8 × 4224 byte dinyatakan eksplisit). Tidak ditampung di memori atau `/tmp`.
   - Selama streaming lock diperpanjang tiap 60 detik. Body yang berhenti datang 60 detik, yang belum selesai setelah 30 menit (batas klien web juga 30 menit), atau klien yang putus (`http.disconnect`) → 408 `BAD_REQUEST` `details.reason` ∈ `upload_stalled`, `upload_too_slow`, `client_disconnected`. 408 tidak disimpan middleware idempotency, jadi retry dengan key yang sama berjalan lagi. Lock yang hilang di tengah → 409 `import_expired`.
   - Batas: arsip > 200 MiB → 413 `PAYLOAD_TOO_LARGE`, dihentikan saat batas terlewati. Field lain atau lebih dari satu file → 422.
   - Magic bytes harus zip, gzip, atau tar. Selain itu 400 `UNSUPPORTED_FILE_TYPE` dengan `details.detected_mime`.
   - Selesai unggah: sha256 dan ukuran dihitung, `.part` di-rename menjadi `<job_id>.archive`. Di bawah lock baris project: status diperiksa ulang, lock diperpanjang (sudah hilang → 409 `import_expired`), `sync_state = importing`, `error = null`, audit `project.import_requested` (`job_id`, nama file yang sudah disanitasi, ukuran, sha256, ip), commit. Lalu job worker di-enqueue.
   - 202 dengan envelope `status: accepted` dan `data = {repository, job_id, upload: {filename, size, sha256}}`.
   - Gagal di tengah (klien putus, batas, tipe, enqueue gagal) → `.part`/`.archive` dihapus, lock dilepas. Enqueue gagal → `sync_state = error`, `error = import_not_started` dan audit `project.import` `result=error` dalam satu transaksi, 503 `DEPENDENCY_UNAVAILABLE`.
3. **Satu import per project.** Lock Redis `kk:import:<project_id>` (`SET NX`, nilai = `job_id`, TTL 45 menit) diambil sebelum body dibaca, diperpanjang pemiliknya (selama unggah, di `finish_import`, saat job mulai, setelah ekstraksi, dan sebelum publikasi), dan dilepas worker (hanya oleh pemiliknya) di akhir job. Worker yang mati tidak mengunci project selamanya; TTL yang menutupnya. Job dibatasi `time_limit` 40 menit, lebih pendek dari TTL, jadi lock tidak pernah habis selama job hidup.
4. **Job worker** `app.worker.platform_jobs.import_archive(project_id, job_id, user_id, filename)` di antrean `ide` (`filename` sudah disanitasi, hanya untuk pesan commit). Ini shell tipis di atas `services.project_imports.run_import`. Semua yang ditulis job dinamai menurut `job_id`, sehingga kepemilikannya eksplisit:
   - **Satu run per job.** Job memegang `flock` eksklusif pada arsipnya. Salinan kedua (pengiriman ulang at-least-once yang berjalan bersamaan) → `skipped` tanpa menyentuh apa pun. `flock` dilepas kernel saat proses mati, jadi redelivery setelah child worker mati (OOM) langsung berjalan. Batas: `flock` per host; tier S satu node.
   - Sisa run sebelumnya dari job yang sama (`.import-<job_id>` dan staging-nya) dihapus dulu.
   - Memeriksa ulang: lock masih milik job ini (diperpanjang), project masih menunggu (`provider = upload`, `sync_state = importing`, tidak dihapus), arsip ada. Lock hilang → kegagalan `import_expired` (lihat "Menulis kegagalan"). Project tidak menunggu lagi (pengiriman ulang setelah selesai) → `skipped`. Arsip hilang padahal lock dipegang (worker tanpa volume bersama) → `import_failed`.
   - `import_archive(arsip, <id>/.import-<job_id>, strip_single_root=True)` di thread. Semua batas ADR-005 dan semua penolakan WP-1.2b berlaku. Lalu `git init` pada default branch, `commit_all` "Import from archive <nama file>" (author = user pengunggah, aturan `_author` 2.1a), dan deteksi stack, **semuanya di folder kerja**.
   - **Publikasi terakhir** (review AG-13): di bawah lock baris project, status dan lock diperiksa lagi, penanda ditulis, lalu `.import-<job_id>` di-rename menjadi `repo/` di dalam transaksi yang menulis `sync_state = ready`, `error = null`, stack, dan audit `project.import` `result=success` (`job_id`, files, dirs, bytes, `stripped_prefix`, commit). Commit gagal → `repo/` dikembalikan ke folder kerja. Jawaban commit hilang → status dibaca ulang; bila `ready`, `repo/` dipertahankan. Pembacaan ulang memakai `FOR SHARE` (menunggu commit yang masih berjalan di database, maksimal 30 detik) setelah sesi yang gagal di-rollback, lalu memutuskan dari event `project.import` success milik job ini (bukan dari `sync_state`, yang bisa sudah diubah pihak lain). Bila pembacaan ulang juga gagal → `ImportRetry` dengan `repo/` dan penanda utuh: retry mendapati `ready` (selesai, penanda dihapus) atau, di bawah row lock project, project masih menunggu (penandanya membuktikan `repo/` itu miliknya: diambil kembali, lalu import diulang). Rename yang gagal (`OSError`) menghapus penandanya; cancel yang tiba setelah rename tidak menghapusnya. `repo/` lain tidak pernah dihapus job (→ `import_failed`).
   - Gagal:
     - `ArchiveRejected(reason)` → `error = archive_rejected:<reason>`;
     - git → `import_git_failed`;
     - lainnya → `import_failed`.
   - **Menulis kegagalan:** dalam satu transaksi di bawah lock baris project (yang juga diambil `finish_import`), `sync_state = error`, `error = <kode>`, dan audit `project.import` `result=error`. Ditulis hanya bila project masih menunggu dan lock masih milik job ini atau tidak dimiliki siapa pun. Lock dimiliki unggahan yang lebih baru → `skipped` + audit `result=error` `reason = import_superseded`.
   - **Hasil tidak pasti** (Redis atau DB tidak menjawab, termasuk koneksi DB yang ditolak; kegagalan tidak bisa ditulis; commit tidak pasti) → `ImportRetry`: arsip dan lock dipertahankan, Celery mengulang (5 kali, backoff acak di bawah 5–120 detik). Setelah retry habis, atau bila retry tidak bisa diantrekan karena Redis (juga broker) mati, lock kedaluwarsa, project terbaca `import_incomplete`, dan unggahan berikutnya menyapu serta mengaudit sisanya. Job yang dibunuh `time_limit`, dibatalkan, atau mati tanpa redelivery berakhir sama.
   - Akhir: folder kerja job dihapus. Kecuali ada retry, arsip dihapus dan lock dilepas.
5. **Import yang tertinggal terlihat.** Project upload dengan `sync_state = importing` tanpa lock (unggahan tidak pernah datang, atau worker mati) dilaporkan saat dibaca sebagai `repository.sync_state = "error"`, `error = "import_incomplete"`. Polanya sama dengan masalah repo 2.1a: jalur baca tidak menulis ke DB. Unggah ulang diizinkan (Goal 2).
6. **`Repository` di respons** tetap `{provider, remote_url, branch, sync_state, last_indexed_at, error}`. `error` hanya berisi kode dari daftar di atas (`archive_rejected:<reason>`, `import_git_failed`, `import_failed`, `import_not_started`, `import_expired`, `import_incomplete`), tidak pernah teks bebas atau path.
7. **Idempotency untuk unggahan.** Middleware tidak menampung body route `/imports` (batas 10 MB untuk route lain tetap). Fingerprint-nya = query + `Content-Length`. `Content-Length` wajib; tanpa itu 400 `BAD_REQUEST`; melebihi 200 MiB + 1 MiB → 413 sebelum body dibaca.
   - Retry dengan key yang sama setelah jawaban hilang → 202 yang sama diputar ulang, tanpa import kedua.
   - Key yang sama tetapi panjang berbeda → 409 seperti biasa.
8. **Layar:**
   - **`/projects/new`:** sumber ketiga "Arsip" dengan input file (`.zip`, `.tar`, `.tar.gz`, `.tgz`) dan cek lokal ≤ 200 MiB. Kirim membuat project lalu mengunggah. Kemajuan unggah ditampilkan dalam persen (XHR `upload.onprogress`), lalu "Mengimpor…" dengan polling `GET /projects/{id}` tiap 2 detik. Hasilnya:
       - `ready` → buka workspace;
       - `error` → alasan per kode (i18n), dengan pilihan unggah ulang file lain ke project yang sama.
     Kunci idempotency create dan unggah mengikuti aturan 2.1a: dipertahankan hanya selama hasil belum pasti.
   - **`/projects/:projectId/import`:** unggah ulang untuk project upload yang gagal atau tertinggal. Komponen unggah yang sama.
   - **`/projects`:** baris project upload menampilkan "Mengimpor…" (`importing`) atau badge masalah. Bila user punya `project:write`, ada aksi "Unggah arsip" ke layar di atas.

## Anti-goals

- Arsip setengah terekstrak, atau `repo/` tanpa commit, tertinggal setelah kegagalan. Kematian proses yang tidak sempat membersihkan tidak boleh mengunci project: unggahan berikutnya menyapunya.
- Body 200 MB ditampung di memori (middleware, parser) atau di tmpfs `/tmp` container `api` (512 MB, berbagi RAM).
- Dua import berjalan untuk satu project, atau import menimpa repo yang sudah ada (FR-015 "overwrite existing").
- Nama file dari klien dipakai sebagai path atau masuk argumen git tanpa disanitasi. Path selalu `<job_id>.archive`; nama hanya untuk audit dan pesan commit (karakter tersembunyi dibuang, ≤ 255).
- `.git` dari arsip ikut masuk. WP-1.2b menolaknya (`git_dir`), dan alasan itu ditampilkan ke user dengan saran membuat arsip tanpa riwayat (`git archive`).

## Keputusan

| Topik | Keputusan | Alasan |
|---|---|---|
| Cara membuat project dari arsip | `POST /projects` `{type:"upload"}` lalu `POST /projects/{id}/imports` | Endpoint import butuh project yang sudah ada. `import_archive` hanya mengekstrak ke folder baru, dan DATA_MODEL sudah punya `provider = upload`. **Konflik #67:** API_CONTRACTS §3 tidak mencantumkan sumber `upload` |
| Import ke project blank/template | Ditolak (409 `repository_not_empty`) | FR-015 "tanpa overwrite existing"; menggabungkan arsip ke repo yang ada adalah fitur lain |
| Status "menunggu/berjalan" | Lock Redis + `sync_state = importing`; tanpa lock dibaca sebagai `import_incomplete` | DATA_MODEL tidak punya status atau kolom job; tidak perlu migrasi |
| Kemajuan | Persen unggah di klien + status impor lewat polling | Tidak ada stream SSE project di kontrak; ekstraksi ≤ 1 GB berlangsung detik–menit. [Kemungkinan Besar] cukup untuk FR-015 "menampilkan progres import" |
| Parser multipart | `python-multipart` 0.0.32 (dependensi langsung, pip-audit bersih), mode streaming | FastAPI `UploadFile` menampung ke `/tmp`; menulis parser sendiri berisiko |
| Antrean | `send_task` lewat port `JobQueue` di `Dependencies`; test menyuntikkan antrean palsu lalu memanggil `run_import` langsung | `app.api`/`app.services` tidak boleh mengimpor `app.worker` (lint-imports); `send_task` tidak menjalankan mode eager |
| Batas laju | 10 unggahan per user per jam (Redis, fail closed) | Unggahan lebih berat daripada create; tidak ada kuota (FR-153 P1) |
| Strip folder pembungkus | `strip_single_root=True` | Arsip "Download ZIP" GitHub selalu dibungkus satu folder |
| Pesan commit | "Import from archive <nama>" | Konsisten dengan "Initial commit from template <id>" |
| Kepemilikan file job | Folder kerja `.import-<job_id>`, `repo/` dipublikasikan di transaksi `ready`, `flock` arsip per run | Review backend S1/S2 dan AG-13: tidak ada `rmtree` atas dasar dugaan; salinan job kedua tidak merusak hasil pertama |
| Klaim run | `flock`, bukan kunci Redis | Kunci Redis ber-TTL tetap ada setelah child mati, sehingga redelivery segera (`reject_on_worker_lost`) akan ter-`skipped` dan import macet sampai TTL habis |
| Unggahan macet/putus | 408 dengan kode `BAD_REQUEST` | Tidak disimpan idempotency (key bisa diulang). **Deviasi:** API_CONTRACTS §1 tidak mencantumkan 408; kodenya kode yang sudah ada |

## Yang diserahkan ke builder

- Teks i18n untuk setiap alasan `archive_rejected:<reason>` (`format`, `oversize`, `ratio`, `too_many_files`, `link`, `device`, `duplicate`, `invalid_name`, `git_dir`, `traversal`, `absolute`, `empty` (arsip tanpa file: tidak ada commit awal); alasan tak dikenal → teks umum).
- Bentuk komponen unggah (satu komponen untuk kedua layar).
