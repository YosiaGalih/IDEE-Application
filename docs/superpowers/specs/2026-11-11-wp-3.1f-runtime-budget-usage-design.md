## Goals 3.1f1

1. **Ledger.**
   - Tabel `usage_records` (migrasi 0010, model `app/models/usage.py`) menyimpan satu baris untuk setiap percobaan yang sampai ke provider, termasuk yang gagal dan yang di-cancel (FR-133).
   - Writer `app/services/usage.py` mengubah `AttemptRecord` + konteks panggilan (project, task, agent run, agent, `call_id`, batas token permintaan) menjadi baris lewat `PricingTable.estimate(partial=status != "ok")`.
   - Baris ditulis di transaksinya sendiri dan bersifat idempoten per `(call_id, attempt)`.
2. **BudgetGuard** (`app/workflow/budget.py`).
   - `check_before_attempt(task, next_call)` menolak percobaan berikutnya bila pemakaian task **ditambah batas atas percobaan itu** melewati plafon efektif. Plafon yang diperiksa: durasi, iterasi tool, token, dan biaya.
   - Penolakan berupa `BudgetExceeded(kind, limit, used)`. Akuntansi konservatif menurut Keputusan Lead #6.
   - Kebutuhan ini datang dari syarat AG-13 3.1a M2. BudgetGuard baru boleh dihitung sebagai bukti T4 setelah syarat itu terpenuhi.
3. **Hook per percobaan.**
   - `create_with_retry(..., before_attempt=...)` dipanggil sebelum **setiap** percobaan, termasuk percobaan ulang.
   - Pengecualian dari hook menghentikan panggilan tanpa mengirim request (ARCHITECTURE §5.4 "sebelum setiap request"; konflik M).
4. **Tabel tarif dimuat saat worker start** (`PRICING_PATH`). File rusak atau hilang membuat worker menolak start (syarat 3.1a).
5. **`GET /usage`** (API §9, bentuk §11 #9):
   - `totals`, `series` per `group_by` (`day`/`model`/`agent`), dan `records` yang dipaginasi;
   - scope menurut Keputusan Lead #7;
   - agregasi `cost_status` menurut Keputusan Lead #5.
6. **`GET/PATCH /projects/{id}/budget`** (API §9, §11.3): default budget project menurut Keputusan Lead #2. Perubahan diaudit `project.budget_updated`.
7. **Dashboard.**
   - `usage` bulan berjalan (#70) diambil dari ledger untuk project yang terlihat.
   - `recent_tasks`/`failed_queue` membawa `usage` per task.
   - `meta.unavailable` tinggal `agent_activity`.
   - Uang ditulis sebagai string desimal; frontend diselaraskan.

## Keputusan Lead 3.1f (untuk 3.1f1)

1. **Pembagian 3.1f1/3.1f2/3.1f3** seperti di atas. Ratifikasi ADR-073 #6 menjadi prasyarat 3.1f2, bukan 3.1f1.
2. **Budget project adalah default untuk task** (API §9: "default budget project"). Ini bukan plafon kumulatif project.
   - Disimpan di `projects.settings["budget"]` = `{max_cost_usd, max_tokens, max_tool_iterations, max_duration_minutes}`. Setiap field nullable; `null` berarti mewarisi default env. `max_duration_minutes` ditambahkan dari §11.3.
   - Plafon efektif per field diambil berurutan: `tasks.budget_limit` → `projects.settings.budget` → env (`TASK_MAX_COST_USD`, `TASK_MAX_TOKENS`, `TASK_MAX_DURATION_MINUTES`).
   - `max_tool_iterations` tidak punya default env. Tanpa nilai, task tidak punya plafon iterasi tool; batas per run (registry `limits.max_iterations` dan `CLAUDE_MAX_TOOL_ITERATIONS`) tetap berlaku di 3.1f2.
   - Plafon dihitung pada saat pemeriksaan. 3.2 boleh menyalin nilai efektif ke `tasks.budget_limit` saat task dibuat; setelah itu nilai task yang menang.
   - `PATCH /projects` tetap menolak kunci `budget`. Budget hanya diubah lewat endpoint-nya, dan perubahan `settings` lain tidak menghapusnya.
   - Plafon kumulatif project (FR-132 "per project", `BudgetView` v2.2) tidak dibangun di sini. Dicatat di #72 (konflik A).
3. **Satu baris ledger per percobaan** (FR-133 "setiap request model", dan keputusan 3.1a).
   - Kolom: `call_id` (satu panggilan logis, dipakai bersama oleh retry-nya), `attempt` (mulai 1), `retry_count = attempt - 1`, `status` (`ok`/`error`/`cancelled`), `error_kind`, `request_id`, `duration_ms`, token nullable, `input_token_bound`, `output_token_cap`, `agent_id`.
   - Unik `(call_id, attempt)`: menulis ulang percobaan yang sama tidak menggandakan baris. `call_id` sejalan dengan `call_id` v2.2 (K19).
   - `project_id` NOT NULL FK `ON DELETE CASCADE`. `task_id` dan `agent_run_id` nullable FK `ON DELETE CASCADE`. Purge project menghapus riwayat biayanya; jejaknya tetap ada di audit (`project.deleted`).
   - DATA_MODEL menyebut satu baris per panggilan (`retry_count`) dan v2.2 "satu `usage_records` per panggilan": dicatat di #72 (konflik B).
4. **Presisi uang.**
   - `estimated_cost numeric(20,10)`, menyimpang dari `numeric(12,6)` di DATA_MODEL, supaya biaya kecil tidak dibulatkan menjadi 0 berlabel `estimated` (3.1a silent M3).
   - `actual_cost` dicadangkan, dengan CHECK `IS NULL` (ADR-025).
   - Di API, uang selalu **string desimal atau `null`**, sesuai API (kamus usage event: "`estimated_cost` string desimal|null"). DTO dashboard yang sekarang `float` diubah, dan frontend ikut.
   - Dicatat di #72 (konflik L).
5. **Agregasi `cost_status`** untuk totals, series, dashboard, dan `TaskSummary.usage` (konflik K):
   - tanpa baris: `estimated`, biaya `"0"`, token 0;
   - semua baris `estimated`: `estimated`;
   - ada baris `partial`, atau campuran baris berbiaya dengan baris `unavailable`: `partial`, dengan biaya = jumlah biaya yang diketahui (batas bawah);
   - semua baris `unavailable`: `unavailable` dengan biaya `null`.

   Token adalah jumlah yang diketahui. Bila ada baris tanpa token, angkanya batas bawah dan `cost_status` tidak `estimated`.
6. **Akuntansi konservatif BudgetGuard** (AG-13 3.1a M2; #11; konflik M).

   Nilai per baris ledger:

   | Baris | Token dihitung | Biaya dihitung |
   |---|---|---|
   | `ok` | token tercatat | `estimated_cost` |
   | gagal tanpa usage, `error_kind` ∈ {`rate_limited`, `overloaded`, `bad_request`, `auth`} (request ditolak sebelum diproses) | 0 | 0 |
   | gagal atau di-cancel tanpa usage, jenis lain | `input_token_bound + output_token_cap` | kasus terburuk |
   | gagal atau di-cancel dengan usage parsial | input + cache tercatat + `output_token_cap` | kasus terburuk |

   - Kasus terburuk = harga model itu, atau harga tertinggi di tabel bila modelnya tidak dikenal.
   - Hitungan token = `input + output + cache_creation`. `cache_read` dikecualikan karena loop agent mengirim ulang konteks yang di-cache; plafon biaya yang menanggungnya. [Menebak] kecocokan default `TASK_MAX_TOKENS=400000` untuk loop 40 iterasi; dicatat di #72.
   - Sebelum setiap percobaan, BudgetGuard memeriksa `used + bound(next)` terhadap plafon.
   - Durasi diukur dari `tasks.started_at`.
   - Iterasi tool dihitung dari baris `tool_calls` task yang sampai ke handler: status selain `denied` dan `approval_required`.
   - Pelanggaran → `BudgetExceeded(kind ∈ {duration, tool_iterations, tokens, cost}, limit, used)`. Pembuatan approval `budget_increase` dan transisi task adalah milik pemanggil (3.1f2/3.2), bukan BudgetGuard.
7. **Scope `GET /usage`** (#9, konflik F). Tidak ada izin baru `usage:read`.
   - `project_id` → `project:read` di project itu; tidak terlihat → 404.
   - `task_id` → `task:read` di project task itu; tidak terlihat → 404.
   - Tanpa keduanya → jumlah atas project yang terlihat (`visible_projects_filter`).
   - `usage:read_all` **tidak** memperluas ke project yang tidak terlihat di v1 (AC-01). Dicatat di #72.
   - Rentang `from`/`to` setengah terbuka (UTC); default 30 hari terakhir; maksimal 366 hari.
   - `records` dipaginasi: `page_size` default 50, maksimal 200.
8. **Ledger gagal ditulis = panggilan gagal** (3.1a silent L6).
   - Writer meneruskan kegagalannya. `create_with_retry` sudah meneruskan kegagalan `on_attempt`.
   - Respons berbayar yang tidak tercatat tidak dipakai. Di 3.1f2 run menjadi `failed` dengan kode `usage_unrecorded`.
9. **Smoke test tidak masuk ledger di v1** (konflik I). `project_id` NOT NULL, dan readiness tetap tercatat di laporannya. Dicatat di #72 sebagai penyimpangan FR-133.
10. **Pemuatan tarif saat start.** Mekanismenya dipilih di plan dan dibuktikan dengan test proses. Sinyal Celery yang menelan exception tidak cukup.
11. **Durasi hanya sesudah `started_at`.**
    - Plafon durasi berlaku sejak task pertama kali masuk `running` (`tasks.started_at`).
    - Panggilan model saat perencanaan (`draft`) dibatasi oleh `timeout_seconds` per run di 3.1f2.
    - `created_at` tidak dipakai sebagai pengganti, karena task draft yang lama menganggur akan langsung dihentikan.
12. **`agent_runs.estimated_cost` juga `numeric(20,10)`.** Diubah di migrasi 0010, supaya total run di 3.1f2 tidak membulatkan biaya yang diperbaiki di ledger (Keputusan #4).
13. **Uang di API, layar, dan JSONB.**
    - Di API: string desimal polos tanpa eksponen, lewat tipe `Money`. Serializer bawaan Pydantic menulis `5.000E-7`.
    - Di layar: biaya di atas 0 dan di bawah 0,01 tampil sebagai "< US$0,01", bukan "US$0,00".
    - Di `projects.settings.budget`: `max_cost_usd` disimpan sebagai string, karena JSONB dibaca kembali sebagai `float`.
14. **Usulan di plan diterima** (bagian "Keputusan plan" #1–#14), termasuk:
    - letak modul;
    - BudgetGuard membaca DB sendiri dan diserahkan ke runtime sebagai callable `before_attempt`;
    - harga kasus terburuk per jenis tarif;
    - pembulatan simpan ke atas;
    - batas input budget;
    - `Settings.task_max_cost_usd` bertipe `Decimal`;
    - writer memeriksa konteks dan konflik isi;
    - kontrak import-linter "Budget accounting never calls a provider".

    ARCHITECTURE §5.4 diselaraskan menjadi `check_before_attempt`.

## Review Focus 3.1f1

1. Tidak ada percobaan yang dikirim tanpa `before_attempt`, termasuk retry. Plafon diperiksa terhadap `used + bound(next)`.
2. Akuntansi konservatif: stream yang macet atau di-cancel, `usage=None`, dan model di luar tabel tidak pernah dihitung lebih kecil dari kasus terburuk. Penolakan sebelum diproses dihitung 0 hanya untuk jenis yang disebut.
3. Biaya kecil tidak menjadi 0. Uang tidak pernah `float` di API.
4. Scope `/usage` dan budget: project lain → 404; `usage:read_all` tidak memperluas.
5. Writer idempoten per `(call_id, attempt)`, dan kegagalannya tidak diam.
6. Worker tidak start dengan tabel tarif yang rusak.
