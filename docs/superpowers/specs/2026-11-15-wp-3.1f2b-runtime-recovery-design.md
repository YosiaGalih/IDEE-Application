## 1. Maksud

`AgentRuntime` (WP-3.1f2a) bisa menjalankan satu agent run, tetapi belum aman dipakai produksi. Ada tiga celah:

1. **Worker yang mati meninggalkan jejak palsu.** Baris `agent_runs` dan `tool_calls` tetap `running` selamanya.
2. **Beberapa akhir run tidak tercatat jujur.** Contohnya baris yatim saat ack `start` hilang (N5/D-I6), dan audit `budget.exceeded` yang hilang di jalur `fail()` (D-I5).
3. **Gerbang provider tidak belajar dari panggilan nyata.** Key yang ditolak (`auth`), model yang hilang (404), dan tabel tarif yang berganti tidak menurunkan readiness.

WP ini menutup ketiganya, sehingga pemanggil produksi pertama (engine WP-3.2) bisa membangun di atasnya. Prinsip produk yang dijaga:
- **#1 evidence over claims:** status hanya dari fakta DB.
- **#4 PostgreSQL sumber kebenaran.**
- **#5:** recovery tidak pernah mengarang hasil.

Dashboard `agent_activity` dan `RUNTIMES_AVAILABLE` ikut di sini karena keduanya menunggu tabel `agent_runs`, yang sekarang sudah ada.

## 2. Goals

- **G1 Recovery run.**
  - Baris `agent_runs` yang `running` tanpa pekerja hidup diakhiri `failed` / `error_code=interrupted` oleh sweep yang sudah ada (start worker + beat 30 dtk).
  - Waktu akhir diambil dari jam DB, dan usage dari ledger dengan status `partial` atau `unavailable`, tidak pernah nol "estimated".
  - Event `agent.run_finished` dikirim di transaksi yang sama.
- **G2 Recovery tool call.** Baris `tool_calls` yang `running` milik run yang dipulihkan diakhiri `error` / `outcome_unknown`, sama seperti replay WP-3.1d1. Handler tidak dijalankan ulang. Audit `tool.executed` dicatat untuk R1+, dan event `tool.call_finished` dikirim.
- **G3 Sweep run basi.** Run yang melewati tenggat wall-clock ditambah batas penutupannya diakhiri walaupun lease task-nya masih hidup. Ini jaring pengaman untuk baris yatim dan run yang macet.
- **G4 Tanpa baris yatim saat ack `start` hilang (N5/D-I6).** Id run dibuat runtime, `start` idempoten, dan `_write_end` tidak pernah membuat baris kedua.
- **G5 Kontrak pemanggil `AgentRunUnfinished` (#48).**
  - Exception membawa `agent_run_id` dan `task_id`.
  - Satu fungsi baca memberi pemanggil hasil yang tercatat di DB: akhir yang tertulis, atau "belum berakhir, milik recovery".
  - Kontraknya tertulis di ARCHITECTURE §6.1.
- **G6 Audit `budget.exceeded` di jalur `fail()` (D-I5).** Breach yang sudah diketahui runtime ikut ke akhir minimal, dan audit `budget.exceeded` tertulis di transaksi itu.
- **G7 Readiness turun pada penolakan nyata.**
  - Kegagalan `auth` (termasuk `billing_error`/`permission_error`) atau 404 dari provider dalam run mereset readiness ke `unknown` dengan reason baru `provider_rejected`, dan reset itu diaudit `provider.readiness_reset`.
  - Semua run berikutnya berhenti di gerbang (`provider_not_ready`) sampai smoke baru lulus.
- **G8 `pricing_version` di predikat.** Gerbang runtime menolak (`unknown`, reason `pricing_changed`) bila versi tarif di laporan readiness berbeda dari tabel tarif yang dipegang worker.
- **G9 Dashboard `agent_activity`.** Sepuluh run terbaru di project yang terlihat oleh pemanggil, dari snapshot yang sama dengan bagian dashboard lain. `agent_activity` keluar dari `meta.unavailable`.
- **G10 `RUNTIMES_AVAILABLE` jujur.** Teks alasan `runtime_unavailable` di UI menyatakan keadaan sebenarnya. Flag-nya sendiri tetap `False` sampai ada pemicu produksi (Keputusan #9).

## 3. Non-goals

- Job worker yang memanggil `build_agent_runtime`, bootstep registry di worker, pemetaan hasil run ke transisi task, dan resume task `interrupted`. Semuanya milik engine WP-3.2 (S non-goals, S #22, WBS WP-3.2).
- `GET /tasks/{id}/agent-runs` dan halaman detail run (WP-3.2). Tautan dashboard tetap ke task.
- Marker percobaan / reservasi budget untuk LOW-3 (Keputusan #7 menerimanya).
- Run fase `draft` tanpa lease (K6, milik WP-3.2).
- Mengubah kebijakan retry percobaan model atau klasifikasi galat selain pemetaan `auth`/404 ke reset readiness.

## 4. Anti-goals

Perubahan berikut dianggap gagal walaupun test-nya hijau:
- Recovery menutup run yang pekerjanya masih hidup. Contohnya predikat "semua `running` saat worker start" di deployment dengan dua worker.
- Recovery menulis status selain `failed/interrupted`, atau menghitung usage run yang dipulihkan sebagai lengkap.
- Handler tool dijalankan ulang, atau `tool_calls` ditutup sebagai `ok`.
- Reset readiness menimpa laporan smoke yang lebih baru dari percobaan yang gagal.
- Penulis kedua `agent_runs` muncul di luar modul yang diizinkan guard AST.

## 5. Batasan

- Penulis `agent_runs`: `app/services/agent_runtime.py` (guard `test_agent_run_writer_guard.py`). DATA_MODEL sudah meramalkan recovery sebagai penulis kedua.
- Penulis `tool_calls`: `app.tools.gateway` (konvensi di `app/models/tools.py`).
- Penulis ledger: `app/services/usage.py`.
- Kontrak import-linter "Layers": `app.workflow` tidak boleh mengimpor `app.services`.
- Runtime (`app/agents/runtime.py`) tidak mengimpor model atau DB. Semua efek lewat port, dan setiap perubahan protocol port perlu AG-13 🔒.
- Sweep harus aman dijalankan bersamaan oleh beberapa worker: `FOR UPDATE SKIP LOCKED` dan UPDATE bersyarat `status='running'`.
- Library baru: tidak ada.
- Fixture mirip secret di test dibangun lewat konkatenasi, misalnya `"-----BEGIN " + "RSA PRIVATE KEY-----"`, supaya tidak ada baris ter-commit yang cocok dengan rule gitleaks.
- Hindari `rf"…{x}…"` di modul target Semgrep yang punya method async di dalam class (tracker § WP-3.1f2c, "Sesudah merge PR #33").

## 6. Pendekatan

### 6.1 Pembagian kerja

- **Opsi 1, satu PR untuk semua:** satu review AG-13 besar, campuran backend inti dan layar.
- **Opsi 2, dua sub-WP (dipilih):**
  - **3.1f2b1** "integritas akhir run": G1–G6. Backend saja, menyentuh port runtime 🔒.
  - **3.1f2b2** "gerbang belajar dan tampilan": G7–G10. Backend gerbang, dashboard, dan teks frontend 🔒.
  - Keduanya independen. 3.1f2b1 lebih dulu karena memblokir pemanggil produksi dengan risiko terbesar.
- **Alasan:** pola yang sama sudah dipakai untuk 3.1d1/d2, 3.1e1/e2, dan 3.1f1/f2a/f2c. Review AG-13 yang fokus menemukan lebih banyak, dan setiap PR bisa di-merge sendiri.

### 6.2 Letak recovery run (K2)

| Opsi | Untung | Rugi |
|---|---|---|
| A. Di `app/workflow/recovery.py` seperti ARCHITECTURE §5.3, dalam transaksi task | Satu transaksi task + run | Melanggar "Layers" (workflow → services: total ledger, penulis tunggal), atau memindahkan penulis `agent_runs` ke workflow |
| **B. Modul `app/services/run_recovery.py`, dipanggil job `recovery_sweep` sesudah recovery task (dipilih)** | Layer utuh; memakai `incomplete_run_totals` dan gateway; penulis kedua yang sudah diramalkan DATA_MODEL | Penutupan task dan run berada di dua transaksi |

Dua transaksi tetap benar, karena predikat run tidak bergantung pada status task. Predikatnya adalah "lease task tidak hidup", dan itu sudah berlaku begitu lease kedaluwarsa, sebelum task dipulihkan. Kalau sweep run gagal, sweep berikutnya mengulangnya. Recovery task tidak berubah.

### 6.3 LOW-3 (percobaan yang mati bersama worker)

| Opsi | Biaya | Menutup |
|---|---|---|
| A. Marker sebelum setiap percobaan → baris `unavailable` oleh recovery | Migrasi, satu tulis DB per percobaan, port runtime baru 🔒, melanggar DM "satu baris per percobaan yang sampai ke provider" dan "tidak pernah diubah" | Kurang hitung ≤ 1 percobaan per crash |
| **B. Diterima secara tertulis (dipilih), dengan pemicu tinjau ulang** | Nol | Tidak menutup apa pun. Batasnya tetap ≤ 1 percobaan per crash per task, dan setiap crash butuh tindakan manusia untuk melanjutkan task |

### 6.4 N5/D-I6 (ack `start` hilang)

| Opsi | Catatan |
|---|---|
| Cegah saja (id dari runtime + `start` idempoten) | Tidak menyembuhkan crash |
| Sembuhkan saja (sweep basi) | Baris kedua tetap tercipta; baris yatim hidup sampai tenggat + batas |
| **Keduanya (dipilih)** | Pencegahannya murah, dan sweep basi tetap perlu untuk crash dan hang |

## 7. Keputusan Lead 3.1f2b

1. **Dua sub-WP** (§6.1). 3.1f2b1 = G1–G6, 3.1f2b2 = G7–G10. Masing-masing punya plan, PR, dan review AG-13 sendiri.
2. **Tidak ada pemanggil produksi di WP ini (K1).** S #48 ("kontrak ini untuk worker 3.1f2b") dibaca sebagai "kontrak yang dibangun 3.1f2b untuk worker". Job pemanggil milik WP-3.2, sesuai non-goals S, S #22, dan WBS. 3.1f2b tetap "blocking sebelum pemanggil produksi" (T).
3. **Recovery run di `app/services/run_recovery.py`** (§6.2, K2). Fungsinya dipanggil job `recovery_sweep` sesudah `recover_expired` dan diekspos lewat CLI `recover`.
   - `RecoveryResult` job mendapat hitungan run dan tool call.
   - Bila salah satu bagian gagal, job tetap menaikkan `RecoveryIncomplete`.
   - Guard penulis `agent_runs` diperluas ke modul ini. ARCHITECTURE §5.3 dan DATA_MODEL diperbarui.
4. **Predikat run yang dipulihkan.** `agent_runs.status='running'` dan salah satu dari:
   - **(a)** lease task tidak hidup: `tasks.lease_expires_at IS NULL OR < clock_timestamp()`. Ini mencakup task yang sudah dipulihkan atau sudah berakhir;
   - **(b)** run basi (Keputusan #5).

   Baris dikunci `FOR UPDATE SKIP LOCKED`, lalu di-UPDATE bersyarat `status='running'`. Bila runtime menang balapan, recovery melewatinya. Bila recovery menang, `finish` runtime mendapat `RunAlreadyFinished` (perilaku 3.1f2a #48).
5. **Definisi run basi (K5):** `started_at + timeout_seconds + RUN_CLOSE_BOUND < clock_timestamp()`.
   - `timeout_seconds` dibaca dari `agent_profiles.limits` agent run itu.
   - `RUN_CLOSE_BOUND` = 60 dtk. Nilai ini di atas batas penutupan ARCHITECTURE §5.3 (grace tool 10 dtk, penutupan 2 × 5 dtk, akhir minimal 5 dtk, total ±25 dtk) ditambah margin jam.
   - Profil yang hilang atau tanpa `timeout_seconds` memakai batas atas registry, yaitu 3600 dtk (`AgentLimits.timeout_seconds`, `le=3600`). Batas ini deterministik dan tidak bergantung pada profil lain (penajaman saat plan).
   - Tidak ada migrasi. Kolom liveness (`deadline_at`/`worker_id`) ditolak, karena tenggat run sudah dapat diturunkan dari profil dan hanya dipakai sebagai jaring pengaman.
   - Risiko yang diterima: profil yang `timeout_seconds`-nya diturunkan di tengah run bisa menutup run itu lebih awal. `finish` runtime lalu menerima `RunAlreadyFinished`, dan akhir yang tercatat tetap `interrupted`, bukan hasil palsu [Kemungkinan Besar, jarang].
6. **Akhir run yang dipulihkan.**
   - Status dan waktu:
     - status `failed` / `error_code=interrupted`;
     - `finished_at` = jam DB;
     - `duration_ms` dari `started_at`.
   - Usage:
     - token dan biaya dari `incomplete_run_totals`;
     - `cost_status`: `partial` bila ada baris ledger, `unavailable` bila tidak ada.
   - Kolom lain:
     - `error` = teks tetap dari `ERROR_TEXTS["interrupted"]`;
     - `output` tetap NULL.
   - `agent.run_finished` dikirim di transaksi yang sama (DM, API §5.1). Run tidak diaudit sendiri: SEC §214 tidak mewajibkannya, dan task-nya sudah diaudit `task.status_changed`.
7. **LOW-3 diterima** (§6.3; T mengizinkan "keputusan Lead tertulis yang menerimanya"). Kurang hitung ≤ 1 percobaan (input bound + `max_tokens`) per crash worker per task. Setiap crash membuat task `interrupted`, dan di v1 task itu butuh tindakan manusia untuk lanjut, sehingga kurang hitungnya tidak dapat berulang tanpa manusia. D2-I4 (cancel worker saat ledger menulis) masuk kelas yang sama.
   - **Pemicu tinjau ulang:** WP mana pun yang menambah resume atau retry otomatis task `interrupted` wajib membuka lagi opsi marker/reservasi (§6.3 A).
   - SECURITY_MODEL §13 diperbarui ke "diterima (3.1f2b #7)".
8. **Tool call yang dipulihkan (K4)** memakai `status=error`, `error_code=outcome_unknown`, seperti replay. "(`interrupted`)" di T berlaku untuk run, bukan tool call. Penulisnya fungsi baru di `app/tools/gateway.py`, yang menjaga penulis tunggal `tool_calls`. Audit `tool.executed` untuk R1+ dan event `tool.call_finished` meniru `_replay`.
   - **Unit recovery adalah task, dalam satu transaksi** (builder check, 15 Nov). Untuk setiap task kandidat, baris `agent_runs` dan `tool_calls` miliknya yang `running` dan memenuhi predikat dikunci (`FOR UPDATE SKIP LOCKED`) lalu ditutup bersama. Tidak ada keadaan run tertutup yang meninggalkan tool call yang tak terlihat lagi oleh sweep berikutnya.
   - **Predikat tool call:** `tool_calls.status='running'` dan salah satu dari:
     - (a) lease task tidak hidup (Keputusan #4a). Ini termasuk tool call tanpa run (`agent_run_id` NULL, pemanggil engine WP-3.2);
     - (b) run-nya ikut dipulihkan di transaksi ini;
     - (c) run-nya sudah terminal.
   - Kasus (c) menutup sisa jalur runtime yang sudah ada. Saat tenggat atau cancel, `_settle_cancelled`/`_mark_record_failed` bisa gagal menulis. Baris tool call lalu tetap `running` sementara runtime menutup run-nya, dan replay yang diandalkan docstring `_settle_cancelled` tidak pernah datang, karena kunci idempotensi memuat `agent_run_id`. Docstring itu diluruskan.
   - Tool call milik run yang sudah terminal tidak mungkin masih sah berjalan, sebab runtime menunggu atau membatalkan tool sebelum menulis akhir run. Karena itu (c) berlaku walaupun lease task masih hidup.
9. **`RUNTIMES_AVAILABLE["agent_runtime"]` tetap `False` (K9).**
   - "`ready` adalah klaim bahwa agent dapat jalan sekarang" (`readiness.py`), dan tanpa pemicu produksi klaim itu palsu.
   - WP-3.2 membaliknya bersama pemicu run.
   - Teks UI `runtime_unavailable` diganti dari "runtime belum dibangun" menjadi pernyataan yang benar, yaitu belum ada mesin yang menjalankan agent (kunci i18n id/en).
   - Fakta pendukung: dengan flag dibalik pun, 13 agent llm/profile tetap `not_ready (tools_unavailable)` [Pasti, discovery].
10. **N5/D-I6: cegah dan sembuhkan** (§6.4).
    - `AgentRunRequest` mendapat `agent_run_id: UUID` (default `uuid4`), sehingga pemanggil memegang id run sebelum `run()` dimulai. `RunStart` membawa id itu ke port. Alasannya (builder check, 15 Nov): pada galat tak terduga dan `CancelledError`, `_wrap_up_after_error` me-raise ulang galat asli, bukan `AgentRunUnfinished`. Id dari pemanggil berlaku di semua jalur keluar tanpa mengubah tipe galat.
    - `RunStore.start` menjadi idempoten: `INSERT … ON CONFLICT (id) DO NOTHING`, lalu memeriksa bahwa baris yang ada milik task/agent yang sama. Bila tidak sama, galat.
    - Penajaman final review (ruling R5, R10; AG-13 MEDIUM-1, delta MEDIUM-2) [Pasti]: port-nya `RunStore.start(run, *, retry: bool)`. Start **pertama** sebuah request (`retry=False`) yang INSERT-nya tidak membuat baris ditolak `AgentRunIdConflict`, apa pun task, agent, atau status baris yang ada; tidak ada yang ditulis. Hanya start ulang sesudah ack hilang (`retry=True`) yang idempoten: baris `running` milik task dan agent yang sama dibiarkan, baris yang sudah berakhir ditolak `RunAlreadyFinished`, dan baris task/agent lain ditolak `AgentRunIdConflict`. Runtime mengirim `retry=True` hanya bila start sebelumnya sudah terkirim. Akibatnya request ganda atau id yang terpakai tidak pernah menjalankan model/tool di bawah baris run lain; start pertama tidak pernah mengambil alih run yang hidup; dan run yang sudah berakhir tidak pernah dibuka kembali. Residu yang diterima (AG-13 delta-2 LOW-1) [Pasti]: start pertama request A mati sebelum INSERT-nya (mis. koneksi putus), request ganda B dengan `agent_run_id` yang sama meng-commit baris `running`-nya di sela itu, lalu start ulang A di jalur penutupan (`retry=True`) menganggap baris B miliknya karena task dan agent-nya sama, sehingga `finish` A mengakhiri run B yang masih hidup. Kontrolnya id baru per `run()` (ARCHITECTURE §6.1, tidak pernah dipakai ulang); pemicu tinjau ulangnya WP-3.2 (SECURITY_MODEL §13). Melanjutkan di bawah id yang sama (WP-3.2) butuh jalur penulis "reopen" tersendiri yang ditinjau AG-13.
    - `_write_end` yang tidak menerima ack `start` memakai id yang sudah ada. Bila belum ada baris, `start` diulang sekali secara idempoten lalu `finish`.
    - Perubahan protocol port ini diperiksa AG-13.
11. **`AgentRunUnfinished` (#48, G5).**
    - Exception membawa `agent_run_id: UUID` (= `request.agent_run_id`, #10) dan `task_id`.
    - `app/services/agent_runtime.py` mendapat `read_run_outcome(session, agent_run_id) -> RunOutcome`: `finished(status, error_code)`, `running` ("milik recovery; jangan mengarang"), atau `missing` (run ditolak sebelum baris dibuat, atau `start` tidak pernah ter-commit).
    - Penajaman final review (ruling R6, G2; silent L1, AG-13 delta LOW-2) [Pasti]: signature-nya `read_run_outcome(session, agent_run_id, *, task_id, agent_id)`, sehingga baris milik task atau agent lain terbaca `missing`; dan `approval_required` terbaca `paused` (menunggu keputusan manusia, belum berakhir), bukan `finished`. Pemanggil memakai `agent_run_id` baru untuk setiap pemanggilan `run()`, tidak pernah dipakai ulang untuk retry atau redelivery job.
    - ARCHITECTURE §6.1 menulis kontrak pemanggil untuk **setiap** jalur keluar `run()` selain `RunResult`, baik `AgentRunUnfinished`, galat tak terduga, maupun `CancelledError`. Pemanggil tidak menulis status task dari exception, tetapi membaca baris DB lewat `request.agent_run_id`.
12. **D-I5: `fail()` membawa breach (G6).**
    - Port `RunStore.fail(agent_run_id, *, task_id, agent_id, breach: BudgetBreach | None)`. Runtime meneruskan breach yang sudah diketahui saat `finish` gagal. `task_id` dan `agent_id` (penajaman final review, ruling R6) membatasi UPDATE ke baris run itu sendiri, sehingga id asing tidak pernah ditutup.
    - Status akhir minimal tetap `failed internal_error` (S #40). Breach tidak mengubah status, tetapi audit `budget.exceeded` (SEC §214) dan event `usage.budget_exceeded` (API §5.1) ditulis di transaksi `fail()` yang sama.
    - Bila `fail()` juga gagal, baris tetap `running` dan recovery menutupnya sebagai `interrupted` tanpa audit breach. Ini diterima, karena breach hanya ada di memori proses yang sudah gagal menulis dua kali.
    - **Dua jalur lain yang juga kehilangan audit breach, diterima di final review (AG-13 INFO-2, silent L6, M4)** [Pasti]:
      - recovery menutup run lebih dulu (lease mati atau run basi) sebelum `finish`/`fail` runtime mendarat. `finish` mendapat `RunAlreadyFinished` (runtime lalu tidak memanggil `fail`), atau `fail` yang datang sesudahnya tidak mengenai baris apa pun; akhir yang tercatat adalah `interrupted` tanpa audit maupun event breach;
      - audit atau event breach di `fail()` gagal ditulis. Keduanya ditulis dalam savepoint (ruling R7): yang di-rollback hanya savepoint itu, kegagalannya di-log `budget_audit_unrecorded` (id run, id task, jenis breach, tipe galat), dan akhir minimal tetap di-commit, juga bila kegagalannya terjadi saat flush (G3).
      - Alasan penerimaan sama: breach hanya ada di memori proses yang penulisannya sudah kalah atau gagal, dan status akhir tidak pernah palsu. Residu ini tercatat di SECURITY_MODEL §13.
    - K7 dicatat: T menulis D-I5 tertutup, sedangkan AG-13 @082f104 menyebutnya SEBAGIAN.
13. **Reset readiness pada penolakan nyata (G7, K10).**
    - **Port.** `ProviderGate` mendapat `reject(cause, *, checked_at)` dengan `cause ∈ {"auth", "not_found"}`.
    - **Kapan runtime memanggilnya.** Saat percobaan berakhir dengan `LLMError` kind `auth`, atau dengan `status_code == 404` / `vendor_type == "not_found_error"`.
    - **Implementasi `DbProviderGate`, dalam transaksi pendek sendiri:**
      - `readiness_status='unknown'`;
      - `readiness_report` diberi tanda `invalidated = {cause, at}`;
      - audit `provider.readiness_reset` (actor system/worker, cause; tanpa isi galat).
    - **Compare-and-set.** UPDATE hanya bila `readiness_checked_at` masih sama dengan saat gerbang diperiksa, sehingga laporan smoke yang lebih baru tidak tertimpa.
    - **Best-effort.** Kegagalan reset di-log dan tidak mengubah akhir run. Run berikutnya yang ditolak akan mencoba lagi.
    - **Reason verdict.** `provider_ready` mengembalikan reason baru `provider_rejected` untuk status `unknown` dengan tanda `invalidated`.
    - **Mode scripted** diperlakukan sama, supaya bisa diuji tanpa pengecualian.
    - **`record_report` berikutnya** mengganti seluruh laporan, sehingga tandanya hilang dengan sendirinya.
14. **`pricing_version` di predikat (G8, K8).** `WorkerCredentials` mendapat `pricing_version`, yaitu versi tabel yang dimuat saat worker start. `provider_ready(held=…)` mengembalikan `unknown`/`pricing_changed` bila `row.pricing_version` berbeda dari versi itu.
    - Verdict di api tidak berubah, karena api tidak memuat tarif di v1 (CONFIGURATION).
    - Konsekuensinya diterima: file tarif yang berubah tanpa restart worker menahan run sampai worker di-restart. Ini sama dengan perilaku rotasi key.
15. **`agent_activity` (G9).**
    - Isinya maksimal 10 run terbaru (`started_at` menurun, termasuk yang `running`) di project yang terlihat (`visible_projects_filter`). Query diambil dari `services/agents.py` (`RunSummary`) dan dijalankan di snapshot REPEATABLE READ yang sama dengan bagian dashboard lain.
    - `agent_name` diambil dari `agent_profiles.name`.
