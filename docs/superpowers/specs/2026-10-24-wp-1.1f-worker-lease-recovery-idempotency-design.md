## Intent

Orchestrator (WP-3.x) membutuhkan tiga hal deterministik yang tidak boleh ia tulis ulang: proses worker yang aman, lease untuk menjamin satu eksekusi per task (NFR-05), dan sweep yang memulihkan task yatim. API butuh `Idempotency-Key` sebelum endpoint mutasi pertama di luar auth muncul (WP-2.1).

**Goals**

1. **Aplikasi Celery** (`app/worker/celery_app.py`):
   - broker Redis;
   - hanya JSON (tanpa pickle);
   - `acks_late` dan `reject_on_worker_lost`;
   - prefetch 1;
   - `task_always_eager` mengikuti setting;
   - beat menjalankan `recovery_sweep` tiap 30 dtk;
   - sweep juga dijalankan saat worker siap.
2. **`workflow/lease.py`**:
   - `claim_lease(db, task_id, worker_id)` sesuai SQL §5.3, termasuk batas `MAX_ACTIVE_TASKS` saat claim;
   - `renew_lease`;
   - `release_lease`.
3. **`workflow/recovery.py`**: `recover_expired(sessions, bus, audit)`. Task `running|validating` yang lease-nya kedaluwarsa dipindah ke `interrupted`, atau ke `cancelled` bila `cancel_requested`. Lease dikosongkan, dan perpindahan dilakukan lewat `transition` (audit + event).
4. **CLI** `python -m app.cli recover` (RUNBOOK).
5. **Middleware `Idempotency-Key`** untuk POST/PUT/PATCH/DELETE terautentikasi di luar `/auth/*`:
   - respons pertama (status < 500) disimpan 24 jam di Redis, lalu di-replay;
   - kunci yang sama dengan body berbeda → 409;
   - kunci yang sama saat request pertama masih berjalan → 409.

**Non-goals**
- `run_task` / orchestrator / heartbeat loop (WP-3.x).
- Tabel `agent_runs` beserta langkah "agent_run → failed" di recovery. Langkah ini ditambahkan saat tabelnya ada (WP-3.x).
- Retensi harian (WP pemilik retensi).
- `Envelope[T]` / `response_model` (ditunda ke WP-1.2).

**Anti-goals**
- **Dua worker sama-sama memegang lease task yang sama.**
- **Sweep memindahkan task yang lease-nya masih hidup**, atau gagal diam-diam.
- **Replay Idempotency-Key bocor antar-user atau antar-sesi**, atau me-replay `Set-Cookie`.
- **Pickle** di jalur Celery.

## Approaches

| | Pendekatan | Trade-off | Status |
|---|---|---|---|
| A | Lease di kolom `tasks` dengan UPDATE bersyarat (§5.3); sweep lewat `transition` | Sesuai kontrak dan atomik. Sweep berbiaya satu UPDATE per task yatim. | **dipilih** |
| B | Lock Redis (Redlock) | Dua sumber kebenaran; melanggar CLAUDE.md #4 | ditolak |
| C | Idempotency di tabel PostgreSQL | Kontrak menyebut Redis 24 jam | ditolak |

Idempotency berupa **middleware ASGI**. Dependency per-route ditolak dengan alasan yang sama seperti CSRF: route yang lupa memasangnya = celah.

- **`jobs.recovery_sweep`** menjalankan `asyncio.run(recover_expired(...))` dengan engine, Redis, dan redaktor yang dibuat per proses dari `Settings`.
- **Sinyal `worker_ready`** menjalankan sweep sekali saat worker siap.

### Lease

**`claim_lease`**:

```
UPDATE tasks SET lease_owner=:w, lease_expires_at=now()+60s
WHERE id=:id AND (lease_expires_at IS NULL OR lease_expires_at < now())
  AND (SELECT count(*) FROM tasks WHERE status IN ('running','validating') AND lease_expires_at > now()) < :max_active
RETURNING id
```

- Mengembalikan `bool`.
- Jalannya diserialisasi dengan `pg_advisory_xact_lock`, supaya batas `MAX_ACTIVE_TASKS` tidak bisa dilewati oleh dua claim yang bersamaan.

**`renew_lease(db, task_id, worker_id)`** hanya memperpanjang lease bila `lease_owner = worker_id` dan lease belum kedaluwarsa. Hasilnya `False` berarti lease sudah hilang, dan worker wajib berhenti.

**`release_lease`** hanya melepas lease bila pemiliknya cocok.

Konstanta: `LEASE_SECONDS = 60`, `HEARTBEAT_SECONDS = 20` (§5.3).

### Recovery

1. Pilih task `status IN (running, validating) AND lease_expires_at < now()` dengan `FOR UPDATE SKIP LOCKED`. Dengan begitu dua sweep tidak memproses task yang sama.
2. Untuk setiap task, jalankan `transition(... interrupted | cancelled, reason="lease_expired" | "cancel_requested", actor=system:recovery)`. Lease dikosongkan dalam transaksi yang sama.
3. Commit per task, lalu `publish_pending`.
4. Kembalikan jumlah task yang dipulihkan.

Kegagalan satu task di-log dengan `task_id` dan `error_type`, lalu sweep lanjut ke task berikutnya. Kegagalan itu juga dihitung dan dilaporkan di nilai kembali.

### Idempotency-Key (middleware)

- **Kapan berlaku:** metode mutasi, path di luar `/api/v1/auth/`, ada cookie `kk_session`, dan ada header `Idempotency-Key`. Kondisi lain diteruskan apa adanya.
- **Format kunci:** `^[A-Za-z0-9_.:-]{1,128}$`. Selain itu → 400 `BAD_REQUEST`.
- **Scope:** `sha256(session_token)` + metode + path + kunci. Respons milik sesi lain tidak pernah di-replay.
- **Request pertama:** `SET kk:idem:<scope-hash> {"state":"pending","body":sha256(body)} NX EX 86400`, lalu request diteruskan.
  - Respons status < 500 dengan body ≤ 1 MiB → simpan `{"state":"done","body_hash","status","content_type","body"}`.
  - Respons 5xx atau body terlalu besar → kunci dihapus, supaya klien bisa mencoba lagi.
  - `Set-Cookie` tidak pernah disimpan.
- **Request berikutnya dengan kunci yang sama:**
  - masih `pending` → 409 `CONFLICT` ("request with this Idempotency-Key is in progress");
  - body hash berbeda → 409 `CONFLICT` ("Idempotency-Key reused with a different body");
  - selain itu → replay status, content-type, dan body, plus header `Idempotent-Replay: true`. `X-Request-ID` tetap milik request baru.
- **Redis tidak tersedia:** 503 `DEPENDENCY_UNAVAILABLE` (fail closed). Mengeksekusi ulang mutasi yang diminta idempoten lebih berbahaya daripada menolaknya.
- **Urutan:** middleware dipasang di dalam CSRF. Request yang gagal CSRF tidak pernah menyentuh penyimpanan idempotensi.
