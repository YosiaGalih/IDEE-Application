## Intent dan perubahan cakupan

Rencana lanjutan (U10) dan WBS WP-1.4 menyebut layar login, dashboard, projects, agents, dan approvals. Backend di repo saat ini hanya punya route `auth` dan `health` [Pasti, `backend/app/api/routes/`]. Endpoint `/dashboard`, `/projects`, `/agents`, dan `/approvals` belum ada; masing-masing milik WP-2.1, WP-3.1, dan WP-INT-03. Layar untuk endpoint itu hanya bisa dibangun di atas mock MSW. Mock itu tidak bisa diverifikasi ke backend nyata, dan berisiko dikerjakan ulang ketika kontrak berubah di WP tersebut.

**Keputusan Lead (konflik #63):**
- 1.4b mencakup semua yang API-nya sudah ada: login, logout, lupa dan reset password, ganti password, penjaga sesi, dan menu pengguna.
- Layar dashboard, projects, agents, dan approvals dikerjakan bersama WP backend masing-masing, sehingga satu PR berisi API dan layarnya.

**Goals**
1. **`/login`:**
   - email, password, "ingat saya";
   - validasi lokal (Zod) sebelum kirim;
   - 401 tampil sebagai satu pesan generik (tidak membedakan email salah, password salah, atau akun terkunci);
   - 429 menampilkan waktu tunggu dari `Retry-After`;
   - 503 dan jaringan putus menampilkan state yang sesuai;
   - tombol nonaktif saat mengirim.
2. Setelah login, pengguna diarahkan ke `?next=` bila nilainya path internal yang aman, selain itu ke `/`. Tidak ada open redirect.
3. **Penjaga sesi:** semua route di dalam layout aplikasi memanggil `useMe`.
   - Saat memuat, tampil state loading.
   - 401 mengarahkan ke `/login?next=<path sekarang>`.
   - Error lain tampil lewat `StateView` dengan aksi coba lagi.
   - Halaman publik (`/login`, `/forgot-password`, `/reset-password/:token`) tidak dijaga, dan handler 401 global tidak memantulkannya.
4. **Menu pengguna** di top bar: nama tampilan, ganti password, keluar. Keluar ke `/login` (cache dikosongkan) hanya setelah sesi berakhir: sukses, atau 401 (sesi sudah tidak ada). Kegagalan lain (5xx, `CSRF_FAILED`, jaringan) membuat pengguna tetap di aplikasi dengan pesan "gagal keluar, sesi masih aktif" dan tombol yang sama untuk mencoba lagi; cache tetap. *Diubah dari rancangan awal ("ke /login walau gagal") atas review AG-13, frontend, dan silent-failure: form login ketika sesi masih hidup tampak seperti sudah keluar di komputer bersama.*
5. **`/forgot-password`:** setelah 200 selalu menampilkan pesan generik yang sama, terdaftar atau tidak (tidak ada enumerasi email). Karena email baru ada di P1 (konflik #64), pesannya tidak menjanjikan pengiriman: "permintaan diterima; versi ini belum mengirim email; minta operator instalasi mengatur ulang kata sandi" (nada info, bukan sukses; fokus pindah ke pesan). 429 ditampilkan sebagai batas percobaan beserta waktu tunggunya: batasnya per IP (`kk:rl:forgot:{ip}`), jadi tidak membocorkan apa pun, sedangkan "sudah dikirim" pada 429 adalah klaim palsu.
6. **`/reset-password/:token?`** (satu route, sehingga state halaman bertahan saat URL diganti):
   - token dibaca ke state, lalu URL diganti menjadi `/reset-password` (`navigate(..., { replace: true })`) agar token tidak tersimpan di riwayat sesi tab. Muat ulang setelah itu menampilkan "buka lagi tautan reset". Risiko sisa yang diterima: riwayat global browser dan saran address bar tetap menyimpan URL awal (token sekali pakai, 30 menit, gugur saat ada permintaan baru);
   - log dan Referer (review AG-13): nginx `web` mencatat path `/reset-password/*` sebagai `[redacted]` dan tidak mencatat Referer; Caddy memasang `Referrer-Policy: no-referrer` untuk `/reset-password*` (di tempat lain tetap `same-origin` sesuai DEPLOYMENT/SECURITY_MODEL). Memindahkan token ke fragment (`#token`) adalah syarat AG-13 sebelum jalur pengiriman tautan mana pun (email atau admin/CLI) di-merge;
   - password baru dan konfirmasi divalidasi lokal (12–1024 karakter dihitung per code point seperti `len` Python, sama persis);
   - 400 tampil sebagai "tautan tidak valid atau kedaluwarsa";
   - setelah sukses, pengguna diarahkan ke `/login` dengan pesan.
7. **Ganti password:** dialog dari menu pengguna (password lama, password baru, konfirmasi).
   - 403 = password lama salah;
   - 409 = password berubah di tempat lain, pengguna diminta masuk ulang;
   - sukses berarti sesi lain dicabut oleh server (backend `change_password`).

**Anti-goals**
- Pesan yang membedakan "email tidak terdaftar" dari "password salah".
- `next` yang mengarah ke origin lain, ke `//host`, atau ke `javascript:`.
- Token reset tertinggal di URL atau riwayat.
- Password di log, state global, atau storage.

## Keputusan

| Topik | Keputusan | Alasan |
|---|---|---|
| Form | `react-hook-form` 7.89.0 (26 Sep, lolos batas umur) + resolver Zod lokal (`src/lib/zodResolver.ts`, ±15 baris) | Kontrak menyebut React Hook Form + Zod. `@hookform/resolvers` membawa ~25 peer opsional, dan graf peer seperti itu yang membuat `npm ci` npm 10 menolak lockfile di WP-1.4a |
| Aksesibilitas | `eslint-plugin-jsx-a11y` 6.10.2 (rekomendasi, level error) | Tertunda dari review WP-1.4a; mendukung ESLint 9 |
| Kunci i18n bertipe | `CustomTypeOptions` i18next dari `id.json` | Tertunda dari review WP-1.4a; kunci salah ketik menjadi error typecheck |
| `next` | Hanya path yang diawali satu `/`, tanpa `//`, `\`, karakter kontrol, atau skema; bukan halaman publik auth. Diurai dengan `new URL(next, origin)`: origin harus sama, lalu diambil `pathname + search + hash` | SECURITY_MODEL: open redirect |
| `Retry-After` | `ApiError.retryAfterSeconds` diisi dari header 429 | API_CONTRACTS §1 |
| Penjaga | Komponen `RequireSession` di elemen layout, bukan loader router | Layout sudah ada; status `useMe` (loading/401/error) dipetakan ke `StateView` |
| Handler 401 global | Dilewati untuk halaman publik dan untuk query/mutasi ber-`meta` `HANDLES_UNAUTHENTICATED` (`/auth/me` milik penjaga, mutasi login); navigasi `replace` ke `/login?next=` | Review WP-1.4a: `onUnauthenticated` harus sadar route publik |
| Aturan field | Email: berisi `@` dan ≤ 320 karakter, sama dengan backend (`services/users.py`); bukan `z.email()`, yang menolak `admin@localhost`. Password: dihitung per code point | Validasi lokal tidak boleh lebih ketat dari server: owner yang sah tidak bisa masuk |
| Cache saat masuk | Halaman login membuang semua query saat dibuka dan setelah login sukses; tidak ada "alihkan bila sudah masuk" | Data sesi lama tidak tampil lewat Back, dan pengguna lain di tab yang sama tidak melihatnya. Pengalihan dari `/auth/me` yang ter-cache dan basi bisa berputar (login → app → 401 → login) |
| Path auth | `AUTH_PATHS` di `src/lib/safeNext.ts` dipakai route, link, dan `safeNext` | Satu sumber; lint i18n tetap tanpa pengecualian atribut `to` |
| `safeNext` | Setelah diurai, path yang diawali `//` ditolak; halaman publik dikenali setelah decode dan huruf kecil (`/LOGIN`, `/%6Cogin`) | `"/..//evil.test"` lolos pemeriksaan awal lalu menjadi `//evil.test` (ditemukan saat test merah); router mencocokkan route tanpa membedakan huruf dan pada path ter-decode (review) |
| Error per kode | Teks khusus layar dipilih dari `error.code`, bukan status: 403 bisa `FORBIDDEN` atau `CSRF_FAILED`; 400 reset hanya `BAD_REQUEST` | Review: `CSRF_FAILED` tampil sebagai "kata sandi salah" |
| Hasil tak pasti | Reset dan ganti password tanpa jawaban (jaringan, timeout, 2xx bukan envelope) memberi tahu bahwa kata sandi mungkin sudah berubah | Review: ulangan setelah sukses yang jawabannya hilang memberi 400/403 menyesatkan dan memakai jatah lockout |
| Bukti sesi | Login sukses diikuti `/auth/me`; 401 di situ → "browser tidak menyimpan sesi" | Review: cookie diblokir atau `Secure` di http memantulkan pengguna ke form kosong tanpa kata |
| Password di memori | `gcTime: 0` pada mutasi login, reset, dan ganti password | Review AG-13: variabel mutasi (password) tertinggal 5 menit di cache global |
| Pemberitahuan login | `passwordReset` dan `sessionExpired` lewat state navigasi, dibaca sekali lalu dihapus dari entri riwayat. `sessionExpired` dari handler 401 global dan dari `/auth/me` ber-kode `SESSION_EXPIRED` (kunjungan pertama tidak) | Review: pengguna yang sesinya habis melihat halaman login tanpa penjelasan |

## Konflik baru

- **#63.** WBS WP-1.4 dan rencana lanjutan U10 memasukkan layar dashboard, projects, agents, dan approvals ke WP-1.4. API-nya belum ada di backend repo. Keputusan Lead: layar dibangun bersama WP backend masing-masing (WP-2.1, WP-3.1, WP-INT-03). WP-1.4b berisi auth, sesi, dan menu pengguna.
- **#64.** PRD/API_CONTRACTS memuat alur lupa password lewat email, tetapi pengiriman email dijadwalkan di P1: backend hanya mencetak tautan reset ke log pada `APP_ENV=development`, dan produksi tidak mengirim apa pun [Pasti, `backend/app/api/routes/auth.py` `forgot_password`]. Layar 1.4b tidak mengklaim "terkirim"; pesannya menyuruh menghubungi admin bila tautan tidak sampai. Sampai email ada, reset di produksi hanya bisa lewat admin. Perlu keputusan PO: majukan email ke P0, atau sediakan reset oleh admin/CLI.
