# WP-3.1e — Pengaturan provider, readiness gate, kill switch (desain)

Induk: `docs/superpowers/specs/2026-11-05-wp-3.1-agentic-core-design.md` (baris 3.1e; konflik #7 dan #13 "diputuskan di 3.1e"). Discovery: 8 Nov 2026 (FR-045 bagian, FR-128, FR-130, FR-135, FR-158; ADR-004, ADR-011, ADR-032, ADR-053; API §9, §11 #8, §11.3; DATA_MODEL `provider_configs`). 🔒 AG-13.

## Intent

Sebelum agent mana pun memanggil Claude, platform harus bisa membuktikan bahwa provider siap (ADR-032) dan admin harus bisa menghentikan panggilan per project (FR-158). WP ini membangun bukti itu, tempat menyimpannya, dan pintu untuk melihat/menjalankannya. Penegakan saat runtime (menolak panggilan LLM, `PROVIDER_DISABLED`) milik 3.1f; 3.1e memberinya predikat yang sudah teruji.

## Pembagian

- **3.1e1 (backend):** tabel `provider_configs`, runner readiness, `claude-smoke` + `make smoke`, job smoke di worker, endpoint `/settings/providers*`, predikat untuk 3.1f, kunci `provider_calls_enabled`, readiness provider di `/agents`.
- **3.1e2 (layar):** `/settings/providers`, landing `/settings`, sidebar menurut izin, pernyataan data flow. Butuh endpoint 3.1e1.

## Goals 3.1e1

1. **`provider_configs`** (migrasi 0009, model `ProviderConfig`): kolom DATA_MODEL ditambah `llm_provider_mode` (§11 #8), `secret_status` (`configured`/`missing`/`unknown`), `secret_hint` (mis. `sk-ant-…a1b2`), `secret_fingerprint` (16 hex pertama SHA-256 key; tidak dapat dibalik), `secret_checked_at`. Satu baris per provider; dibuat bila belum ada (idempoten) oleh worker atau API.
2. **Runner readiness** (`app/llm/readiness.py`, murni lewat port `LLMProvider`): 9 check bernama tetap, delapan dari §11 #8 (`api_key_valid`, `model_accessible`, `messages_ok`, `streaming_ok`, `usage_reported`, `tool_use_roundtrip`, `timeout_cancel_handled`, `secret_not_in_logs`) ditambah `pricing_verified` (syarat warisan AG-13 3.1a). Setiap check `passed`/`failed`/`skipped` dengan `detail` yang sudah diredaksi; satu check gagal tidak menghentikan yang lain kecuali dependensinya gagal (lalu `skipped`). `ready` = semua `passed` (atau `skipped` hanya untuk `pricing_verified` di luar produksi).
3. **`claude-smoke`** (`python -m app.cli claude-smoke`, berjalan di container `worker`) dan `make smoke` (RUNBOOK §4): menjalankan runner, menulis baris, mencetak laporan teredaksi, exit 0 hanya bila `ready`.
4. **Job smoke di worker** (`app.worker.platform_jobs.provider_smoke`): sama dengan CLI, dipicu API. Satu smoke per provider pada satu waktu (lock Redis); key tidak pernah keluar dari worker.
5. **Endpoint** (izin global `settings:providers`, owner/admin):
   - `GET /settings/providers`: `[{id, provider, base_url, model_policy, effective_models, secret_status, secret_hint, secret_checked_at, enabled, pricing_version, llm_provider_mode, readiness_status, readiness_checked_at}]`.
   - `PATCH /settings/providers/{id}` `{model_policy?, enabled?}`: model ID divalidasi; mengubah `model_policy` mengembalikan readiness ke `unknown` (ADR-032); `base_url` ditolak (Keputusan #6).
   - `GET /settings/providers/{id}/readiness` (§11.3): laporan terakhir.
   - `POST /settings/providers/{id}/smoke-test`: mengirim job lalu menunggu ≤ `SMOKE_WAIT_S` sampai laporan baru tercatat; menjawab bentuk §11 #8. Lewat batas: `202 {job_id}` dan laporan kemudian lewat GET readiness. Smoke yang masih berjalan: `409`.
   - Setiap perubahan dan permintaan smoke diaudit (`provider.updated`, `provider.smoke_requested`), dan setiap laporan yang ditulis worker (`provider.readiness_recorded`).
6. **Predikat untuk 3.1f** (`app/services/provider_readiness.py`): `provider_ready(...)` (status `passed`, mode sama dengan `LLM_PROVIDER` sekarang, `enabled`, dan di worker fingerprint key sama dengan yang tercatat; key yang dirotasi → status kembali `unknown`), `provider_calls_allowed(project)` (FR-158), `resolve_model(alias)` (Keputusan #5).
7. **`/agents` memakai readiness provider:** `provider_ready` tidak lagi selalu `None`; alasan `provider_not_ready`/`provider_disabled`/`provider_readiness_unknown`.
8. **Kill switch `provider_calls_enabled`** (FR-158, ADR-011): kunci `projects.settings` (boolean; tidak ada = `true`) di `SETTINGS_KEYS` dan `SettingsIn`; diaudit sebagai `project.update` yang sudah ada.
9. **Syarat warisan AG-13 3.1a:** variabel yang dibaca SDK/httpx untuk CA dan proxy didokumentasikan (CONFIGURATION); `verify_before_production: true` membuat `pricing_verified` gagal di produksi.

## Goals 3.1e2

1. `/settings/providers`: daftar provider, status key (`configured`/`missing` + hint), model efektif dan `model_policy` (ubah), `enabled`, readiness terakhir per check, tombol smoke test (batas waktu klien 60 dtk; `202` → tampil "masih berjalan" dan muat ulang readiness).
2. Landing `/settings` dan item sidebar hanya untuk pemegang `settings:*`.
3. Pernyataan data flow (SECURITY_MODEL §7) di layar, lewat kunci i18n `id`/`en`.

## Non-goals

- Penegakan runtime (AgentRuntime menolak bila tidak siap atau kill switch mati; task `failed` `PROVIDER_DISABLED`): 3.1f.
- Smoke dengan key sungguhan sebagai gate: WP-INT-07 (PO + Operator).
- Dialog pernyataan data flow saat task pertama: WP-3.2. Toggle kill switch di layar pengaturan project: WP layar project berikutnya (belum ada layar pengaturan project).
- Key per proses (`KK_PROCESS_ROLE`, ADR-053).

## Keputusan Lead 3.1e

1. **Pecah 3.1e1/3.1e2** (pola 3.1c1/3.1c2): backend dan layar diuji dan direview terpisah.
2. **Key hanya di `worker`.** ARCHITECTURE §2, SECURITY_MODEL §7, ADR-053, compose dan `test_compose_policy.py` menaruh `ANTHROPIC_API_KEY` hanya di worker, dan `api` tidak punya jaringan keluar. ADR-004 "(dan `api` untuk smoke test)", SECURITY_MODEL §1/§6.1, CONFIGURATION "+api smoke" dan DEPLOYMENT diselaraskan; smoke berjalan di worker (CLI atau job). Konflik #12/#40 ditutup dengan cara ini.
3. **Smoke dari API = job worker + tunggu terbatas.** Menyatukan §9 (`{job_id}`) dan §11 #8 (sinkron): selesai dalam batas → bentuk §11 #8; lewat batas → `202 {job_id}` dan laporan lewat §11.3. Tanpa result backend Celery: API membaca baris `provider_configs`.
4. **Status key dilaporkan worker.** `api` tidak memegang key, jadi `secret_status`/`secret_hint`/`secret_fingerprint` adalah yang terakhir dilihat worker (CLI, job, atau 3.1f). Fingerprint mendeteksi rotasi; hint memenuhi "masked identifier" FR-128.
5. **Model:** `model_policy` (per alias `default`/`fast`/`complex`) menimpa `CLAUDE_MODEL_*` per alias; alias yang kosong memakai env. ID divalidasi pola `claude-…`; tidak ada ID atau harga yang di-hard-code (FR-130).
6. **`base_url` tidak bisa diubah lewat API.** Mengarahkan key ke host lain adalah eksfiltrasi; `ANTHROPIC_BASE_URL` tetap dari env dengan validasi https produksi yang sudah ada (AG-13 3.1a L1). `base_url` di GET adalah yang dilaporkan worker.
7. **Kill switch vs belum siap:** kill switch mati → task `failed` `PROVIDER_DISABLED` (SECURITY_MODEL §7); provider belum siap → task berhenti di `draft` dengan banner (ARCHITECTURE §5.4). Keduanya ditegakkan 3.1f; 3.1e memberi predikat dan menambahkan `PROVIDER_DISABLED` ke daftar kode error.
8. **Mode scripted dan `LLM_REQUIRE_READINESS=false`:** smoke berjalan terhadap provider yang dikonfigurasi (`ScriptedProvider` di dev/test) dan mencatat `llm_provider_mode`; laporan dari mode lain tidak dihitung siap. `LLM_REQUIRE_READINESS=false` (dilarang di produksi) membuat `provider_ready` benar tanpa laporan, dan itu disebut di `/agents`.
9. **Check kesembilan `pricing_verified`:** syarat warisan "verify_before_production ditegakkan" paling murah ditegakkan sebagai check readiness; aditif terhadap 8 kunci §11 #8.
10. **Siapa yang memegang kill switch (AG-13 3.1e1 M2, 11 Nov 2026).** UC-10/GLOSSARY menjadikan FR-158 kontrol admin (`settings:providers`), sedangkan `PATCH /projects/{id}` hanya butuh `project:write`. Admin global tidak melihat project orang lain tanpa role di project itu (AC-01: role global tidak memperluas visibilitas), jadi "hanya admin, dua arah" berarti project milik developer tidak bisa dimatikan sama sekali. Diputuskan: **mematikan** (`false`) boleh oleh siapa pun yang boleh menulis project (arah aman: menghentikan aliran data project itu sendiri); **menyalakan kembali** (`true`) butuh `settings:providers`, sehingga stop dari admin tidak bisa dibatalkan penulis project. Admin yang perlu menyalakan kembali project developer butuh role di project itu.

## Review Focus 3.1e1 (dibuktikan test)

1. Key tidak pernah muncul di respons API, laporan readiness, log, audit, atau error (juga saat check gagal).
2. `api` tidak pernah membaca key; smoke hanya berjalan di worker.
3. Readiness hanya `passed` bila semua check lulus dengan mode yang sama; mengubah `model_policy` atau merotasi key mengembalikannya ke `unknown`.
4. `PATCH` tidak bisa mengubah `base_url` atau menerima key; semua endpoint menolak tanpa `settings:providers`.
5. `provider_calls_enabled=false` membuat `provider_calls_allowed` salah; kunci lain di `settings` tetap ditolak.

## Konflik (dilaporkan ke #72)

- Pemegang key: ADR-004, SECURITY_MODEL §1/§6.1, CONFIGURATION, DEPLOYMENT, IMPLEMENTATION_DESIGN_V2 (`api` juga) vs ARCHITECTURE §2, SECURITY_MODEL §7, ADR-053, compose (worker saja). Diputuskan: worker saja (Keputusan #2).
- Respons smoke: §9 `{job_id}` vs §11 #8 sinkron tanpa polling vs §11.3 GET readiness. Diputuskan: Keputusan #3.
- DATA_MODEL `provider_configs` tanpa `llm_provider_mode` dan kolom status key; `base_url` di §9 PATCH. Diputuskan: kolom ditambah, `base_url` ditolak.
- `projects.settings` tanpa `provider_calls_enabled`; FR-158 tidak ada di daftar FR WP-3.1 di WBS. Diputuskan: ditambah di 3.1e.
- Kode error `PROVIDER_DISABLED` tidak ada di tabel API §1.
- Check kesembilan `pricing_verified` di luar 8 kunci §11 #8.
- Pemegang kill switch: UC-10/GLOSSARY (admin, `settings:providers`) vs `PATCH /projects/{id}` (`project:write`) vs AC-01 (admin global tidak melihat project orang lain). Diputuskan: Keputusan #10.
