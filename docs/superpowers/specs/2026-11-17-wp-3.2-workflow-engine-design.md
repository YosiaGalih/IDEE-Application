Tanggal: 17 Nov 2026. Status: Proposed. Keputusan Lead diambil di bawah mandat PO "jalan tanpa menunggu, catat keputusan Lead, laporkan konflik ke #72".

Bahan:
- WBS `docs/wbs/wbs_data.py:197-201`: WP-3.2 = "Orchestrator S1–S10, dispatch, lease/heartbeat, checkpoint, recovery, cancel, SSE replay, chat→task", FR-033–040, FR-048–058, AC-04, AC-05, AC-14, AC-17;
- `docs/IMPLEMENTATION_ROADMAP.md` R3.4–R3.6, R4.5, R5.3, R5.5;

## 1. Maksud

Semua bagian bawah sudah ada dan teruji:
- state machine `transition`;
- lease `claim/renew/release`;
- recovery task dan run;
- `BudgetGuard`;
- event store `task_events` beserta publish sesudah commit;
- `AgentRuntime` + `build_agent_runtime`;
- `ToolGateway` dengan 14 builtin;
- approval `tool_r3`;
- klien SSE frontend.

Yang belum ada adalah **lapisan yang menyatukannya**. Belum ada kode yang membuat task, mengirim job, menjalankan tahap, menulis checkpoint, membatalkan task, atau men-stream event ke browser. Belum ada juga layar task maupun chat. WP ini membangun lapisan itu, sehingga satu prompt menjadi task yang punya requirement, plan, dan commit di branch task. Progresnya dapat diikuti, dibatalkan, dan dilanjutkan sesudah restart.

Prinsip produk yang dijaga:
- **#1 evidence over claims:** task tidak pernah `completed` dari teks agent. Di WP ini task tidak pernah `completed` sama sekali (Keputusan #2).
- **#2 satu pintu side effect:** semua tool lewat `ToolGateway`, termasuk tool-mode A04.
- **#3:** engine tidak menjalankan kode project. S4 hanya menulis file dan commit lewat `app/gitops`.
- **#4:** status hanya lewat `transition`.
- **#5:** approval dibuat server dan diputuskan manusia.
- **#7:** orchestrator adalah kode deterministik di worker, bukan LLM (AGENT_CATALOG §9).

## 2. Keadaan sekarang (ringkas) [Pasti]

| Bagian | Ada | Belum |
|---|---|---|
| State machine | `ALLOWED` lengkap termasuk ADR-021; catatan WBS "kurang 3 transisi" basi (N1) | pemanggil yang memajukan task (draft→planned→queued→running) |
| Lease | `claim_lease` (hanya `queued`), `renew_lease`, `release_lease`, kapasitas dari lease hidup | pemanggil produksi `claim`/`release`; lease untuk fase `draft` (K6) |
| Recovery | task `running|validating` kedaluwarsa → `interrupted`; run/tool call yatim ditutup | task `draft`/`queued` yatim (N7) |
| Event | `emit_task_event`, `task_events` (seq tanpa celah), publish sesudah commit | endpoint SSE, subscriber Redis, gap-fill dari DB (LOW-14) |
| Runtime | `AgentRuntime.run`, `read_run_outcome`, `RUNTIMES_AVAILABLE` (masih `False`) | pemanggil produksi; pemetaan hasil run → status task (N15) |
| Data | `tasks` (semua kolom), `conversations`, `agent_runs`, `tool_calls`, `approvals`, `usage_records` | `messages`, `requirements`, `acceptance_criteria`; evidence (`artifacts`, `test_runs`, `findings`, `acceptance_reports`) |
| API | – | seluruh API §5 (tasks, conversations, events) |
| Worker | Celery, beat, `JobQueue` (`send_task`), `worker_ready` sweep | job `run_task`, `enqueue_task`, `worker_id` |
| Frontend | `openEventStream`/`useTaskEvents` teruji, route placeholder `tasks`, `tasks/:taskId` | `features/tasks`, ChatPanel (placeholder `capability_disabled`) |
| Skenario | `generic`, `faults`, `readiness` | `calc` (3.1f3) |

Batas arsitektur yang mengikat (import-linter, `backend/pyproject.toml`):
- `app.workflow` di bawah `app.services`, jadi engine tidak boleh mengimpor `build_agent_runtime`, `tool_r3`, atau `job_queue`;
- runtime dilarang mengimpor `states` dan `models.tasks`;
- `app.api` tidak boleh mengimpor `app.workflow`, `app.worker`, atau runtime;
- FastAPI hanya di `app.api`.

Guard AST yang berlaku: penulis status, penulis `agent_runs`, satu jalur panggilan model, penulis approval, penulis usage.

## 3. Goals

- **G1 Chat → task (AC-04).**
  - Conversations dan messages tersimpan sesudah redaksi.
  - `POST /projects/{id}/tasks` dan `POST /conversations/{cid}/messages` membuat task `draft` dengan budget efektif yang disalin, lalu mengirim job.
  - Daftar dan detail task memakai bentuk API §5 dan §11 #1–#2.
- **G2 Stream (AC-05).**
  - `GET /tasks/{id}/events` (SSE) melakukan replay dari DB, lalu subscribe Redis, membuang duplikat seq, dan mengisi celah dari DB (LOW-14). Heartbeat 15 dtk; stream berhenti di status terminal.
  - Tersedia juga `GET /tasks/{id}/events/history`.
- **G3 Engine S1–S4.**
  - Job `run_task` meng-claim lease, menjalankan tahap dari checkpoint secara idempoten, dan memajukan status lewat `transition`:
    - S1 A02: requirement baseline v1, atau `needs_clarification`;
    - S2 A04 tool-mode: paket konteks ≤ 60 KB;
    - S3 A03: plan DAG;
    - plan approve, atau otomatis menurut kebijakan;
    - S4 B14 di worktree `kk/task-<8hex>` + `git.commit_task`.
  - Sesudah S4 task berhenti jujur (Keputusan #2).
- **G4 Dispatch dan pemulihan (AC-17).**
  - Duplicate delivery tidak menjalankan task dua kali.
  - Worker mati: planning dikirim ulang dengan batas; eksekusi menjadi `interrupted`.
  - `resume` melanjutkan dari checkpoint tanpa mengulang langkah selesai.
  - Pesan broker yang hilang dikirim ulang oleh sweep.
- **G5 Cancel dan pause (AC-14).**
  - `cancel_requested` mencapai `CancelToken` worker.
  - API memanggil `sandbox.kill_task`. Kill yang gagal ditandai eksplisit.
  - Pause berhenti di batas langkah sesudah checkpoint.
- **G6 Approval milik engine.**
  - `budget_increase` dibuat dari `BudgetBreach`; handler-nya → `queued`/`cancelled`, divalidasi terhadap `BUDGET_MAX_*`.
  - Task diparkir di `waiting_approval` hanya bila approval `pending`.
  - Resume `tool_r3` di bawah run yang sama lewat jalur "reopen" yang ditinjau AG-13.
  - Approval saat planning (`draft ↔ waiting_approval`, ADR-021).
- **G7 Layar.**
  - `/projects/:id/tasks`: daftar task.
  - `/tasks/:id`: Ringkasan, Rencana, Agents & Tools, Log/timeline; aksi clarify, plan approve, cancel, pause, resume; badge "Scripted provider (demo)".
  - ChatPanel di IDE: riwayat, `context_refs`, `agent.delta` dengan `reset` per `call`, kartu bukti tool yang terpisah dari output AI, stop.
  - Dashboard: quick create dan aksi antrean (FR-010/011).
- **G8 Runtime hidup.** `RUNTIMES_AVAILABLE` `agent_runtime` dan `workflow_engine` menjadi `True`. Semua syarat bawaan dari T terpenuhi atau dipindah dengan alasan (§9).

## 4. Non-goals

- S5 test dan S6 debug: `tests.run`, `test_runs`, debugger C20 (WP-4.1, ROADMAP R4.2/R4.4).
- S7 review, S8 user proxy, `verify_report`, S9 gate, S10 apply/merge, handler `apply_changes`, dan tabel evidence (WP-5.1/5.x, ROADMAP R5.2–R5.5).
- Tool `memory.*`, `review.get_task_diff`, `acceptance.*`, dan `env.inspect_runtime`.
- Skenario `calc-debug` dan `calc-gap`, karena butuh S5–S8.
- Take-over ADR-058 (WP-13.1), multi-task paralel per project, dan tier M/L.
- Tab Testing, Review & Diff, dan User Proxy di `/tasks/:id` (WP-5.2), selain tautan diff branch.

## 5. Anti-goals

Hal berikut membuat WP ini gagal walau secara teknis "jalan":
- task `completed`, `passed`, atau `validated` tanpa evidence tool;
- status yang disimpulkan dari teks agent atau dari exception, bukan dari `AgentRunResult`/`read_run_outcome`;
- loop LLM sinkron di handler HTTP (NFR-02); request web menunggu agent;
- lease yang dilepas selama tool berjalan, sehingga recovery menutup panggilan yang sedang hidup (ARCHITECTURE §5.3 predikat a);
- tombol "stop" yang hanya menghentikan animasi (FR-036);
- event yang hilang diam-diam saat reconnect, atau seq ganda di layar;
- `agent_run_id` yang dipakai ulang lintas `run()`.

### 7.1 Letak engine

| Pendekatan | Isi | Untung | Rugi |
|---|---|---|---|
| **A. Engine di `app/workflow/engine.py` dengan port** (dipilih) | Logika tahap, checkpoint, dan pemetaan hasil run → transisi di `app.workflow`. Runtime, gateway, git, dispatcher, dan sandbox masuk lewat Protocol `WorkflowPorts`, dirakit di `app/services/tasks.py::build_orchestrator()` (ADR-022) dan dipanggil job `app/worker/jobs.run_task` | Sesuai ADR-022 dan lapisan import-linter. Engine bisa diuji dengan port palsu tanpa Celery. `transition` dan `lease` sudah di `app.workflow` | Port bertambah. Perakitan di services perlu disiplin |
| B. Engine di `app/services/orchestrator.py` | Memanggil `build_agent_runtime` langsung | Lebih sedikit port | Melanggar ADR-022, dan menaruh logika state di services yang juga dipakai API. Test butuh lebih banyak infrastruktur |
| C. Satu job Celery per tahap (chain) | `run_intake` → `run_context` → … | Tahap terisolasi | Claim/lease per tahap, state tersebar di broker, cancel dan pause lebih sulit, `visibility_timeout` per tahap. Tidak ada dokumen yang memintanya |

A dipilih. C ditolak karena menggandakan semantik lease dan memindahkan sumber kebenaran urutan ke broker (bertentangan dengan prinsip #4).

**Penyelarasan 3.2c2c2 (N58, #95).** Kalimat "pemetaan hasil run → transisi di `app.workflow`" dan "runtime … masuk lewat Protocol `WorkflowPorts`" pada baris A **digantikan** oleh ini, sesuai kode: `WorkflowPorts` tidak punya port runtime. Runtime masuk lewat langkah. `build_orchestrator` (`app/services/orchestrator.py`) merakit `AgentRuntime` per delivery dengan owner lease delivery dan mengikatnya ke langkah lewat adapter `app/services/agent_step.py`. Pemetaan murni akhir run → verdict ada di `app/workflow/run_outcomes.py` (tanpa IO, hanya mengembalikan hasil langkah); **engine yang menulis status** lewat `transition`/`fail_task`, tidak pernah adapter atau pemetaan. Perakitan di `app/services/orchestrator.py`, bukan `app/services/tasks.py` seperti tertulis di baris A.

## 8. Keputusan Lead 3.2

1. **Cakupan (N2).** WP-3.2 mencakup:
   - ROADMAP R3.4 (engine S1–S4, SSE), R3.5 (chat/task API + layar), dan R3.6 (worktree per task);
   - R4.5 (cancel, recovery, resume), yang ditarik maju karena WBS menaruhnya di WP-3.2 dan task yang berjalan tanpa cancel tidak aman.

   S5–S6 tetap di WP-4.1, sedangkan S7–S10 dan handler `apply_changes` di WP-5.1/R5.5. Catatan WBS "3 transisi kurang" dan bukti snapshot "178 test" tidak berlaku (N1).
2. **Titik berhenti jujur sesudah S4.**
   - Sesudah S4 berhasil (commit ada di branch task), engine mentransisi `running → interrupted` dengan `status_reason=validation_unavailable`, menyimpan `checkpoint.phase=test`, melepas lease, dan meng-emit `task.log` `{code: "validation_unavailable"}`.
   - Task tidak pernah `validating`, karena sweep akan mengubah `validating` tanpa lease menjadi `interrupted lease_expired`, yang menyesatkan. Task juga tidak pernah `completed`.
   - `POST /resume` atas task ini menjawab 409 `CONFLICT` `details[0].reason=validation_unavailable` selama S5 belum ada.
   - Layar menjelaskan bahwa perubahan ada di branch `kk/task-…`, bahwa validasi otomatis belum tersedia, dan menautkan diff.
   - Alternatif yang ditolak:
     - `needs_changes` (menyatakan ada yang salah);
     - `failed` (menyatakan gagal);
     - `validating` (dipulihkan sweep).
3. **K6: satu job, lease untuk planning.**
   - `run_task(task_id)` meng-claim task `draft` (planning S1–S3; status tetap `draft` selama di-lease) dan task `queued` (→ `running` lewat `transition`).
   - `claim_lease` diperluas dengan himpunan status yang dapat di-claim. Kapasitas tetap dihitung dari semua lease hidup, sehingga planning ikut dihitung `MAX_ACTIVE_TASKS`. Ini menyimpang dari ARCHITECTURE §5.3 "hitungan task `running|validating`", dilaporkan sebagai N12, dan diselaraskan di dokumen.
   - Runtime dan recovery run tidak berubah: run planning kini memegang lease hidup.
4. **Dispatch yatim (N7) dan planning yang terputus.**
   - Sweep recovery menambah satu fase: task `draft`/`queued` tanpa lease hidup yang dispatch terakhirnya (`checkpoint.dispatch.at`) lebih tua dari grace dikirim ulang lewat `enqueue_task`. Kirim ulang ini aman, karena claim menolak duplikat.
   - Planning yang terputus (lease `draft` kedaluwarsa) dihitung di `checkpoint.dispatch.planning_attempts`. Pada percobaan ke-4 task `draft → failed` dengan `error_code=planning_interrupted`.
   - Ini retry otomatis, sehingga memicu tinjau ulang LOW-3 (SECURITY_MODEL §13). AG-13 meninjaunya di 3.2c1, walau sub-WP itu tidak 🔒.
   - Task `queued` tidak dapat `failed` (edge tidak ada), jadi selalu dikirim ulang. Biaya dibatasi oleh budget task.
5. **Letak engine.** Pendekatan A (§7.1):
   - `app/workflow/engine.py` + `app/workflow/checkpoint.py`;
   - `WorkflowPorts` dirakit `app/services/tasks.py::build_orchestrator()`;
   - job `app/worker/jobs.run_task`.

   Engine memanggil `transition` dan tidak pernah menulis `.status` (guard AST tetap berlaku).
6. **Dispatcher (N6).**
   - Port `JobQueue` yang ada (WP-2.1b) menjadi seam dispatcher ADR-028 dengan metode baru `enqueue_task(task_id)` (queue `ide`, nama `app.worker.jobs.run_task`). `RecordingDispatcher` = antrean palsu di test.
   - Enqueue dilakukan sesudah commit. Galat kirim tidak menggagalkan request (task sudah tersimpan): galat di-log, dan sweep Keputusan #4 yang mengirim ulang.
7. **Gerbang pembuatan task.**
   - Sampai engine dapat membawa task melewati planning (3.2d), `POST /projects/{id}/tasks` dan `POST /conversations/{cid}/messages` dengan `create_task=true` menjawab 503 `DEPENDENCY_UNAVAILABLE` dengan `details[0].reason=workflow_engine_unavailable`, sebelum menulis apa pun.
   - Gerbangnya `RUNTIMES_AVAILABLE["workflow_engine"]`. Flag ini dan `agent_runtime` dibalik di 3.2d.
   - Pesan chat tanpa task selalu boleh.
   - Alternatif yang ditolak: membuat task `draft` dan menjawab 202 tanpa ada yang memprosesnya (klaim "accepted" palsu).
8. **Pemetaan hasil run → status task (N15; arah, difinalkan 3.2c2).** **Digantikan #8 final (tabel final di §16.6.5 A, WP-3.2c2c2)**: tabel arah, kalimat "`tasks.error_code` ditulis bersama transisi" dan dua himpunan nilai di bawah ini tetap sebagai riwayat. Yang berubah: `lease_lost` menjadi `LeaseLost` dan `worker_cancelled` menjadi `StepAbandoned` (bukan "tidak ada transisi" tanpa nama), `cancelled` menjadi `StepAbandoned("run_cancelled")` (N51), kode provider ditulis huruf kecil (N21), `read_run_outcome` dipakai untuk jalan keluar tanpa hasil (N57), dan himpunan `tasks.error_code` menjadi 19 kode tertutup (N55) menggantikan "kode run ∪ {…}".

   | Hasil run | Fase planning (`draft`) | Fase eksekusi (`running`) |
   |---|---|---|
   | `succeeded` | lanjut tahap | lanjut tahap |
   | `failed` `provider_not_ready` / `PROVIDER_DISABLED` / `provider_auth` | `failed`, `error_code` = kode run | `interrupted`, `status_reason` = kode run (Keputusan Lead 3.1f #15) |
   | `failed` `timeout` / `iteration_limit` / `invalid_output` / `model_error` / `internal_error` / `usage_unrecorded` | `failed` + `error_code` | `failed` + `error_code` |
   | `failed` `lease_lost` / `worker_cancelled` | tidak ada transisi; job berhenti, lease bukan milik kita lagi atau worker berhenti; sweep yang menangani | sama |
   | `cancelled` | `cancelled` bila `cancel_requested`, selain itu seperti `worker_cancelled` | sama |
   | `budget_exceeded` | sementara (sebelum 3.2g): `failed` `error_code=budget_exceeded`; sesudah 3.2g: `waiting_approval` + `budget_increase` | sama |
   | `approval_required` | sebelum 3.2g: `failed` `error_code=approval_unsupported` (MVP tanpa tool R3 hidup); sesudah 3.2g: parkir hanya bila approval `pending` | sama |
   | jalan keluar tanpa `AgentRunResult` | `read_run_outcome(...)`, tidak menyimpulkan dari exception | sama |

   `tasks.error_code` ditulis bersama transisi (savepoint yang sama). Himpunan nilainya (digantikan #8 final) = kode run ∪ {`planning_interrupted`, `budget_exceeded`, `approval_unsupported`, `worktree_failed`, `commit_failed`}, dan didokumentasikan di DATA_MODEL.

   Penambahan (3.2c2b1, §16.5): `step_unavailable` (N35), `step_result_invalid`, dan `duration_exceeded`. Penambahan 3.2c2c: `agent_unavailable` dan `agent_input_invalid` (#52). Himpunan saat ini (digantikan #8 final, §16.6.5 A: 19 kode tertutup, `TASK_ERROR_CODES`) = kode run ∪ {`planning_interrupted`, `step_unavailable`, `step_result_invalid`, `duration_exceeded`, `budget_exceeded`, `approval_unsupported`, `worktree_failed`, `commit_failed`, `agent_unavailable`, `agent_input_invalid`}.
9. **Retry planning yang gagal: edge `failed → draft` (ADR-076 Proposed).**
   - `POST /resume` atas task `failed` yang plan-nya belum disetujui (`checkpoint.plan_approved` tidak ada) → `failed → draft` + dispatch. Bila plan sudah disetujui → `failed → queued` (edge lama).
   - Tanpa edge ini, planning yang gagal hanya bisa diulang di status `running`, padahal S1–S3 berjalan di `draft` (ARCHITECTURE §5.2), sehingga gerbang plan approval terlewati.
   - Edge ini menambah satu baris di `ALLOWED`, test matriks, dan diagram ARCHITECTURE §5.1 di 3.2f.
10. **Cancel lintas proses (N9) dan kill gagal (N8); arah, difinalkan 3.2f.**
    - Perpanjangan lease (heartbeat runtime + perpanjangan engine di batas langkah) membaca `cancel_requested`/`pause_requested` di UPDATE yang sama (`RETURNING`), lalu memicu `CancelToken` milik job. Latensi ≤ `HEARTBEAT_SECONDS`. Engine juga memeriksa di setiap batas langkah.

### 13.2 Keputusan Lead 3.2b

27. **Satu hub per proses.**
    - `TaskEventHub` membuka satu koneksi pubsub (`psubscribe kk:task:*`) per proses api, dimulai saat lifespan.
    - Hub menyebar pesan ke antrean per stream yang dibatasi 1000 pesan.
    - Antrean penuh → stream ditandai tertinggal. Event persisten tetap dipulihkan dari DB (gap-fill); ephemeral yang terbuang tidak dipulihkan (RD-2: narasi dimuat ulang dari `agent.message`/`agent_runs`).
    - Redis putus → hub menyambung ulang dengan backoff. Selama itu stream tetap benar lewat cek DB di setiap ping (#28), hanya lebih lambat.
    - Alternatif yang ditolak: satu koneksi pubsub per stream, karena koneksi Redis tumbuh sebanyak tab terbuka.
28. **Urutan tanpa celah dan tanpa duplikat (LOW-14).**
    1. Daftarkan listener di hub **sebelum** replay.
    2. Replay `seq > cursor` dari DB per halaman 500, setiap halaman dalam sesi pendek. Tidak ada sesi DB yang dipegang selama stream hidup.
    3. Pesan live:
       - `seq ≤ cursor` → dibuang;
       - `seq = cursor+1` → dikirim;
       - `seq > cursor+1` → isi celah dari DB dulu, baru dikirim;
       - ephemeral (`seq` null) → dikirim tanpa `id`.
    4. Pada setiap ping (15 dtk) satu query membaca `tasks.event_seq` dan `status`. Bila `event_seq > cursor`, isi dari DB. Ini menutup penulis yang commit tanpa publish.
29. **Titik lanjut.**
    - Header `Last-Event-ID` menang atas `?after_seq=`, karena header itu mekanisme reconnect klien.
    - Keduanya bilangan bulat 0..2^63−1. Nilai lain → 422 `VALIDATION_ERROR` sebelum stream dimulai.
    - Tanpa keduanya → replay dari awal.
30. **Akhir stream.**
    - Bila status task ∈ {`completed`, `failed`, `cancelled`, `rejected`} (`FINISHED`) dan semua event sampai `event_seq` sudah terkirim, server mengirim frame tanpa `id`: `event: stream.end`, `data: {"task_id", "status"}`, lalu menutup.
    - Bila baris task hilang (project dihapus): frame yang sama dengan `status: null`.
    - Klien yang menerima `stream.end` berhenti tanpa reconnect (status `ended`). Layar membuka stream lagi sesudah aksi user (resume, retry, reopen).
    - `interrupted` dan `waiting_approval` bukan akhir, karena dapat lanjut tanpa aksi di tab itu.
31. **Umur dan izin.**
    - Satu koneksi paling lama 55 menit (di bawah `read_timeout` Caddy 1 jam). Sesudah itu ditutup tanpa `stream.end`, dan klien menyambung ulang dengan `Last-Event-ID`.
    - Umur tiap stream diacak hanya ke bawah, merata di [0,9 × 55, 55] menit (49,5–55 menit; `jittered_timings`), supaya stream yang dibuka bersamaan, mis. sesudah deploy, tidak menyambung ulang bersamaan. Batas 55 menit di atas tetap berlaku (ruling R7, fix wave akhir 3.2b).
    - Setiap 60 dtk sesi dan izin `task:read` atas project task diperiksa ulang dengan memuat ulang actor dari sesinya. Gagal → tutup tanpa `stream.end`, sehingga reconnect klien mendapat 401/404 dan berhenti (`FATAL`).
32. **Batas.**
    - Paling banyak 8 stream terbuka per user dan 256 per proses. Lewat batas → 429 `RATE_LIMITED`, `details[0].reason = "too_many_streams"`, sebelum stream dimulai.
    - Penghitung ada di memori proses. Ini benar untuk satu proses (tier S). Tier yang lebih tinggi membawa penghitung ke Redis (dicatat).
33. **Bentuk frame.** Mengikuti API §5.1:
    - `id: <seq>` hanya untuk event persisten;
    - `event: <type>`;
    - `data: <JSON satu baris>`, yaitu pesan tersimpan `{task_id, seq, type, ts, payload}`.
    - Event dari DB dan dari Redis memakai fungsi bentuk pesan yang sama.
    - `type` diperiksa `^[a-z][a-z0-9_.]{0,59}$` sebelum ditulis ke baris `event:`. Yang tidak cocok tidak dikirim, dan di-log.
    - Header respons: `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store`, `X-Accel-Buffering: no`, `X-Request-ID`.
    - Galat sebelum stream dimulai memakai envelope JSON biasa.
34. **Riwayat.**
    - `GET /tasks/{tid}/events/history?after_seq=0&limit=100` (`limit` 1..500) → `[TaskEvent]` urut `seq` naik, dengan `meta.next_after_seq` = seq terakhir bila halaman penuh, selain itu `null`.
    - Izin `task:read`. Di luar scope → 404, sama dengan id acak.
35. **Letak kode.**
    - `app/services/task_events.py`, tanpa FastAPI: query halaman, riwayat, `TaskEventHub`, dan generator frame `async def stream_frames(...) -> AsyncIterator[str]`.
    - Route di `app/api/routes/tasks.py` membungkus generator dengan `StreamingResponse`.
    - Hub dibuat dan dimulai bersama `Dependencies`, lalu dihentikan saat shutdown.
36. **Frontend.**
    - `openEventStream` mengenal `stream.end`: status baru `ended`, tidak reconnect, dan `retry()` memulai lagi.
    - `useTaskEvents` menyimpan paling banyak 500 event terakhir dan menghitung `dropped`, sehingga layar dapat memuat yang lebih lama lewat riwayat. `ended` tidak menghasilkan `uxState` galat.

      - Bila perubahan status ditolak, event dan catatan checkpoint ikut batal.
    - **Exception langkah tak terduga (R-T3c).** Heartbeat dihentikan, lease dilepas best-effort, exception dilempar ulang. Tidak ada status ditulis; sweep yang ada memulihkan task.
    - **Pipeline habis tanpa transisi (R-T3d).** Log `pipeline_exhausted`, lease dilepas, tanpa kode error baru.
    - **Heartbeat berbatas (R-T3h, diubah sesudah review).** Perpanjangan yang gagal atau macet diulang hanya sampai `last_ok + lease − heartbeat_s`. Setiap percobaan dibatasi `asyncio.timeout(heartbeat_s)`. Lewat tenggat, engine menganggap lease hilang dan membatalkan langkah.
    - **Reset putaran checkpoint (R-T3k).** Engine memperlakukan `completed_steps` dan `dispatch.planning_attempts` apa adanya. Penulis setiap edge masuk ulang yang me-reset-nya:
      - 3.2d: jawaban klarifikasi (`needs_clarification → draft`) membuang `context`/`plan` dari `completed_steps` dan me-reset `planning_attempts`;
      - 3.2f: resume (`interrupted → queued`) mempertahankan `completed_steps` (AC-17); retry (`failed → draft`, ADR-076) me-reset langkah planning dan `planning_attempts`;
      - 3.2g: approval `→ draft` me-reset sesuai keputusannya;
      - iterasi baru (`completed|needs_changes → queued`) me-reset pipeline `running`.
    - **Tanpa port `clock` (R-T3a).** Semua keputusan waktu memakai jam DB.
    - **Batas durasi job (R-T5b).** Belum ada di 3.2c1. 3.2c2 memasang `TASK_MAX_DURATION_MINUTES` di sekitar `engine.run`.
    - **Id task tidak sah di `run_task` (R-T5a).** Di-log `run_task_invalid_id` dan job kembali tanpa raise, supaya pesan tidak dikirim ulang terus.

    - PoC black hole AG-13 3.2c1 menjadi test regresi.

### 16.7.2 Konflik dan Keputusan Lead (N64–N77)

101. **N64 → hibrida: penulis `cancelled` ditentukan oleh ada tidaknya lease hidup.**
     - Di bawah kunci baris (`FOR UPDATE`, dengan jam DB), API memeriksa lease. Task **tanpa lease hidup** (`lease_owner` null, atau `lease_expires_at <= clock_timestamp()`) di-`transition` langsung oleh API ke `cancelled`. Task **dengan lease hidup** hanya diberi flag `cancel_requested=true` lalu di-commit. Engine pemilik lease yang menulis `cancelled` (N51).
     - `queued` tidak pernah ber-lease hidup, karena claim memindahkannya ke `running` di transaksi yang sama. Jadi `queued` selalu langsung `cancelled` [Pasti].
     - Respons `Task` memuat `cancel_requested=true` dan status saat itu. Status bisa masih `running`; FE menampilkannya sebagai "membatalkan…".
     - Teks #10 "task tetap `cancelled`" dibaca "pembatalan tetap berjalan": kill yang gagal tidak membatalkan pembatalan. Teks #10 diperbarui.
     - Bila worker mati sebelum menulis, recovery sudah menutup task menjadi `cancelled` (`recovery.py:131-139`), dalam ≤ lease 60 dtk + sweep [Pasti].
102. **N65 → token milik engine per percobaan langkah; heartbeat engine membaca flag.**
     - `StepContext.cancel: CancelToken` dibuat baru untuk setiap percobaan langkah. `AgentStep` meneruskan `ctx.cancel` ke `AgentRunRequest.cancel`, menggantikan `CancelToken()` yang yatim.
     - Fungsi baru `renew_lease_flags(session, task_id, owner) -> LeaseFlags | None` = `renew_lease` + `RETURNING cancel_requested, pause_requested`. Fungsi ini menghormati owner yang dicabut dengan cara yang sama (`HELD`, tanpa SQL). Hanya heartbeat engine yang memakainya. `renew_lease` dan `LeaseHeartbeat` runtime tidak berubah.
     - Heartbeat engine memicu token sekali bila `cancel_requested`. Latensi pembatalan langkah yang sedang berjalan ≤ `heartbeat_s` (20 dtk).
     - Penyimpangan dari #10 ("heartbeat runtime"): satu sumber kebenaran dan permukaan 🔒 yang lebih kecil. Dicatat sebagai penyempurnaan.
103. **N66 → `pause_requested` tidak memicu token** (ADR-031: pause berhenti di batas langkah). Dikerjakan di 3.2f2.
104. **N67 → pause hanya dari `running`** (kelak juga `validating`). Status lain → 409 `INVALID_TRANSITION`. Pause pada `running` tanpa lease hidup hanya memasang flag, lalu recovery menutupnya menjadi `interrupted`. 3.2f2 memutuskan apakah recovery menghormati flag pause (`paused_by_user`) atau tetap menulis `lease_expired`.
     - Flag di-reset oleh engine saat dihormati, oleh resume/retry di UPDATE yang sama, dan saat task mencapai status akhir.
     - R-T3g: langkah yang selesai tepat sebelum batas pause dicatat di `completed_steps`.
     - `pause_requested` ditambahkan ke `Task` (aditif).
     - Rinciannya di 3.2f2.
105. **N68 → titik baca cancel di engine, dan cancel menang atas semua hasil lain kecuali kehilangan lease.**
     - (i) **Sesudah claim.** Task ber-flag tidak menjalankan langkah apa pun; engine menulis `cancelled`. Ini menutup `draft` yang dikirim ulang sweep sesudah worker mati.
     - (ii) **Di batas langkah** (`_locked`, sebelum hasil diterapkan dan sebelum langkah berikutnya). Hasil yang dibuang di-log `step_result_dropped` (jenisnya saja).
     - (iii) **Sesudah `StepAbandoned`** selama lease masih dipegang. Flag dibaca ulang; `run_cancelled` dengan flag menyala menjadi `cancelled`, bukan sekadar lepas lease.
     - (iv) **Batas delivery dan `_stop_before_step`.** Flag diperiksa lebih dulu, sehingga `cancelled` menang atas `duration_exceeded` (AG-13 3.2c2b1 INFO-2).
     - (v) **Heartbeat** memicu token (#102).
     - `LeaseLost`: engine tidak menulis apa pun, karena recovery yang menutup. Cancel luar (`CancelledError`) tidak berubah.
     - `Stopped` mendapat nilai `"cancelled"`. Aktor `system:engine`, alasan `cancel_requested`. Aktor user tercatat di audit `task.cancel_requested` dari API.
     - Efek samping langkah yang sudah terjadi (misalnya commit) tidak dibatalkan. `cancelled` adalah status akhir, tanpa resume.
106. **N69 → edge `failed → draft` ditentukan dari event `task.status_changed` terakhir dengan `to="failed"`.** `from="draft"` → `draft`; selain itu → `queued`. Polanya `tool_r3._last_change`. `checkpoint.plan_approved` (3.2d) menjadi penjaga tambahan bila ada.
     - `transition` me-NULL-kan `completed_at` juga untuk target `draft`.
     - Retry membersihkan `error_code`/`error_message` di UPDATE yang sama. Teks DATA_MODEL diubah menjadi "ditulis oleh `fail_task`, dihapus saat retry".
     - ADR-076 (Proposed) ditulis di 3.2f2. Penyimpangan dari #9 (`plan_approved`) dicatat.
107. **N70 → reset checkpoint per kunci (`jsonb_set`) dan stempel `dispatch.at`/`count` di transaksi yang sama.**
     - Resume `→ queued` mempertahankan `completed_steps`.
     - Retry `→ draft` membuang langkah `PIPELINE["draft"]` dan mereset `planning_attempts`.
     - Dikerjakan di 3.2f2.
108. **N71 → resume hanya dari `interrupted` dan `failed`.**
     - `interrupted validation_unavailable` → 409 `CONFLICT` `reason=validation_unavailable`.
     - Project wajib aktif.
     - Resume digerbang `ensure_engine_available`. Cancel dan pause tidak digerbang.
     - Task `failed budget_exceeded`/`approval_unsupported` boleh di-resume. Engine akan gagal lagi secara jujur, dan approval yatim dibawa ke 3.2g (N62).
     - Dikerjakan di 3.2f2.
109. **N72 → enqueue dari API dilakukan sesudah commit.** Kegagalan di-log `resume_enqueue_failed` (id dan tipe galat saja), respons tetap sukses, dan sweep mengirim ulang berkat stempel `dispatch.at`.
     - Kode HTTP: cancel dan pause **200** `Task`; resume **202** `Task`.
     - Bagian resume dikerjakan di 3.2f2.
110. **N73 → urutan kill: flag lalu commit, lalu kill di luar DB, lalu penanda bila gagal.**
     1. Di satu transaksi: kunci baris, pasang flag, `transition` bila tanpa lease hidup, tulis audit `task.cancel_requested`, lalu commit.
     2. **Sesudah commit**, bila task punya lease hidup atau berstatus `running|validating` saat dikunci: `sandbox.kill_task(task_id)` di luar sesi DB, dibatasi `asyncio.timeout(KILL_TIMEOUT_S=10)`.
     3. Bila kill berhasil dengan `killed > 0`, tulis audit `sandbox.run_killed` (`task_id`, `killed`). Ini menjadi penulis pertama baris SECURITY_MODEL §6.
     4. Bila kill gagal (`SandboxError`, `SandboxUnavailable`, atau timeout), buka transaksi pendek kedua. Isinya event `task.log` `{level:"warning", code:"cancel_unconfirmed", message:<kalimat tetap>}` dan audit `task.cancel_unconfirmed` (`result=error`, metadata hanya `error_type`). Status tidak diubah dan galat tidak diteruskan ke klien.
     - Payload `task.log` menjadi superset `{level, code?, message}`, sehingga API §5.1 diperbarui.
     - Kill yang tidak terjangkau dapat memasang penanda palsu-positif walaupun tidak ada run; kalimatnya jujur: "tidak dapat dikonfirmasi".
     - **Sisa celah race** [Kemungkinan Besar]: run sandbox baru dapat dimulai di antara kill dan pemicuan token (≤ 20 dtk). Celah ini kini tak terjangkau, karena belum ada tool sandbox di builtin MVP, dan gateway menolak tool sesudah token dipicu. Diterima sebagai LOW dan dibawa ke WP-4.x: kill kedua oleh worker saat engine menulis `cancelled`, ketika tool sandbox hidup.
111. **N74 → route, otorisasi, idempotensi, dan letak penulis status.**
     - Route `POST /tasks/{task_id}/cancel`, body `{reason?: str, ≤ 200}`, 200 `Task`.
     - Otorisasi di service, dari `task.project_id` dengan izin `task:control`: 404 bila task di luar scope, 403 bila tanpa izin (pola `get_task`).
     - Idempotensi alami tanpa `Idempotency-Key` HTTP:
       - cancel atas `cancelled` → 200 tanpa efek, tanpa kill, tanpa audit baru;
       - cancel atas task ber-flag yang masih `running` → 200, flag tetap, kill diulang (aman);
       - cancel atas `completed`/`rejected` → 409 `INVALID_TRANSITION`.
     - Logika di bawah kunci baris ada di modul workflow baru `app/workflow/control.py`, yang ditambahkan ke `TRANSITION_WRITERS` (daftar eksak). Service `app/services/task_control.py` mengorkestrasi otorisasi, panggilan workflow, kill, dan penanda. Route tetap hanya bergantung pada `app.services` (kontrak import-linter).
     - `reason` disimpan di metadata audit, setelah diredaksi dan dibatasi 200 karakter.
112. **N75 → `cancel_open_tasks` memasang `cancel_requested=true` di UPDATE yang sama**, lalu tetap men-`transition` langsung, karena project sedang dihapus. Tidak ada kill di handler hapus project, karena handler itu berjalan di jalur approval tanpa klien sandbox. Heartbeat engine (#102) menghentikan langkah yang sedang berjalan dalam ≤ 20 dtk. Kill yang tidak ada di sini dicatat sebagai batas yang diterima dan dibawa ke WP-4.x.
113. **N76 → approval `pending` pada task yang dibatalkan dibiarkan** sampai kedaluwarsa 24 jam. Handler tool R3 mengabaikan task yang sudah `FINISHED`. Diputuskan di 3.2g bersama N62.
114. **N77 → sinkronisasi dokumen** (daftar lengkap ada di discovery §2 N77).
     - **3.2f1:** API §1/§5.1/endpoint cancel, ARCHITECTURE §5.3 (hibrida), DATA_MODEL `cancel_requested`, SECURITY_MODEL §6 (`sandbox.run_killed`) dan §13 (INFO-2 ditutup, baris baru celah race dan `cancel_open_tasks`), TEST_STRATEGY (`test_cancellation.py`), CONFIGURATION (`HEARTBEAT_SECONDS` sebagai konstanta kode), GLOSSARY, dan spec #10.

Audit `sandbox.run_killed` hanya ditulis bila `killed > 0`. `test_cancel_running_kills_sandbox` memakai `kill_returns=1`, dan test lain memastikan `killed == 0` tidak menulis audit itu.

Test-nya meniru race "flag dipasang sesudah `_locked` terakhir, sebelum pelepasan".

- **R-F6 (BC-6): flag dibaca di transaksi claim, sebelum `count_planning_attempt` dan sebelum `queued → running`.**
  - `draft` ber-flag → `draft → cancelled` langsung, tanpa menghabiskan percobaan planning.
  - `queued` ber-flag → `queued → cancelled` langsung. Jalur ini defensif dan seharusnya tak terjangkau, karena API langsung membatalkan `queued`.
  - Satu baris audit transisi per task.
