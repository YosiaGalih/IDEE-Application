3. **Konstruktor tunggal** (spec #17, AG-13 3.1f1 L1).

   - `bind_model_call(call) -> BoundCall(bound: CallBound, ledger: UsageCallContext)` di services adalah satu-satunya tempat kedua nilai dibangun, dan keduanya dari `ModelCall` yang sama. `GuardBudget` memakai `.bound`, `LedgerRecorder` memakai `.ledger`.
   - `request.metadata["call_id"] == str(call_id)` diwajibkan `__post_init__`, karena `retry.py` me-log `usage_attempt_unrecorded` dengan `req.metadata.get("call_id")` [Pasti].
   - `request_size_bytes` = ukuran UTF-8 JSON ringkas dari `system`, semua blok `messages`, dan definisi `tools`. Batas ini [Kemungkinan Besar] cukup: satu token BPE byte-level paling sedikit satu byte, dan overhead JSON (kunci, kutip, skema tool) jauh lebih besar daripada prompt tool yang disisipkan provider. 5. **Heartbeat latar selama panggilan dan tool** (melengkapi spec #18).
   - Fakta [Pasti]: `LEASE_SECONDS = 60`, `HEARTBEAT_SECONDS = 20`, sedangkan `CLAUDE_REQUEST_TIMEOUT_SECONDS` default 120, `retry-after` bisa ditunggu sampai 60 dtk, dan `ToolSpec.timeout_s` default 60.
   - Heartbeat yang hanya dipanggil sebelum percobaan dan tool bisa kehilangan lease di tengah satu percobaan panjang. Recovery lalu memulihkan task, dan worker lain bisa mengklaimnya, sehingga dua percobaan berjalan untuk satu task (persis yang dilarang AG-13 M1).
   - Karena itu runtime juga menjalankan `beat` tiap `heartbeat_interval_s` (default 20) selama `_call_model` (termasuk jeda retry) dan selama `execute`. `LeaseLostError` dari heartbeat latar menghentikan run lewat token (butir 6) dengan alasan `lease_lost`.
   - Heartbeat titik sebelum setiap percobaan dan setiap tool tetap ada, persis seperti spec #18.

6. **Satu token berhenti per run.**
   - Runtime membuat `CancelToken` internal yang diteruskan ke provider dan ke `ToolContext.cancel`. Token itu dibatalkan oleh alasan pertama dari tiga: `CancelToken` pemanggil (`cancelled`), tenggat run `limits.timeout_seconds` (`timeout`), atau heartbeat latar (`lease_lost`). Alasan pertama yang menang.
   - Pembatalan kooperatif ini dipilih daripada `asyncio.timeout`, karena provider (scripted dan adaptor) menyertakan usage parsial pada `LLMError("cancelled")`, sehingga ledger mencatat `partial`, bukan `unavailable` [Pasti, `scripted_provider._stream`, `_Progress.error`].
   - Pembatalan asyncio terhadap runtime itu sendiri (worker dimatikan) diperlakukan terpisah: run ditutup `failed interrupted` lewat tulisan yang di-shield, lalu `CancelledError` diteruskan.

7. **Rumus `timeout_s` per percobaan** (spec #19, syarat 3.1a):

   ```python
   REQUEST_BASE_S = 30.0            # connect + time to first token for a long prompt [Menebak]
   MIN_OUTPUT_TOKENS_PER_S = 40.0   # the slowest output rate still waited for [Menebak]
   def attempt_timeout_s(max_tokens: int, *, cap_s: float, remaining_s: float) -> float:
       return min(REQUEST_BASE_S + max_tokens / MIN_OUTPUT_TOKENS_PER_S, cap_s, remaining_s)
   ```

   - Dengan `max_tokens = 8192`: 30 + 204,8 → dipotong ke `CLAUDE_REQUEST_TIMEOUT_SECONDS` (120). Dengan 1024: 55,6 dtk.
   - `remaining_s` = sisa tenggat run. Bila ≤ 0 sebelum percobaan, run berakhir `failed timeout` tanpa mengirim apa pun.
   - Konstanta [Menebak]; diuji ulang dengan smoke key nyata di WP-INT-07.

8. **Pemetaan akhir run** (spec #15, #19, #20; Review Focus 5). Fungsi murni `classify(error, stop_reason)` dan tabel test:

   | `submit_result` valid | `succeeded` | – |

   | gerbang `not_ready`/`unknown`; pembuat provider tidak bisa membangun (tanpa key) | `failed` | `provider_not_ready` |

12. **Redaksi `agent.delta`** (spec #24).
    - Bunyi spec: "prefiks teredaksi sampai len − 256; sisanya ditahan". Bila hanya prefiksnya yang diredaksi, secret yang melintasi titik potong lolos sebagian [Pasti, dari pola `app/core/redaction.py`]:
      - `password=ab|cdef`: prefiks diredaksi menjadi `password=[REDACTED]`, lalu `cdef` keluar mentah di delta berikut karena kuncinya sudah terkirim;

**Alur `run`** (urutan yang diuji):
1. Pemeriksaan tanpa baris (Keputusan plan #10): `grant_for(registry, agent_id)`; mode `llm` atau `profile`; runtime = agent itu sendiri atau `runtime_agent`; runtime ∈ `OUTPUT_CONTRACTS`; bukan `ABSORBED_PROFILES`; prompt ada; `type(agent_input) is INPUT_CONTRACTS[runtime]`; ukuran JSON input ≤ `CONTEXT_MAX_BYTES`; `scenario` hanya bila `config.scripted`.
2. `heartbeat.beat` → `gate.check` → `providers.open()`. Kegagalan di sini membuat baris (`start` dengan model `None`) lalu langsung `finish` dengan kode tabel Keputusan plan #8.
3. `runs.start(RunStart(...))` dengan `model_provider = provider.name`, `model_name = models[spec.model_tier]`, `step = STEPS[runtime]`, `prompt_version`.
4. Tool yang ditawarkan: `defs = tools.tool_defs_for(grant)` (grant ∩ terdaftar ∩ prasyarat, urut nama; spec #22), lalu `ToolDef(SUBMIT_RESULT, …, OUTPUT_CONTRACTS[runtime].model_json_schema())` di urutan terakhir (prefiks cache stabil). `ToolContext.offered = {d.name for d in defs}` (tanpa `submit_result`).
5. Pesan pertama: `Message("user", "<agent_input>\n" + redactor.redact(input_json) + "\n</agent_input>")`.
6. Loop sampai `iterations == run_cap(spec.limits.max_iterations, config.max_tool_iterations)`:
   - token berhenti dicek → selesai dengan alasannya;
   - `remaining_s <= 0` → `failed timeout` tanpa mengirim;
   - `iterations += 1`; bangun `LLMRequest` (`max_tokens = config.max_output_tokens`, `timeout_s = attempt_timeout_s(...)`, `metadata = {call_id, task_id, agent_run_id, agent_id, output_contract[, scenario]}`) dan `ModelCall`; `_call_model`; `events.usage_updated`;
   - respons dengan `submit_result` → Keputusan plan #11;
   - respons dengan `tool_use` lain → untuk setiap blok **berurutan**: `budget.before_tool(scope)`, `heartbeat.beat`, `tools.execute(ctx, name, input, tool_use_id=id)` dengan heartbeat latar; `approval_required` → selesai `approval_required` dengan `output = {"pending_tool": {tool_use_id, tool_name, tool_call_id}}`, blok sisanya tidak dijalankan; selain itu `ToolResultBlock(id, result.content, is_error=result.is_error)`;
   - tanpa `tool_use`: sudah di-nudge → `failed invalid_output`; belum → tambahkan `NUDGE` (iterasi berikutnya dihitung).
7. Iterasi habis → `failed iteration_limit`.
8. `finally`: provider ditutup oleh `providers.open()`; token berhenti dan tugas latar dibatalkan dan ditunggu.
