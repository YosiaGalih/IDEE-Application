# WP-3.1f2b2 — gerbang belajar dan tampilan: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The provider gate learns from real calls: a provider that rejects the key (`auth`) or the model (404) drops readiness to `unknown`, and a pricing table that changed since the smoke drops it too. The dashboard shows recent agent runs, and the UI text for `runtime_unavailable` tells the truth.

**Architecture:**
- The runtime's `ProviderGate` port gains `reject(...)`. `check` now returns the report timestamp it judged, so a reject is a compare-and-set against that same report. `DbProviderGate` writes the reset in its own short transaction with an audit row.
- `provider_ready` gains two computed reasons: `provider_rejected` from a marker in the report, and `pricing_changed` from the worker-held pricing version.
- The dashboard reuses the `/agents/{id}` run-summary query inside its REPEATABLE READ snapshot.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy async, PostgreSQL 16, pytest; React 19 + TypeScript, Vitest + RTL + MSW, i18next.

**Spec:** `docs/superpowers/specs/2026-11-15-wp-3.1f2b-runtime-recovery-design.md` covers this plan: Goals G7–G10, Keputusan Lead 3.1f2b #9, #13, #14, #15, and conflicts K8, K9, K10. It builds on WP-3.1f2b1, which is already on this branch.

## Global Constraints

- **Layers and isolation:**
  - `app/agents/runtime.py` imports no models and no DB code. Its effects go through ports, and every port protocol change is reviewed by AG-13 🔒.
  - `uv run lint-imports` must still report "10 kept, 0 broken".
- **Provider config writes:**
  - Only `app/services/provider_readiness.py` and `app/services/provider_settings.py` write `provider_configs`. The reset's DB write lives in `provider_readiness.py`, and `DbProviderGate` calls it.
  - SECURITY_MODEL §214 requires an audit row for every provider config change. The reset's audit is `provider.readiness_reset`, with actor `system`/`worker` and metadata `{provider, cause}`, and no error text.
- **Fixed values (exact strings):**
  - reject causes: `"auth"` and `"not_found"`;
  - verdict reasons: `"provider_rejected"` and `"pricing_changed"`;
  - report marker key: `"invalidated"`, holding `{"cause", "at"}`;
  - `agent_activity` length: `RECENT_RUNS` (= 10).
- **Not-found test:** an `LLMError` counts as not-found when `status_code == 404` or `vendor_type == "not_found_error"`. An auth reject is `kind == "auth"`; that kind already includes billing and permission errors.
- **Reset behaviour:**
  - A reset is best-effort. A failed reset is logged (`provider_reject_unrecorded`, with ids and error type) and never changes the run's end.
  - A reset writes only when the row still holds the same report (`readiness_checked_at` equals the timestamp `check` returned) and that report is not already invalidated. A newer smoke is never overwritten, and many failing runs write one reset and one audit row.
- **API verdict:** the api's verdict (no `held`) never computes `pricing_changed`, because the api loads no tariffs in v1 (CONFIGURATION).
- **`RUNTIMES_AVAILABLE["agent_runtime"]` stays `False`.** Only the UI text changes (Keputusan #9).
- **Frontend:**
  - UI text comes only from i18n keys, and `id.json` and `en.json` must have the same keys.
  - Run `npm run format:check && npm run lint && npm run lint:guards && npm run typecheck && npm test`.
- **Backend checks:** `uv run ruff check . && uv run ruff format --check . && uv run pyright && uv run lint-imports`. Tests run only through the worktree runner `f1-pytest.sh`, never two pytest processes on one DB.
- **No migration and no new library.** Secret-like test fixtures are built by concatenation. No `rf"…{x}…"` in Semgrep-scanned modules that have async methods in a class.
- **Docs:** Indonesian, with identifiers in English and claims labelled [Pasti]/[Kemungkinan Besar]/[Menebak].

## Review Focus

1. **A smoke lands between a run's gate check and its rejected call.** The newer passing report stays `passed`; the reject is a no-op (Task 2).
2. **Twenty runs fail `auth` at the same moment.** One reset and one audit row, with no lost update (Task 2).
3. **A run whose provider error comes from its own cancel or deadline.** No reset: only a real `auth`/404 from the provider counts. The runtime calls `reject` only for the `LLMError` it classified, and only when `run.stop.reason is None` (Task 1).
4. **An api verdict (no `held`) for a row whose `pricing_version` differs from some worker.** The verdict stays as it was; only the worker gate refuses (Task 3).
5. **A dashboard for a user who sees no project.** `agent_activity` is `[]`, with nothing leaked from other projects (Task 4).

- Test: `backend/tests/integration/test_provider_readiness.py`, `backend/tests/security/test_runtime_gate.py`

**Interfaces:**
- Produces:

  ```python
  async def invalidate_report(
      session: AsyncSession, *, cause: RejectCause, report_at: datetime | None, audit: AuditWriter
  ) -> bool
  ```

  It returns True when it wrote. It writes `readiness_status="unknown"` and `readiness_report = {**report, "invalidated": {"cause": cause, "at": <iso now>}}`, assigning a new dict. It also writes the audit row. It writes only when `row.readiness_checked_at == report_at`, `"invalidated" not in row.readiness_report`, and the row is locked `FOR UPDATE`. The caller commits.
- `provider_ready` returns `ProviderVerdict("unknown", "provider_rejected")` when `readiness_status == "unknown"` and the report carries `"invalidated"`. This check comes before the generic `no_report`. `record_report` replaces the whole report, so the marker goes away with the next smoke.
