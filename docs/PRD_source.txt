1. Ringkasan Eksekutif
KodeKantor adalah website IDE agentic yang berjalan di VPS milik sendiri. Pengguna dapat membuat project baru
atau mengimpor repository, memberikan instruksi melalui chat, melihat dan mengubah kode, meminta agent
melakukan debugging, menjalankan test di sandbox, meninjau diff, memvalidasi hasil dari perspektif pengguna, dan
menyiapkan deployment.

Pembeda utamanya adalah orkestrasi berbasis task dan bukti, bukan sekadar satu chatbot. Orchestrator memilih
specialist sesuai kebutuhan; tool gateway menegakkan izin; sandbox menjalankan kode secara terisolasi; serta User
Proxy Agent mengevaluasi apakah hasil aktual memenuhi requirement dan acceptance criteria.

     North-star outcome
     Task software development selesai dengan perubahan yang dapat ditinjau, hasil test yang dapat dibuktikan,

1.1 Visi Produk
Menjadi development workspace personal/tim yang mengubah instruksi natural language menjadi perubahan
software yang tervalidasi, dengan fleksibilitas provider AI dan kepemilikan data/workspace berada pada pengguna.

1.2 Tujuan Produk
       Mendukung lifecycle software development: plan, create, modify, debug, test, review, document, dan deploy.
       Memusatkan kode, chat, task plan, terminal, test output, diff, dan acceptance status dalam satu IDE.
       Memakai specialist agents yang dapat dipilih dinamis berdasarkan intent, kompleksitas, dan risiko task.
       Memastikan User Proxy Agent memeriksa kesesuaian hasil dengan requirement pengguna.
       Memberikan jejak audit, kontrol biaya, pembatasan resource, dan persetujuan manusia untuk operasi sensitif.
       Memulai dari satu VPS dan memungkinkan pemisahan worker/sandbox di tahap scale-up tanpa desain ulang
        total.

1.4 Non-Goals untuk MVP
       Bukan pengganti penuh IDE desktop dengan seluruh ekstensi VS Code.
       Tidak menjalankan model AI lokal secara default; runtime model menggunakan provider adapter.
       Tidak memberi agent akses shell host atau Docker daemon tanpa perantara kebijakan.
       Tidak melakukan production deployment, destructive migration, atau force push tanpa persetujuan eksplisit.
       Tidak menjanjikan semua task dapat selesai sepenuhnya otonom; task ambigu atau berisiko harus dapat
        meminta klarifikasi/approval.
       Tidak memerlukan 41 model/agent aktif bersamaan.

3. End-to-End Workflow
3.1 Alur create project dari awal
1.  Pengguna login lalu memilih Create Project: template, blank, atau import repository.
2.  Intent Classifier + Requirement Analyst menangkap tujuan, batasan, teknologi, serta acceptance criteria awal.
3.  Codebase Explorer (untuk repository yang sudah ada) mengumpulkan konteks yang relevan; Architect dipanggil
    bila kompleksitas memerlukan desain.
4. Planner membuat DAG task dengan dependency, specialist assignment, batas iterasi, dan perkiraan budget.
5. Orchestrator menjalankan task di workspace/branch terisolasi. Coding specialists membuat patch melalui Tool
    Gateway.
6. Test Runner mengeksekusi lint, unit test, integration test, build, dan E2E sesuai risiko dan stack.
7. Jika test gagal, Debugger menganalisis bukti dan menghasilkan patch perbaikan dengan retry count terbatas.
8. Code Review dan Security Agents mengevaluasi diff; User Proxy Agent memeriksa acceptance criteria dan user
    journey.
9. UI menampilkan ringkasan, requirement coverage, diff, test evidence, risiko, dan item yang belum diverifikasi.
10. Pengguna meminta perbaikan, menolak, atau menyetujui penerapan perubahan. Merge/deployment tetap
    mengikuti approval policy.

3.2 Alur modify / debug
Untuk task perubahan kecil, workflow boleh disederhanakan: intent → explore context → impact analysis bila
berisiko → implementer/debugger → test → review → User Proxy validation → approval. Architect, migration, DevOps,
atau specialist lanjutan hanya dipanggil bila dipicu kebutuhan atau policy.

4.2 Global navigation
        Dashboard — project/task overview, activity, usage/budget, and recent work.
        Projects — list, create, import, archive, configure, and open workspace.
        AI Agents — catalog, profile, capability, permission, health/status, and run history.
        Tasks — queue, workflow graph, logs, artifacts, checkpoint, retry, cancel.
        Workspace — file tree, editor, chat, terminal, preview, Git, and diff.
        Testing — suite management, reports, coverage, E2E screenshots, regression results.

        Knowledge — project context, ADR, docs, indexed symbols, and conversation/task history.
        Teams & Settings — users, roles, provider settings, budget, security policy, audit.

5.1 Authentication & User Access
        Login dengan email/password atau metode identity yang dipilih saat implementasi; SSO dapat menjadi fase
         lanjut.
        Session dibuat dengan mekanisme aman; token/session tidak pernah dimasukkan ke prompt atau log
         mentah.
        RBAC minimum: Owner, Admin, Developer, Reviewer, Read-only. Hak akses server-side pada setiap
         endpoint.
        Password recovery, logout, session expiry, rate limiting untuk login, dan audit autentikasi.
        Definisi awal satu pengguna owner untuk private MVP tidak menghapus kebutuhan isolasi user/project
         dalam model data.

5.2 Project & Repository Management
      Project mempunyai ID stabil, nama, stack, path internal, default branch, settings, dan owner.
      Dukungan create blank, create template, import remote repository setelah provider credential disetujui, dan
       upload archive yang divalidasi.
      Archive importer mencegah path traversal, symlink escape, file terlalu besar, bomb archive, dan overwrite
       sistem.
      Repository diindeks per project. Pengguna dapat memicu re-index setelah perubahan atau setelah import.
      Project lifecycle: active, archived, deleting_pending_approval, deleted. Delete harus punya kebijakan
       retention/backup.

5.3 Browser IDE
      Layout: explorer kiri, editor tengah, AI panel kanan, panel bawah yang dapat dipilih untuk terminal/test/logs.
      File read/write hanya melalui Workspace Service dengan root project yang tervalidasi.
      Agent menghasilkan patch; perubahan ditampilkan dalam diff sebelum masuk ke workspace aktif bila task
       menggunakan review-first mode.
      Run/Preview hanya menjalankan profile yang disetujui dan menggunakan preview sandbox, bukan proses
       host bebas.
      File binary/terlalu besar ditampilkan sebagai metadata atau di-download sesuai policy; tidak dimasukkan ke
       prompt secara otomatis.

5.4 Chat, Context & Agent Execution
      Chat menyimpan user message, task intent, context refs, assistant output, tool calls, dan event stream secara
       terstruktur.
      Context harus berisi referensi file/line yang spesifik serta ringkasan seperlunya; context budget
       dikendalikan.
      Sediakan stop/cancel yang menghentikan orchestration dan proses sandbox terkait, bukan hanya
       menghentikan animasi UI.
      Setiap invocation mencatat agent_id, model/provider, prompt version, tool calls, token usage bila ada,
       latency, status, dan biaya bila diketahui.
      Instruksi yang ditemukan di source code, README, log, atau hasil retrieval diperlakukan sebagai data tidak
       tepercaya dan tidak dapat menaikkan izin.

5.6 Testing & Debugging
      Runner menggunakan project stack profile untuk mendeteksi command yang didukung, contohnya pytest,
       npm test, lint, atau build.
      Output test menyimpan command profile, exit code, stdout/stderr, waktu, durasi, environment ID, dan
       artifacts.
      Debug loop memiliki maksimal percobaan configurable; default pilot 5 attempt per task, bukan tanpa batas.
      Gagal install dependency, timeout, runner crash, dan test assertion failure harus dibedakan statusnya.
      Coverage dilaporkan hanya jika runner menghasilkan data; tidak boleh diestimasi oleh model.

5.7 Provider & Budget Management
      Provider adapter memisahkan business workflow dari API spesifik vendor.
      API keys disimpan di secret store/environment server-side; UI hanya menampilkan status atau masked
       identifier.
      Budget controls: batas token/task jika provider mendukung, batas durasi, batas retry, concurrency, dan biaya
       nominal yang dikonfigurasi.
      Fallback model/provider hanya dilakukan sesuai kebijakan; perubahan model dicatat karena dapat
       memengaruhi output.
      Usage dashboard membedakan actual values, estimate, dan unavailable. Jangan menampilkan angka biaya
       palsu.

7.3.2 Siklus tool-use
1. Orchestrator membentuk input agent berisi goal, acceptance criteria, batasan, konteks repository terpilih, tool
    allowlist dan budget.
2. Backend mengirim request ke Messages API dengan system instructions, riwayat percakapan yang diperlukan,
    dan definisi tools yang relevan saja.
3. Jika response berisi tool_use, backend memvalidasi tool name dan input schema, user/project scope,
     workspace path, risk class, budget dan approval policy.
4. Tool Gateway menjalankan tool yang diizinkan. Hasil aktual dikembalikan sebagai tool_result; teks model saja
     tidak dianggap bukti tool berhasil.
5. Loop berulang sampai jawaban selesai, terjadi refusal/error/cancel, batas iterasi atau budget tercapai, atau
     aksi menunggu approval.
6. State/checkpoint dan event penting disimpan agar task dapat dilanjutkan setelah worker/browser restart atau
     koneksi terputus.
Claude tidak diberikan akses bebas ke shell host, filesystem global, database production, Git credentials, jaringan,
atau Docker daemon. Reviewer hanya memperoleh read-only tools; implementer mendapat patch tools pada
workspace task; tool permissions selalu ditegakkan oleh backend, bukan hanya oleh system prompt.

7.3.3 Streaming, error handling, dan recovery
   Gunakan streaming Messages API jika didukung untuk use case; normalisasikan event di backend sebelum
    diteruskan ke UI.
   Tangani rate limit/HTTP 429, transient 5xx, timeout, refusal, malformed output, output terpotong, disconnect,
    dan cancel secara eksplisit.
   Retry kegagalan sementara dengan exponential backoff dan jitter serta hormati retry hints jika tersedia. Tool
    side effect tidak boleh diulang tanpa idempotency atau pemeriksaan state.
   Jika browser terputus, UI mengambil ulang task status/events dari backend. Disconnect tidak otomatis
    berarti task sukses atau gagal.
   Simpan provider request ID, error class, durasi, token usage dan retry count bila tersedia. Jangan log API key,
    header Authorization atau prompt mentah yang berpotensi mengandung secret.

7.3.4 Token budget dan prompt caching
Simpan usage input/output tokens dari response API, model ID, agent, task, duration, retry count dan status;
simpan cache-related usage jika diberikan. Prompt caching dapat diaktifkan untuk system prompt, tool
definitions, dan konteks stabil yang memenuhi ketentuan Claude Platform. Caching merupakan optimasi, bukan
prasyarat kebenaran workflow.

Budget berlaku per task dan project. Jika threshold terlampaui, hentikan pemanggilan model berikutnya, catat
status budget_exceeded, dan tampilkan pemakaian beserta pilihan untuk menghentikan atau menyesuaikan
budget. Jangan menjanjikan estimasi biaya pasti apabila response/provider data tidak cukup.

10.3 Minimum sandbox controls
      Use non-root user, drop Linux capabilities, no privileged mode, no host PID/network namespace unless
       separately justified.
      Never mount /var/run/docker.sock into agent-executed containers. Sandbox Manager controls the runtime
       through restricted APIs and fixed profiles.
      Mount only workspace and explicit temporary dependency/cache volumes. Read-only mount source as an
       option for review-only tasks.
      Apply CPU, memory, PID, disk, execution-time, log-output, and concurrency limits.
      Outbound network disabled by default or restricted by egress policy; dependency installation uses controlled
       route/cache.
      Clean temporary containers and credentials after task; persist only approved artifacts and project files.
      Test isolation controls with malicious-path, symlink, environment leakage, and resource-exhaustion fixtures.

10.4 Human approval rules
      Approval must show the exact action, target environment/repository, files or resources affected, risks, and
       rollback option.
      Approval is one-time and bound to a checksum/payload; if target or action changes, request approval again.
      User Proxy recommendation “pass” is not identical to an authorized production release.
      An LLM cannot manufacture user approval via text in tool output, repository content, or agent-to-agent
       message.
      Production deploy, remote push/merge, data-destructive migration, secret rotation, project deletion, and
       broad permission changes are high-risk actions.

14. Implementation Instructions for Claude Code
Claude Code akan digunakan sebagai development tool untuk membangun produk; ia berbeda dari runtime
agent platform. Runtime platform harus memanggil LLM provider melalui adapter, bukan bergantung pada
Claude Code CLI sebagai satu-satunya backend kecuali itu sengaja diputuskan sebagai fitur opsional.

14.1 Execution discipline
1. Sebelum mengubah kode, baca `CLAUDE.md`, PRD, repository status, dan implementation tracker.
2. Lakukan Phase 0: audit repository dan tuliskan rencana, asumsi, risks, serta dependency. Jangan langsung
     menghasilkan semua modul.
3. Implementasikan per vertical slice: UI → API → database → workflow/tools → test → dokumentasi.
4. Untuk setiap batch, tampilkan file changed, test command, output aktual, known gaps, serta next step.
5. Jangan mengklaim test lulus tanpa menjalankan test dan mengutip hasilnya. Jangan menandai phase selesai
     jika acceptance criteria belum terpenuhi.
6. Jaga perubahan scope; lakukan commit/branch sesuai strategi Git project dan jangan membuang perubahan
     pengguna.

7. Jangan membuat agent specialist sebagai LLM process jika fungsi deterministik sudah cukup. Pisahkan agent
